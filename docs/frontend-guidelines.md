# 리트리버 프런트엔드 구현 가이드

> 상태: 초안
>
> 이 문서는 React 코드를 어떻게 구성하고 검증할지 정의한다. 제품 요구사항은 `docs/PRD.md`, 화면 흐름은 `docs/ui-patterns.md`, 시각 규칙은 `docs/design-system.md`가 우선한다.

## 1. 작업 전 읽기 순서

프런트엔드를 변경하기 전에 다음 순서로 확인한다.

1. `docs/PRD.md` — 무엇을 만들어야 하는가
2. `docs/ui-patterns.md` — 사용자가 어떻게 이동하고 어떤 상태를 보는가
3. `docs/design-system.md` — 화면을 어떤 시각 규칙으로 표현하는가
4. 이 문서 — React로 어떻게 구현하고 검증하는가

문서와 코드가 다르면 임의로 한쪽을 맞다고 가정하지 않는다. 현재 동작을 확인하고, 제품 결정이 필요한 차이라면 `[결정 필요]`로 기록한 뒤 개발자에게 확인한다.

## 2. 현재 스택과 경계

- React + TypeScript
- Vite
- React Router
- 카카오맵 JavaScript SDK
- FastAPI가 `/api/*`와 빌드된 정적 파일을 제공

프런트엔드 작업의 기본 범위는 `frontend/`다. API 계약이 부족하다는 이유만으로 FastAPI, 데이터베이스, 수집 로직을 함께 바꾸지 않는다. 백엔드 변경이 필요하면 별도 작업으로 범위와 계약을 먼저 합의한다.

## 3. 디렉터리 역할

```text
frontend/
├─ src/
│  ├─ api/          HTTP 요청과 응답 처리
│  ├─ components/   화면 컴포넌트
│  ├─ lib/          UI와 무관하게 재사용 가능한 계산·표현 함수
│  ├─ App.tsx       현재 탐색 화면의 상태 조합
│  ├─ router.tsx    라우트 정의
│  ├─ styles.css    전역 스타일과 디자인 토큰
│  └─ types.ts      API·화면 공용 타입
├─ vite.config.ts   개발 프록시와 빌드 설정
└─ package.json     스크립트와 의존성
```

- 새 파일은 역할이 가장 가까운 기존 디렉터리에 둔다.
- 파일 하나가 API 호출, 지도 조작, 화면 표시를 모두 담당하게 만들지 않는다.
- 한 번만 쓰는 작은 표현을 성급하게 공통 컴포넌트로 추출하지 않는다.
- 로그인·마이페이지처럼 독립 화면이 늘어날 때 `pages/` 도입을 검토한다.

## 4. 컴포넌트와 상태

- 함수형 컴포넌트와 명시적인 Props 타입을 사용한다.
- 서버 응답 타입은 `types.ts`, 해당 컴포넌트에서만 쓰는 Props는 컴포넌트 파일에 둔다.
- 상태는 사용하는 가장 가까운 컴포넌트에 둔다. 여러 형제 컴포넌트가 함께 쓰면 공통 부모로 올린다.
- 렌더링 중 계산할 수 있는 값은 별도 state로 중복 저장하지 않는다.
- `useEffect`는 외부 시스템과 동기화할 때 사용한다. 사용자 이벤트는 이벤트 핸들러에서 처리한다.
- 요청이 바뀌거나 컴포넌트가 사라질 때 `AbortController`로 불필요한 요청을 취소한다.
- 오래된 응답이 최신 결과를 덮어쓰지 않도록 요청 순서를 보호한다.
- 카카오맵 객체처럼 React 외부의 변경 가능한 객체는 `ref`로 관리하고 cleanup에서 marker·listener·overlay를 정리한다.

> [결정 필요: FE-01] 전역 상태 관리 도구 도입 시점
>
> - 현재 구현: React 내장 state와 props만 사용
> - 권장안: 로그인 사용자 정보가 여러 라우트에서 필요해질 때 먼저 Context + 전용 hook으로 해결하고, 복잡도가 실제로 커질 때 외부 도구를 검토한다.
> - 결정 영향: 의존성, 학습 비용, 디버깅 방식이 달라진다.

## 5. API 통신

- API 호출은 `src/api/client.ts`를 통해서만 수행한다.
- 컴포넌트 안에 endpoint 문자열과 공통 오류 처리를 반복하지 않는다.
- 브라우저에는 카카오 JavaScript 키만 허용한다. Supabase secret, 카카오 REST 키, `CRON_SECRET`을 프런트 코드나 `VITE_*` 변수에 넣지 않는다.
- 서버가 반환한 한국어 오류 메시지를 우선 사용하고, 응답을 읽을 수 없을 때만 공통 fallback을 사용한다.
- `/api/found-items` 결과를 브라우저나 서비스 워커에 영구 캐시하지 않는다.
- API 타입이 바뀌면 `types.ts`, 호출부, loading·empty·error 상태를 함께 확인한다.

## 6. 라우팅

- 라우트는 `src/router.tsx` 한 곳에서 선언한다.
- 페이지 이동이 필요한 화면은 임의의 `window.location` 변경 대신 React Router를 사용한다.
- 로그인 후 돌아갈 위치, 인증이 필요한 화면, 존재하지 않는 경로 처리는 인증 기능을 구현할 때 함께 정의한다.

> [결정 필요: FE-02] 로그인·마이페이지 라우트와 인증 경계
>
> - 현재 구현: `/` 한 개의 공개 라우트만 존재
> - 권장안: `/login`, `/mypage`를 별도 라우트로 두고, 검색·지도는 비로그인 사용자에게도 유지한다.
> - 결정 영향: 인증 제공자, 세션 보관, 보호 라우트, 로그인 후 복귀 동작의 기준이 된다.

## 7. 스타일

- 새 색상·간격·radius·shadow는 `docs/design-system.md`의 토큰을 사용한다.
- 전역 스타일은 `styles.css`에 두되, 컴포넌트 이름을 기준으로 범위를 좁힌 클래스명을 사용한다.
- 인라인 스타일은 카카오맵 SDK가 문자열 또는 객체를 요구하는 경우처럼 피할 수 없을 때만 사용한다.
- 레이아웃을 맞추기 위한 임의의 숫자를 추가하기 전에 기존 spacing 토큰과 구조를 확인한다.
- hover에만 정보를 의존하지 않는다.
- `focus-visible`을 유지하고 `prefers-reduced-motion`을 존중한다.

## 8. 상태와 접근성

모든 비동기 기능은 다음을 명시적으로 처리한다.

- 초기 상태
- loading
- success
- empty
- error
- disabled

상태 메시지는 가능하면 같은 위치에서 바뀌게 해 화면 이동을 줄인다. 결과 갱신은 `role="status"`와 `aria-live="polite"`를 사용한다. 오류 때문에 즉시 사용자의 조치가 필요할 때만 더 강한 알림을 검토한다.

- 입력에는 화면에 보이거나 `sr-only`인 label이 있어야 한다.
- 클릭 가능한 비버튼 요소를 만들지 말고 기본 `button`, `a`, `input`을 우선한다.
- 목록은 `ul`/`ol`과 `li`, 제목은 논리적인 heading 순서를 사용한다.
- 지도만으로 정보를 제공하지 말고 목록이나 텍스트로 같은 핵심 정보를 제공한다.
- 키보드만으로 검색, 결과 선택, 범위 초기화가 가능해야 한다.

## 9. 테스트와 검증

변경 범위에 맞게 아래 검증을 수행한다.

```bash
cd frontend
npm run build
node --test ../tests/web/test_map_radius.js

cd ..
uv run --with 'pytest>=8,<9' pytest -q
```

- 순수 계산 함수는 빠른 단위 테스트를 우선한다.
- 실패 케이스 테스트에는 정상 케이스를 함께 둔다.
- UI를 크게 바꾼 경우 FastAPI와 프런트엔드를 실행하고 실제 화면을 확인한다.
- 데스크톱과 모바일 폭에서 검색, 선택, 결과 목록, 지도 조작을 확인한다.
- 느린 네트워크·0건·API 오류·버튼 disabled 상태를 확인한다.
- 생성된 `src/retriever_lost_found/web/static/` 파일은 Vite 빌드 결과다. 소스 대신 직접 수정하지 않는다.

> [결정 필요: FE-03] 컴포넌트 테스트 도구 도입
>
> - 현재 구현: TypeScript 빌드, Node 테스트, FastAPI 테스트가 중심이며 React 컴포넌트 테스트 도구는 없음
> - 권장안: 로그인 폼이나 마이페이지처럼 상호작용이 늘어나는 첫 기능에서 Vitest + Testing Library를 함께 도입한다.
> - 결정 영향: 의존성과 테스트 작성량이 늘지만 UI 회귀를 더 일찍 발견할 수 있다.

## 10. 완료 기준

- PRD와 UI 패턴의 해당 요구사항을 충족한다.
- 기존 백엔드 계약과 제품 동작을 의도 없이 바꾸지 않는다.
- TypeScript 오류와 빌드 오류가 없다.
- loading, empty, error, disabled 상태가 있다.
- 키보드와 스크린 리더용 이름을 확인했다.
- 모바일과 데스크톱에서 직접 확인했다.
- 관련 문서와 테스트를 갱신했다.
- 관련 없는 화면을 재설계하지 않았다.
