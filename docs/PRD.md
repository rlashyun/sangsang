# 리트리버(Retriever) PRD

> 한 줄 요약: 경찰청 습득물 데이터를 매일 모아, 잃어버린 지점 반경 1·3·5km 안의 보관기관과 실제 보관 중인 습득물을 지도에서 바로 탐색하게 해 주는 웹 서비스.

---

## 1. 배경 및 문제 정의

### 1.1 배경

경찰청은 습득물 정보를 공공데이터포털 API로 공개한다. 우리는 그중 두 개를 사용한다 —
**유실물 연계기관 습득물 API**(지하철·공항·터미널 등)와 **경찰관서 습득물 API**(경찰서·지구대·파출소).

데이터는 이미 공개되어 있다. 문제는 **찾는 방법**이다. 공식 창구인 경찰민원24는 물품분류·지역·기간 드롭다운 검색이고, 습득물 제목은 기관 담당자가 자유 기재한다("검정색 지갑", "지갑 1개", "지갑(남성용)"). 그리고 습득물은 결국 **실물로 어딘가에 보관되어 있어서**, 탐색의 끝은 언제나 "그래서 어디로 가야 하나"인데 기존 검색은 기관 이름 텍스트만 돌려준다.

### 1.2 문제 정의

**고객은 누구인가**

최근 며칠 안에 대중교통·역사·상업시설 주변에서 물건(지갑·휴대폰·가방·카드·무선이어폰·모자)을
잃어버렸고, 정확한 물품명은 몰라도 **잃어버린 대략적인 장소는 기억하는** 사람.

**고객이 겪는 문제**

> 나는 **어제 강남역 근처에서 지갑을 잃어버린 사람**이다. 나는 **내 지갑이 어느 보관소에 들어와 있는지 확인하고 찾으러 가는 것**을 하려 한다. 그러나 **검색이 정확한 분류·용어를 요구하고 결과를 찾아도 그 기관이 내가 잃어버린 곳에서 가까운지 알 수 없기** 때문에 **검색을 몇 번 헛돌다 포기하는 일**이 발생한다.

| 탐색이 어려운 이유 | 리트리버의 해결 |
| --- | --- |
| 정보가 여러 기관/출처에 흩어져 있음 | **습득물 데이터 통합** |
| 어디에서 잃어버렸는지 불확실함 | **방문 장소 기반 다중 탐색** |
| 습득물이 너무 많음 | **위치 기반 탐색 범위 축소** |
| 같은 물건도 표현이 다름 | **물품정보 표준화** |
| 공공데이터 설명이 부족함 | **Vision AI로 사진 정보 보강** |
| 비슷한 물건이 많음 | **유사도 기반 Ranking** |
| 분실자가 물건 사진을 가지고 있음 | **이미지 임베딩 기반 유사 검색** |

**결정 필요** — 현재 위 서술은 팀 관찰과 기존 서비스 UI 분석에 근거한 가설이다. 실사용자 인터뷰 결과와 경쟁 서비스 리뷰의 불만 수집 데이터로 교체해야 한다.

## 2. 목표와 성공 지표

### 2.1 목표 (Goals)

1. 분실자가 기억나는 표현이나 오타가 포함된 검색어로도 데이터베이스에 존재하는 자기 분실물을 정확하게 탐색한다. 현재 MVP는 퍼지 매칭을 사용하며, TOP-3 포함률 95%는 평가셋 구축 후 검증한다. (추후에 다른 검색 알고리즘을 사용할 예정이다.)
2. 분실 지점 **반경 1, 3, 5km 안의 모든 보관기관(연계기관 + 경찰관서)을 한 지도에서** 보여주고, 각 기관이 지금 무엇을 몇 건 보관 중인지 즉시 확인시킨다. (반경 설정 기능)
3. 지도 기반 UI로 보관 기관 위치를 시각화하여 **실제 수령 행동까지** 연결한다.
4. 분실물 검색 조건과 이메일을 저장해 신규 등록 알림을 제공한다. 이메일만 수집할지, 회원가입 기반으로 운영할지는 비교 실험 후 결정한다.

### 2.2 비목표 (Non-Goals)

1. **분실물 신고 등록 및 습득자–분실자 직접 매칭.** 우리는 공공 습득물 DB의 *탐색*만 한다.
2. **수령 예약·본인 인증·택배 발송 등 실제 반환 절차.** 기관 방문으로 연결하고 끝낸다.
3. **6개 서비스 카테고리 밖의 습득물.** 현재 수집 단계에서 제외된다.
4. **자체 모바일 앱.** 모바일 웹으로 대응.
5. 카테고리 확장(6개 → 추가. 수집·매핑 테이블 확장)

### 2.3 성공 지표

| 지표 | 기준선 (날짜) | 목표치 (날짜) | 비고 |
| --- | --- | --- | --- |
| 탐색 성공률 — 정답이 DB에 있을 때 TOP-3 포함 | 결정 필요 (평가셋 미구축) | 95% | — |
| 선택 반경 내 기관이 없는 경우 | 결정 필요 | 반경 확장 전환율 측정 | 1km 결과가 없으면 3km·5km 확장을 제안하되 자동 전환 여부는 사용자 테스트 후 결정 |
| 보관기관 매칭률 (`location_match_status = 'matched'`) | 결정 필요 — `ingestion_runs`로 측정 가능 | 99% | — |
| 일일 동기화 성공률 (`status = 'succeeded'`) | 결정 필요 |  | — |

### 2.4 가설 및 임팩트

**핵심 가설** — 분실자가 실패하는 이유는 *데이터가 없어서*가 아니라 (a) 검색어가 등록명과 맞지 않고 (b) 분실위치를 기준으로 직관적인 탐색이 안된다. 동일한 공공 DB 위에 AI 매칭과 반경 1km 지도를 얹으면 탐색 성공률이 유의하게 오른다.

**검증 방법** — 실제 습득물 기록에서 N건을 표본 추출하고, 각 건에 대해 "그 물건을 잃어버린 사람이 썼을 법한 질의"를 사람이 작성해 질의–정답 쌍 평가셋을 만든 뒤 TOP-3 포함률을 측정한다. N, 작성 기준, 작성자 수는 **결정 필요**.

### 2.5 가드레일 지표

1. **응답 속도** — `/api/found-items` p95 **결정 필요** (제안: 1.5초) → 위치검색, 물품 검색 모두 1.5초. 함수 `maxDuration` 300초는 동기화용이며 조회는 즉시 응답해야 한다. (데이터 최신화 동기화 시간임)
2. **오탐 유입** — 퍼지 임계값(현재 0.5, 2자 이하 질의 0.7)을 완화할 때 무관한 물품이 상위에 오르지 않을 것. 허용 상한 **결정 필요**.

## 3. 범위

### 3.1 포함 범위 (In Scope) — 현재 구현 완료

1. 두 습득물 API에서 6개 카테고리만 선별해 매일 Supabase에 **멱등 upsert**하는 수집 파이프라인 (Vercel Cron, KST 09:00)
2. 출처별 보존기간(연계기관 6개월 / 경찰관서 6개월) 자동 정리 — **동기화가 완전히 성공한 출처만** 삭제 수행
3. 카카오맵 장소명·주소 검색 → 좌표 변환 → 1·3·5km 중 선택한 반경을 지도에 표시
4. 전국 보관기관 지도: 연계기관 핀 + 경찰관서(노란) 핀, 줌 레벨별 클러스터/개별 전환, **핀 배지에 실제 보관 물품 수** 표시
5. 선택한 반경 내 기관들의 습득물 전체 목록 조회, 개별 기관 핀 클릭 시 해당 기관만 재조회, "선택 반경 전체"로 복귀
6. 물품명·원분류명·색상·설명 대상 **다중 필드 가중 퍼지 검색** (유사도 수치는 내부 평가에 사용하고 사용자 화면에는 노출하지 않음)
7. 서버 전용 키 격리(카카오 REST 키·Supabase secret 키 브라우저 미전달), 전 테이블 RLS + `service_role` 전용 권한, CSP·보안 헤더
8. 동기화 감사 로그(`ingestion_runs`)와 출처별 중복 실행 차단

### 3.2 제외 범위 (Out of Scope) (앞으로 만들어야할 것)

1. **이미지 기반 검색** — `vector` 확장은 켜져 있으나 임베딩 컬럼·파이프라인 없음. 4.2의 P1로 분리.
2. **습득물 사진 표시** — `image_url`은 수집·저장되지만 UI에는 아직 노출하지 않는다. 공공데이터 원문 사진을 사용하되, 구현 시 CSP `img-src` 설정과 오류 이미지 처리를 검증한다.
3. **반경 밖 거리 단위(확장검색) 물품 검색** — 현재 위치 선택(1km→3km→5km)
4. 계정, 알림

### 3.3 가정 및 제약사항

- **콘텐츠:** 습득물 제목·설명은 기관 담당자 자유 기재이며 품질이 고르지 않다. 정규화와 퍼지 매칭으로 흡수하되 **원문은 변형하지 않는다**.
- **법적:** 경찰청 공공데이터 이용약관 및 카카오 API 서비스 약관 준수. 습득물 설명 내 개인정보(카드 명의자명 등) 취급 기준 **결정 필요**.
- **기술적:**
    - 데이터 신선도는 최대 24시간 지연(일 1회 크론). Vercel Hobby는 지정 시간대 내에서 실행이 지연될 수 있다.
    - 습득물 검색어 30자 상한 → 넘기면 경고 알림 발생.
    - **보관기관 매칭 실패(unmatched/ambiguous) 건은 `storage_location_id`가 NULL이라 지도·검색에서 전혀 보이지 않는다.**

        → API출력 결과와 데이터베이스 내 기관 이름이 다른 경우 혹은 존재하지 않는 경우 가끔 있다. 이거 해결해야함

    - `/api/institutions`는 CDN 5분 캐시, `/api/found-items`는 무캐시.
- **예산/리소스:** Vercel Hobby + Supabase 무료 티어 가정 → 필요시 유료구매 가능

## 4. 솔루션 개요

### 4.1 접근 방식

**"물품명으로 찾기"가 아니라, "잃어버린 장소로 좁히고 그 안에서는 대충 적어도 찾아지게"**

공간을 1차 필터로 쓴다. → 검색으로 2차필터

**기존 대안 대비 차별점**

| 기존 대안 | 부족한 점 | 우리의 해결 방식 |
| --- | --- | --- |
| 경찰민원24 (경찰청 유실물 통합포털) | 분류·지역 드롭다운 중심, 정확한 용어 요구, 결과가 지도와 분리 | 장소 검색 → 반경 1km 지도 → 그 안에 실제 보관 중인 물품만 좁혀 제시 |
| 각 기관 개별 유실물센터 페이지 | 기관마다 흩어져 있고 경찰 습득물과 합쳐 볼 수 없음 | 연계기관 + 경찰관서를 한 지도·한 목록으로 통합 |
| 지역 커뮤니티·분실물 카페 | 비공식·비구조적, 실제 보관소와 연결 안 됨 | 공공 원천 데이터만 사용, 기관 위치로 직접 연결 |
| 단순 키워드 LIKE 검색 | 오타·표현 차이에 즉시 0건 | 다중 필드 가중 퍼지 매칭(편집거리 + n-gram + 토큰 커버리지) |
| 파인딩올 | uiux불편(서버 응답 속도), 지연 문제, 검색 성능 문제, 습득물보관장소와 지도에서 연결이 안됨 | 장소 검색 → 반경 1km 지도 → 그 안에 실제 보관 중인 물품만 좁혀 제시,<br>데이터 동기화 6개월 제한 |

**핵심 차별점**

1. **공간 우선 탐색** — 반경 1km로 후보를 수백 건 수준까지 줄인 뒤에 검색하므로, 느슨한 검색어를 써도 오탐이 감당 가능한 범위에 머문다.
2. **틀리게 써도 찾아지는 검색** — 물품명 1.0 / 원분류 0.9 / 색상 0.82 / 설명·정규화 텍스트 0.72 가중치에 부분일치·부분문자열·편집거리·자카드·접두 보너스를 결합하고, 유사도 %를 사용자에게 그대로 보여준다.
3. **(기관별 실재 재고 표시** — 지도 핀 배지에 그 기관이 *지금* 보관 중인 6개 카테고리 물품 수를 띄워, "갈 만한 곳"을 즉시 판별시킨다.)

### 4.2 핵심 기능(여기서부터 다시 시작)

| 우선순위 | 기능 | 설명 |
| --- | --- | --- |
| P0 ✅ | 일일 습득물 동기화 | 두 API에서 6개 카테고리 선별, 멱등 upsert, 출처별 보존기간 정리, 감사 로그 |
| P0 ✅ | 장소·주소 검색과 반경 스코프 | 카카오 키워드/주소 검색 → 좌표<br>→ 원 + 범위 내 기관 필터 |
| P0 ✅ | 통합 보관기관 지도 | 연계기관·경찰관서 통합 표시, 줌 기반<br>클러스터/개별 전환, 기관별 보관 수 배지 |

### 4.5 핵심 로직 및 예외 케이스

**핵심 로직**

- **카테고리 선별** — `prdtClNm`("상위 > 하위")을 NFKC 정규화·공백 제거·casefold 후 허용 목록과
**정확히 일치**할 때만 수집한다. 부분일치를 쓰지 않는 이유는 오분류 방지.
- **데이터 추가분 수집** — 출처별로 마지막 등록일을 다시 포함해 재조회하고 보존기간 시작일을 하한으로 둔다. 매일 전체 구간을 재수집하지 않는다.
- **보관기관 해석** — 원문 보관장소명을 ① 별칭 테이블 정확 일치 → ② 정규화명/기관명/괄호 제거 기본명 정확 일치 → ③ 접미사 포함 관계 순으로 매칭한다. 후보 1개면 `matched`, 2개 이상이면 `ambiguous`, 0개면 `unmatched`.
- **보존기간 정리** — API 조회와 모든 upsert가 성공한 출처에 한해서만 보존기간 밖 데이터를 삭제한다.
- **반경 필터** — Haversine 거리로 1,3,5km 선택 후 그 거리 이내 기관만 스코프에 넣고, 그 기관 ID 묶음으로 습득물을 조회한다.
- **순위** — 필드별 가중 유사도, 질의 토큰 포함률, 자카드 유사도를 조합해 정렬하고 임계값 미만은 제외한다. 세부 가중치와 임계값은 평가셋으로 튜닝하며, 유사도 수치는 사용자 화면에 노출하지 않는다.

**예외 케이스**

| 상황 | 현재 동작 | 필요한 조치 |
| --- | --- | --- |
| 보관장소명이 기관과 매칭 안 됨 | `storage_location_id` NULL →<br>지도·검색에 안 보임 | `unmatched_count` 모니터링 + 별칭 등록 운영 절차 |
| 관서 명칭 개편 (수원중부 → 수원장안 등) | 명칭 불일치로 매칭 실패 | 검증된 수동 매핑 스크립트 보유, 반영 주기 **결정 필요** |
| 동명 기관 다수 (`ambiguous`) | 저장은 되나 위치 없음 | 지역 코드·주소·상위 관서 정보를 이용한 구분 규칙을 후보로 검증하고, 해결되지 않으면 운영자 확인 대상으로 분리한다. 상세 규칙은 미결. |
| 검색 0건 | "'X'와 유사한 습득물이 없습니다" | 조치 불필요 |
| 검색어 30자 초과 / 좌표 비수치 | 400 에러 | 클라이언트에서 30자 입력 제한과 좌표 유효성 검사를 적용 |
| Supabase·카카오 장애 | 502 + 한국어 메시지 | 재시도 |
| 크론 중복 실행 | 부분 유니크 인덱스로 차단 | 유지 |
| 크론 미실행·지연 (Hobby) | 데이터 24시간 이상 지연 가능 | 실패 알림 채널 **결정 필요** |
| 습득물이 이미 반환됨 | 원천에서 사라져도 보존기간 정리 때만 제거 | 반영 지연 고지 필요 |

## 10. 부록

**데모 시나리오**

1. "강남역"을 장소 검색한다 → 지도가 이동하고 반경 1, 3, 5km 원이 그려진다.
2. 원 안의 연계기관·경찰관서 핀이 뜨고, 각 핀 배지에 **지금 보관 중인 물품 수**가 보인다.
3. 좌측에 반경 1km 기관들이 보관 중인 습득물 전체 목록이 자동으로 표시된다.
4. 물품 검색창에 오타 "아이퐁"을 입력한다 → 아이폰 습득물이 상위 결과에 표시된다.
5. "검정 지갑"을 입력한다 → 등록명이 "지갑(남성용)"이어도 색상·설명 필드 매칭으로 결과가 나온다.
6. 특정 경찰관서 핀을 클릭한다 → 그 기관 물품만으로 목록이 바뀐다. "1km 전체" 버튼으로 복귀한다.
7. 결과 카드에서 보관장소명과 등록일을 확인하고 해당 기관으로 수령하러 간다.

**용어**

- **연계기관** — 경찰청 유실물 시스템에 연계된 지하철·공항·터미널 등의 기관
- **경찰관서** — 경찰서 및 지구대·파출소
- **matched / unmatched / ambiguous** — 습득물의 원문 보관장소명을 좌표가 있는 기관 레코드에 연결한 결과 상태

**기술 스택 (변경 가능)**

- 프런트엔드: React + TypeScript + Vite + React Router
- 지도: 카카오맵 JavaScript SDK
- 백엔드: FastAPI 기반 Vercel Functions
- 프런트엔드 제공 방식: Vite 빌드 결과물을 FastAPI가 정적 파일로 제공
- 데이터: Supabase Postgres + PostGIS (`vector` 확장 활성, 현재 미사용)
- 스케줄: Vercel Cron 2개, 매일 UTC 00:00 = KST 09:00
- 프런트엔드 구조: `frontend/src/{api, components, lib}`
- 백엔드 구조: `src/retriever_lost_found/{web, integrations, ingestion, search, tools}`
- 배포용 정적 파일: `src/retriever_lost_found/web/static`
