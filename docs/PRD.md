> 한 줄 요약: 경찰청 습득물 데이터를 매일 모아, 잃어버린 지점 반경 1km에서 시작해 1.5·2km까지 넓히며 보관기관과 습득물을 지도에서 탐색하는 웹 서비스.

> **2026-11-21 사진 첨부 UI 사용자 승인(4.2):** 카메라 버튼의 파일 선택·클립보드 이미지 붙여넣기·전송 전 미리보기/삭제·채팅 사진 표시까지만 구현한다. 사진은 브라우저 임시 메모리에 두고 서버·DB·스토리지·LLM에 전송하지 않으며 새로고침 시 사라진다. 사진만 보내는 경우도 지원하고 사진 검색이 아직 준비 중임을 표시한다. 함께 작성한 텍스트는 기존 검색으로 전달한다. AI 사진 분석·영구 보관·대화 복원은 후속 범위다.

> **사진 첨부 단계 후속 승인:** 장소가 확정된 뒤 물품을 찾을 때만 첨부를 허용한다. 장소 확정 전의 첨부 버튼·이미지 붙여넣기는 사진을 추가하지 않고 장소부터 입력·선택하라는 채팅 안내를 표시한다. 장소 변경 중에도 같은 제한을 적용한다.

> **2026-11-21 대화형 검색 후속 사용자 결정(4.3-A·4.5):** 물품 검색이 정상적으로 0건이면 1→1.5→2km 순서로 자동 확장하고 처음 결과가 나오는 범위에서 멈춘다. 각 확장 시 이전 반경의 일치 물품이 없어 다음 반경으로 찾는다는 말풍선을 표시한다. 오류·취소는 0건으로 취급하지 않으며 2km를 넘지 않는다. 기존 단일 검색어 재작성은 전체 실행에서 최대 한 번만 유지한다. 마지막 범위·결과·커서·알림 조건을 함께 갱신한다. 기존 ‘물품 0건은 자동 확장하지 않는다’ 규칙은 대화형 검색에서 이 결정으로 대체한다. 일반 검색 API의 동작은 유지한다.

> **2026-11-21 대화형 프런트 사용자 결정(4.3-A):** 채팅은 입력창 위 아래쪽부터 시간순으로 쌓는다. 장소 후보는 최대 5곳씩 표시하며 선택 버튼은 후보 카드 안에 둔다. 장소 숫자 페이지 대신 “다른 장소 살펴보기”·“이전 장소 보기” 답안 버튼을 사용한다. 기존 일반 검색의 장소 페이지와 물품 번호 페이지는 유지한다. 세부 동작은 [대화형 검색 문서](agent-search.md#프런트-연결)를 따른다.

## 1. 배경 및 문제 정의

### 1.1 배경

경찰청은 습득물 정보를 공공데이터포털 API로 공개한다. 우리는 그중 두 개를 사용한다 —
**유실물 연계기관 습득물 API**(지하철·공항·터미널 등)와 **경찰관서 습득물 API**(경찰서·지구대·파출소).

데이터는 이미 공개되어 있다. 문제는 **찾는 방법**이다. 공식 창구인 경찰민원24는 물품분류·지역·기간 드롭다운 검색이고, 습득물 제목은 기관 담당자가 자유 기재한다("검정색 지갑", "지갑 1개", "지갑(남성용)"). 그리고 습득물은 결국 **실물로 어딘가에 보관되어 있어서**, 탐색의 끝은 언제나 "그래서 어디로 가야 하나"인데 기존 검색은 기관 이름 텍스트만 돌려준다.

### 1.2 문제 정의

**고객은 누구인가**

최근 며칠 안에 대중교통·역사·상업시설 주변에서 물건(지갑·휴대폰·가방·카드·무선이어폰·신분증 등)을
잃어버렸고, 정확한 물품명은 몰라도 **잃어버린 대략적인 장소는 기억하는** 사람.

**고객이 겪는 문제**

> 나는 **어제 강남역 근처에서 지갑을 잃어버린 사람**이다. 나는 **내 지갑이 어느 보관소에 들어와 있는지 확인하고 찾으러 가는 것**을 하려 한다. 그러나 **검색이 정확한 분류·용어를 요구하고 결과를 찾아도 그 기관이 내가 잃어버린 곳에서 가까운지 알 수 없기** 때문에 **검색을 몇 번 헛돌다 포기하는 일**이 발생한다.

| 탐색이 어려운 이유 | 리트리버의 해결 |
| --- | --- |
| 정보가 여러 기관/출처에 흩어져 있음 | **습득물 데이터 통합** |
| 어디에서 잃어버렸는지 불확실함 | **방문 장소 기반 다중 탐색** |
| 습득물이 너무 많음 | **위치 기반 탐색 범위 축소** |
| 같은 물건도 표현이 다름 | **물품정보 표준화** |
| 공공데이터 설명이 부족함 | **Vision AI로 사진 정보 보강** |
| 비슷한 물건이 많음 | **유사도 기반 Ranking** |
| 분실자가 물건 사진을 가지고 있음 | **이미지 임베딩 기반 유사 검색** |

**검증 예정 (Q1)** — 위 서술은 팀 관찰과 기존 서비스 UI 분석에 근거한 가설이다. 2026-10-02 실사용자 인터뷰로 다음 두 가설을 검증한다 — ① 사용자는 지도 기반 UI를 더 편리하게 느낀다 ② 검색어 관련 기능 개선이 필요하다.

## 2. 목표와 성공 지표

### 2.1 목표 (Goals)

1. 분실자가 기억나는 표현으로 쓴 검색어로도 데이터베이스에 존재하는 자기 분실물을 정확하게 탐색한다. 현재 MVP는 동의어·BM25·BGE-M3 혼합 검색을 사용하며, TOP-3 포함률 95%는 평가셋 구축 후 검증한다. (추후에 다른 검색 알고리즘을 사용할 예정이다.)
2. 분실 지점 **반경 1km의 보관기관(연계기관 + 경찰관서)을 한 지도에서** 보여주고, 필요하면 1.5·2km로 넓힌다. 1km 안에 기관이 0곳이면 1→1.5→2km 순서로 최대 2km까지 자동 확장한다(4.5).
3. 지도 기반 UI로 보관 기관 위치를 시각화하여 **실제 수령 행동까지** 연결한다.
4. 검색 조건과 이메일을 저장해 비슷한 물건 알림을 제공한다. 이번 범위는 회원가입 없이 이메일 확인 링크로 활성화하며, 등록 다음날부터 7일간 데이터 갱신 후 새 유사 물품이 있을 때만 알리고 마지막 날에는 종료·연장 안내를 보낸다(4.2).

### 2.2 비목표 (Non-Goals)

1. **분실물 신고 등록 및 습득자–분실자 직접 매칭.** 우리는 공공 습득물 DB의 *탐색*만 한다.
2. **수령 예약·본인 인증·택배 발송 등 실제 반환 절차.** 기관 방문으로 연결하고 끝낸다.
3. ~~6개 서비스 카테고리 밖의 습득물.~~ 2026-11-17 결정으로 비목표에서 뺐다. 두 API의 습득물을 분류와 상관없이 모두 수집한다(3.1-1, 4.5). 번호는 기존 참조를 위해 유지한다.
4. **자체 모바일 앱.** 모바일 웹으로 대응.
5. ~~카테고리 확장(6개 → 추가. 수집·매핑 테이블 확장)~~ 2026-11-20 전체 물품 확대로 대체했다(4.5 카테고리 분류).

### 2.3 성공 지표

| 지표 | 목표치 | 비고 |
| --- | --- | --- |
| 탐색 성공률 — 정답이 DB에 있을 때 TOP-3 포함 | 95% | 평가셋은 2.4 검증 방법 참조 |
| 선택 반경 내 기관이 없는 경우 | 반경 확장 전환율 측정 | 1km 안에 기관이 0곳이면 1→1.5→2km 순서로 최대 2km까지 자동 확장하고 안내한다. 물품 검색 결과가 없다는 이유로 자동 확장하지는 않는다. 각 단계에서 기관이 있으면 자동 확장을 멈춘다(2026-11-09 결정, 4.5) |
| 보관기관 매칭률 (`location_match_status = 'matched'`) | 99% | `ingestion_runs`로 측정 |

기준선(측정 날짜)은 두지 않는다 (2026-09-27 결정).

### 2.4 가설 및 임팩트

**핵심 가설** — 분실자가 실패하는 이유는 *데이터가 없어서*가 아니라 (a) 검색어가 등록명과 맞지 않고 (b) 분실위치를 기준으로 직관적인 탐색이 안된다. 동일한 공공 DB 위에 AI 매칭과 반경 1km 지도를 얹으면 탐색 성공률이 유의하게 오른다.

**검증 방법 (Q2)** — 서울역 반경 5km 습득물 약 41,000건에서 타깃 20건을 선정하고, 타깃마다 "그 물건을 잃어버린 사람이 썼을 법한 검색어" 5개를 작성해(총 100개 질의) 질의–정답 쌍 평가셋을 만든 뒤 TOP-3 포함률을 측정한다.

### 2.5 가드레일 지표

1. **응답 속도** — `/api/found-items` p95 **1.5초** (2026-09-27 결정). 위치 검색, 물품 검색 모두 1.5초. 함수 `maxDuration` 300초는 동기화용이며 조회는 즉시 응답해야 한다. (데이터 최신화 동기화 시간임)
2. **오탐 유입** — 후보 규칙과 혼합 점수를 변경할 때 무관한 물품이 상위에 오르지 않을 것.

## 3. 범위

### 3.1 포함 범위 (In Scope) — 현재 구현과 개편 목표

2026-11-08: 사진·상세 창은 main에 반영됐다. 새 시각 디자인·번호 페이지·유사도순 정렬·알림·수령 안내 흐름은 아래 목표 사양이며 아직 구현 완료로 간주하지 않는다. 현재 코드와의 차이는 `AGENTS.md` 9장에 기록한다.

1. 두 습득물 API의 습득물 전체를 상위분류 21개로 분류해 하루 두 번 Supabase에 **멱등 upsert**하는 수집 파이프라인 (Vercel Cron, KST 09시대·21시대). 2026-11-20 이전에는 6개 카테고리만 선별했다(4.5).
2. 출처별 보존기간(연계기관 6개월 / 경찰관서 6개월) 자동 정리 — **동기화가 완전히 성공한 출처만** 삭제 수행
3. 카카오맵 장소명·주소 검색 → 좌표 변환 → 반경을 지도에 표시 (기본 1km, 기관 0곳일 때 최대 2km 자동 확장, 검색 후 1.5·2km 수동 확장 — 4.2·4.5 참조)
4. 전국 보관기관 지도: 연계기관 핀 + 경찰관서(노란) 핀, 줌 레벨별 클러스터/개별 전환, **핀 배지에 실제 보관 물품 수** 표시
5. 선택한 반경 내 기관들의 습득물 전체 목록 조회, 개별 기관 핀 클릭 시 해당 기관만 재조회, "선택 반경 전체"로 복귀
6. 물품명·원분류명·색상·설명 대상 **동의어·BM25·BGE-M3 혼합 검색** (검색 후 유사도 높은 순으로 정렬하되 점수·%·임시값은 화면에 표시하지 않음 — 4.5)
7. 서버 전용 키 격리(카카오 REST 키·Supabase secret 키 브라우저 미전달), 전 테이블 RLS + `service_role` 전용 권한, CSP·보안 헤더
8. 동기화 감사 로그(`ingestion_runs`)와 출처별 중복 실행 차단
9. 습득물 사진과 상세 창 — 2026-11-08 main 반영. `image_url` 원본, 지연 로딩, 고정 영역, 사진 없음·실패 대체와 기관 ID 기반 연락처 연결을 사용한다(4.3-C).

### 3.2 후속 구현 및 제외 범위

1. **이미지 기반 검색** — `vector` 확장은 준비됐으나 임베딩 컬럼·파이프라인은 미구현이다. 효과 검증 후 포함 여부를 정한다(Q4). 목록 사진 표시와는 별개다. DB에 사진이 없는 물품을 사용자 첨부 사진으로 찾는 성능도 함께 검증한다. 기존 사진 비율 표본이나 평가셋 수치는 이번 UI 변경으로 재측정한 값이 아니다.
2. **디자인 개편과 수령 안내** — 기존 사진·상세 기능을 재사용해 새 카드·페이지·상세/수령 안내 흐름을 적용한다. 아직 코드 반영 전이다.
3. **비슷한 물건 알림** — 예약 저장·이메일 확인·갱신 후 비교/발송·종료/연장 및 입력 화면은 후속 구현 대상이다. 이번 범위에 회원가입은 포함하지 않는다.
4. **모바일 개편** — 이번 디자인 작업은 데스크톱 우선이다. 현재 모바일 반응형과 상세 하단 시트는 유지하고, 전용 화면 재설계는 후속으로 둔다.

### 3.3 가정 및 제약사항

- **콘텐츠:** 습득물 제목·설명은 기관 담당자 자유 기재이며 품질이 고르지 않다. 정규화·동의어와 혼합 검색으로 흡수하되 **원문은 변형하지 않는다**.
- **법적:** 경찰청 공공데이터 이용약관 및 카카오 API 서비스 약관 준수.
- **개인정보 (2026-11-20 변경, Q5):** "경찰청이 마스킹한 뒤 제공한다"는 기존 가정은 틀렸다 — 운영 DB 집계에서 물품명에 카드번호·이름·전화번호·주민번호 형식이 원문 그대로 있었다(`docs/measurements.md`). 전체 물품 확대로 증명서·서류·유가증권·현금 분류도 들어온다. 그래서 서비스가 직접 가린다.
    - **저장은 원문 그대로, 밖으로 나가는 사본만 가린다.** `item_name`·`description`·`raw_payload`는 바꾸지 않는다(원문 보존). 가리는 곳은 `/api/found-items` 응답, 대화 검색의 브라우저·LLM 전달값, 알림 메일, 해외 임베딩 API로 보내는 입력, 정규화 전용 칸 `normalized_search_text`다.
    - **번호(모든 분류):** 주민·외국인등록번호는 전부, 카드번호(13~19자리)는 앞 4자리와 뒤 4자리만 남기고 가운데를 가리며(2026-11-20 사용자 결정: 앞 4자리는 발급사 구분용으로 본인 확인에 쓰이고 PCI DSS 표시 범위 안), 휴대폰(01X)은 가운데를 가린다.
    - **이름:** 모든 분류에서 `○○○ 명의`, `성명:`·`이름:`·`소유자:` 뒤 이름을 `홍*동` 형식으로 가린다(본인·법인·회사·타인 명의 제외). 고위험 분류(카드·지갑·증명서·서류·유가증권·현금, `prdtClNm` 상위분류 **정확 일치**)는 괄호 속 3자 한글(두 글자 성이면 4자)도 흔한 성씨로 시작하고 색상·카드사·브랜드·물품·상태 사전에 없으면 가린다. 2자 괄호 단어는 가리지 않는다(2026-11-20 운영 dry-run에서 괄호 매치의 약 59%가 색상·상태·물품 단어였다 — docs/measurements.md). 명의·성명 문맥 규칙은 2~4자를 그대로 가린다.
    - **검색어:** 카드·주민·전화번호 형태의 검색어는 지도 검색·대화 검색·알림 예약 모두에서 거절하고 "카드사·색상·물품 종류로 찾아 달라"고 안내한다. 번호가 든 대화는 LLM에 보내지 않는다.
    - **아직 남은 것:** 검색 문서(BM25 `search_text`)는 원문이라 같은 기관 범위 안에서 이름으로 역검색할 수 있다. 고위험 분류 사진, 처리방침 페이지 등도 후속이다(`docs/backlog.md` 8장).
- **기술적:**
    - 데이터 신선도는 최대 24시간 지연(일 1회 크론, 주기 유지 — Q6). Vercel Hobby는 지정 시간대 내에서 실행이 지연될 수 있어 24시간 이내로 단정하지 않는다. 크론 실패 시 이메일 알림을 보낸다 (담당 권희준 — 2026-11-05 변경, 미구현).
    - 습득물 검색어 30자 상한 → 넘기면 경고 알림 발생.
    - **보관기관 매칭 실패(unmatched/ambiguous) 건은 `storage_location_id`가 NULL이라 지도·검색에서 전혀 보이지 않는다.**

        → API출력 결과와 데이터베이스 내 기관 이름이 다른 경우 혹은 존재하지 않는 경우 가끔 있다. 이거 해결해야함

    - `/api/institutions`는 CDN 5분 캐시, `/api/found-items`는 무캐시.
- **예산/리소스:** Vercel Hobby + Supabase 무료 티어 가정 → 필요시 유료구매 가능

## 4. 솔루션 개요

### 4.1 접근 방식

**"물품명으로 찾기"가 아니라, "잃어버린 장소로 좁히고 그 안에서는 대충 적어도 찾아지게"**

공간을 1차 필터로 쓴다. → 검색으로 2차필터

**기존 대안 대비 차별점**

| 기존 대안 | 부족한 점 | 우리의 해결 방식 |
| --- | --- | --- |
| 경찰민원24 (경찰청 유실물 통합포털) | 분류·지역 드롭다운 중심, 정확한 용어 요구, 결과가 지도와 분리 | 장소 검색 → 반경 1km 지도 → 그 안에 실제 보관 중인 물품만 좁혀 제시 |
| 각 기관 개별 유실물센터 페이지 | 기관마다 흩어져 있고 경찰 습득물과 합쳐 볼 수 없음 | 연계기관 + 경찰관서를 한 지도·한 목록으로 통합 |
| 지역 커뮤니티·분실물 카페 | 비공식·비구조적, 실제 보관소와 연결 안 됨 | 공공 원천 데이터만 사용, 기관 위치로 직접 연결 |
| 단순 키워드 LIKE 검색 | 표현 차이에 즉시 0건 | 다중 필드 가중 퍼지 매칭(편집거리 + n-gram + 토큰 커버리지) |
| 파인딩올 | uiux불편(서버 응답 속도), 지연 문제, 검색 성능 문제, 습득물보관장소와 지도에서 연결이 안됨 | 장소 검색 → 반경 1km 지도 → 그 안에 실제 보관 중인 물품만 좁혀 제시,<br>데이터 동기화 6개월 제한 |

**핵심 차별점**

1. **공간 우선 탐색** — 반경 1km로 후보를 수백 건 수준까지 줄인 뒤에 검색하므로, 느슨한 검색어를 써도 오탐이 감당 가능한 범위에 머문다.
2. **틀리게 써도 찾아지는 검색** — 물품명 1.0 / 원분류 0.9 / 색상 0.82 / 설명·정규화 텍스트 0.72 가중치에 부분일치·부분문자열·편집거리·자카드·접두 보너스를 결합한다. 2026-11-08 최종 결정: 점수는 정렬·내부 평가에만 사용하고 사용자 화면에는 숫자나 %를 표시하지 않는다. 검색 후 유사도 높은 순으로만 보여주며 % 환산과 임시 점수 표시는 하지 않는다(3.1-6, 4.5).
3. **(기관별 실재 재고 표시** — 지도 핀 배지에 그 기관이 *지금* 보관 중인 물품 수를 띄워, "갈 만한 곳"을 즉시 판별시킨다.)

2026-11-08 사용자 결정 — 목록에서 물품을 선택하면 데스크톱은 중앙 모달, 모바일(820px 이하)은 하단 시트로 상세정보를 표시한다. 사진, 물품명, 분류, 색상, 원문 설명, 등록일, 출처와 보관기관명·주소·전화번호를 표시한다. 전화번호는 전화 연결 링크로 제공하고 누락 정보는 “정보 없음”으로 표시한다. 사진이 없거나 기본 그림이면 사진 없음, 로딩 실패면 대체 표시한다. 현재 API에 없는 보관기한은 표시하지 않는다. 닫기 버튼·Esc·창 바깥 클릭·브라우저 뒤로가기로 상세만 닫으며 검색 조건과 목록 스크롤을 유지한다.

2026-11-09 로컬 연결 — 상세 창은 노션식 안내 문서처럼 상단 사진·속성과 하단 원문 설명·보관 위치로 구성하고 배경을 흐리게 한다. 목록에서는 설명을 숨긴다. “찾으시는 물건이 맞나요?”에 “예, 수령 방법 보기”를 선택하면 보관기관 사전 연락 → 신분증/물품 특징 준비 → 기관 확인 후 수령 순서의 안내 창을 연다. 마지막 버튼은 “확인했어요”이며 안내를 닫고 기존 검색 목록으로 돌아간다. “물품 정보 다시 보기”로 상세 화면에 복귀할 수도 있다. 이 선택은 소유 확인·반환 예약이 아니다. 기관 주소/연락처는 검증된 기관 ID로 연결하고 확인되지 않은 수령 장소나 보관기한을 만들지 않는다.

**E. 비슷한 물건 알림 (2026-11-08 결정)**

- 검색 결과 아래에서 반경 확장 또는 비슷한 물건 알림 받기를 선택한다. 알림을 선택하면 같은 검색 상태를 전달하고 상단 비슷한 물건 알림 탭을 선택 표시한다.
- 장소·제출 물품명·7일 기간은 고정하고 이메일을 입력한다. 알림 조건 수정은 같은 창에서 1·1.5·2km 반경만 변경하며 검색 결과에는 반영하지 않는다. 장소나 물품을 바꾸려면 검색 화면에서 다시 검색한다. 직접 탭 진입 시 조건이 없으면 먼저 장소·물품 검색을 안내한다.
- 이메일 확인 전에는 알림을 보내지 않는다. **기준 일정은 등록일을 D일로 할 때 다음날 D+1부터 D+7까지의 한국시간 달력상 7일**이다. 이메일 확인이 시작일보다 늦어도 일정은 등록일 기준으로 두고 미루지 않는다. 확인 링크는 24시간 유효하며 지나면 다시 신청한다. 연장은 한 번에 7일, 최대 3회다(2026-11-15 담당 결정).
- 일일 발송 시각을 오전 9시 정각으로 약속하지 않는다. 데이터 갱신 후 새 유사 물품이 있는 날에만 물품 안내를 보내며, 없는 날은 건너뛴다. 결과 안내 횟수는 7회로 고정하지 않는다.
- 마지막 날에는 결과 유무와 관계없이 “이번 알림은 종료되며 이후에는 메일이 발송되지 않아요. 계속 받고 싶다면 연장해 주세요.”라는 종료·연장 안내를 보낸다. 연장하지 않으면 종료한다. 마지막 날 결과는 종료 안내 한 통에 합쳐 보내고, 연장은 그날 자정 전까지 받는다(2026-11-15 담당 결정).
- 예약 이후 새로 등록된 물품만 비교하고 같은 물품을 다시 보내지 않는다. 취소한 예약에 대한 후속 발송은 중지한다. 해지·연장 접근은 이메일 링크로 제공한다.
- "유사"는 같은 검색어로 같은 반경을 검색했을 때 결과에 나오는 새 물품이다(4.5의 키워드 단계와 같은 판정, 2026-11-15 담당 결정). 단, 검색어에 동의어 사전의 색·브랜드·특징(이어폰 방향·맥세이프만) 단어가 있으면 그 말이 맞는 물품만 알린다 — 같은 분류(색끼리 등)는 하나만 맞으면 되고 분류끼리는 모두 맞아야 하며, 색을 알 수 없는 물품은 넣는다. 이 점에서 알림은 검색 화면보다 좁다(2026-11-15 사용자 결정). 알림은 화면에서 고른 장소(최대 3곳)를 그대로 저장하고, 장소들 각각의 반경 안 기관을 합쳐 비교한다(2026-11-15 사용자 결정 — 같은 날의 장소 1곳 결정을 바꿈).
- 예약/메일 백엔드는 `feat-alert-scheduler` 브랜치에 구현했고 운영 적용·화면 연결 전이다. 수집·알림 실패 분리, 실패 재시도, 링크 세부 계약은 `docs/alert-scheduler/`(설계 15장·프런트 핸드오프)에 있다.

### 4.4 목업 및 프로토타입

목표 디자인은 전체 화면 지도 위에 왼쪽 검색·결과 패널을 띄우는 데스크톱 UI다. 상단은 `RETRIEVER` 로고 오른쪽에 “물건 찾기”, “비슷한 물건 알림”, 오른쪽 끝에 “이용 안내”를 배치한다. 비슷한 물건 알림 앞에는 이모지를 붙이지 않는다. 파란색·부드러운 회색 텍스트·둥근 개별 카드를 사용한다.

- 장소 카드: 이름·주소·카테고리 두 번째 단계 태그. 전화번호는 초기 장소 카드에서 생략하고 보관기관 연락처는 물품 상세에서 제공한다. `#`은 붙이지 않는다.
- 물품 카드: 사진·카테고리·색상(값이 있을 때만)·원문 명칭·보관장소·등록일. 검색 후에는 카드 구성을 유지하고 유사도 높은 순으로만 정렬한다. 점수 배지는 표시하지 않는다. 설명은 상세로 옮긴다.
- 장소 결과는 같은 높이의 카드 5곳씩 고정하고(마지막 페이지만 남은 개수), 카드 영역 스크롤 대신 하단 번호 페이지를 사용한다. 지도에는 현재 페이지 후보만 같은 번호로 표시한다. 물품 목록은 페이지당 4개로 고정하고 목록 스크롤 없이 번호로 이동한다. 기본 목록의 50건 커서는 필요한 페이지에 도달했을 때만 이어 받고, 경계의 일부 물품도 빠짐없이 다음 묶음과 함께 표시한다. 페이지/반경/알림 행동 영역을 목록과 분리해 겹침을 막는다. 서버가 다음 결과를 전달하는 계약은 검색 담당자와 확정한다.
- 비슷한 물건 알림은 배경을 흐리게 하고 검색 패널보다 넓은 흰색 둥근 창을 연다. 조건 요약은 왼쪽, 이메일 입력은 오른쪽이다.
- 이용안내는 서비스 소개와 두 탭의 사용법을 담은 한 페이지다. 기관 사전 연락, 분류와 상관없이 모든 습득물을 찾을 수 있다는 점과 자주 찾는 물품 예시를 안내한다(2026-11-20, 전 6개 카테고리 안내 대체). 하단에서 서비스 개선 설문 참여를 강조하고 상단 ‘의견 보내기’와 같은 설문으로 연결한다.
- Make는 시각/동작 참고용이다. 실제 카카오맵·검색 API·이메일 연결은 서비스 구현에서 수행한다.
- 상세 배치·반응형·가독성 수치는 `docs/design-system.md`, 동작은 `docs/ui-patterns.md`를 따른다.

### 4.5 핵심 로직 및 예외 케이스

**핵심 로직**

**2026-11-08 상세 조회 예산 조정 및 실패 관측** — 사용자 결정으로 상세 요청 상한은 재시도를 포함한 400회, 상세 단계 예산은 60초다. 동시 4개·요청별 3초·실행 시작 후 180초 마감과 전체 함수 300초는 유지한다. HTTP 429도 네트워크·5xx와 같이 예산 안에서 한 번 재시도한다. API 본문 오류·식별 오류는 재시도하지 않는다. HTTP/API의 숫자 코드, timeout·DNS·TLS·식별·파싱 오류 등 안전한 분류만 `metadata.detail_lookup.failure_attempts_by_reason`에 시도별로 기록한다. 비밀값·전체 URL·응답 본문은 저장하지 않는다. 이 집계는 재시도로 복구된 시도의 오류도 포함하므로 최종 실패 물품 건수와 다르다.

**2026-11-07 일일 동기화 검증 및 시간 예산** — 상세 조회 행과 일반 행 모두 동일한 `detail_status` 키를 포함해 일괄 저장한다. 유일하게 확정되는 검증 별칭/기관 이름에는 상세 API를 호출하지 않는다. 동명 기관의 일시적 네트워크·5xx 실패만 한 번 재시도하며, 재시도도 동시 4개·각 요청 3초·합계 400회·단계 60초 및 실행 시작 후 180초 제한 안에서 처리한다. 영구적인 응답/식별 오류는 재시도하지 않고, 최종 실패·시간 부족·규칙 없음은 미매칭으로 남긴다. 증분 동기화의 목록 수집은 실행 시작 후 150초, 일반 DB 작업은 270초, 감사 로그는 295초까지로 요청과 재시도에 같은 예산을 적용한다. 경찰 목록 API의 재시도는 수집기 한 계층에서만 맡는다. 만료 정리는 기존 출처·등록일 인덱스로 오래된 등록일부터 배치 조회하고, 정리할 시간이 부족하면 다음 실행으로 넘겨 `metadata.cleanup_deferred`에 기록한다. 실패한 출처의 삭제 금지와 6개월 KST 경계는 유지한다. 실제 Vercel 함수 상한은 `vercel.json`의 300초다. 이 설정은 외부 서비스 응답·플랫폼 장애가 없다는 보장이 아니다.

- **카테고리 분류** (2026-11-17 결정, 2026-11-20 반영) — 분류 때문에 물품을 버리지 않는다. `prdtClNm`("상위 > 하위")을 ① `category_mappings`의 정확한 상위+하위 매핑 → ② 상위분류가 `item_categories.name`(경찰청 상위분류 21개)과 **정확히 일치** → ③ 둘 다 없으면 `기타물품` 순으로 분류한다. 비교는 NFKC·casefold 후 글자·숫자만 남긴 값으로 한다. 부분일치는 오분류를 막기 위해 계속 쓰지 않는다. ③으로 저장한 건수는 `ingestion_runs.metadata.category_fallback_count`에 남기고, 0이 아니면 새 상위분류를 마이그레이션으로 추가한다. 분류명이 빈 행은 DB 제약 때문에 `invalid_count`로 센다. 원문 분류명은 `raw_category_name`에 그대로 둔다. 2026-11-20 이전에는 6개 카테고리(4.1)의 허용 목록과 정확히 일치하는 물품만 수집했다.
- **과거 구간 백필** (2026-11-20) — 전체 물품 확대 이전 기간은 수동 CLI(`sync-found-items --backfill-from`)로 1회 채운다. 출처별 7일 단위 실행으로 나누고, DB에 없는 물품만 추가해 기존 물품의 위치·상세정보를 다시 쓰지 않는다. 상세 조회는 실행마다 60초·400회 예산으로 새 물품에만 한다. 크론 시간대(KST 09·11·21·23시대와 직전 20분)에는 시작하지 않고, 실패하면 멈춰 재시작 지점을 남긴다. 감사 로그 `business_date`는 실행한 날로 기록해 임베딩 회차 판정을 바꾸지 않는다.
- **데이터 추가분 수집** — 한국시간 오늘까지 수집한다. 출처별 마지막 등록일과 어제 중 이른 날짜를 다시 포함해 재조회하고 보존기간 시작일을 하한으로 둔다. 오전 09시대·오후 21시대의 별도 크론을 각각 하루 한 번 실행하며 매번 전체 구간을 재수집하지 않는다. (2026-11-14 사용자 결정)
- **보관기관 해석** — 원문 보관장소명을 ① 같은 출처의 활성 기관에 연결된 검증된 수동 예외 별칭 → ② 정규화명/기관명 전체 정확 일치 → ③ 전체 정확 일치가 없을 때만 괄호 제거 기본명 정확 일치 → ④ 앞 단계 후보가 없을 때만 접미사 포함 관계 순으로 매칭한다. 일반적인 이름 정규화는 별칭으로 중복 저장하지 않는다. 후보가 1개면 `matched`, 0개면 `unmatched`로 기존 처리한다. 여러 후보인 이번 수집 물품만 상세 API에서 현재 보관장소·기관 코드를 조회해 아래의 단일 매핑 규칙을 적용한다. 기관 색인과 매핑 사전은 실행마다 한 번 만들고 재사용한다. (2026-11-07 사용자 결정)
- **보존기간 정리** — 오전 실행에서 API 조회와 모든 upsert가 성공한 출처에 한해서만 보존기간 밖 데이터를 삭제한다. 오후 실행은 삭제하지 않으며, 오전 시간 예산 때문에 남은 만료분도 다음 오전에 정리한다. 수동 복구 명령의 성공 후 정리는 유지한다.

## 5. 비기능 요구사항

2026-11-20 대화형 검색 복구 결정: 재시도는 동일 요청 ID·버전으로 수행하고 실패·취소의 중간 대화 상태는 반영하지 않는다. 응답 유실은 최신 완료 결과 재사용으로 복구한다. 세션은 기존 Supabase에 서버 전용으로 저장하며 유휴 30분에 만료한다. 다른 인스턴스에서도 대화·취소를 이어가고, 로그는 원문·개인정보·비밀값 없이 실패 단계·예외 종류·외부 상태 코드·소요 시간·최종 상태·추적 ID를 남긴다. 세부 계약·저장 최소 항목·만료 삭제·배포 및 복구 순서는 [대화형 검색 문서](agent-search.md#실패-복구와-공용-세션-2026-11-20)를 따른다. 운영 DB 적용·앱 배포·PR 병합은 별도 승인 후 진행한다. 이 결정은 운영 반영 완료를 뜻하지 않는다.


**2026-11-11 최종 경로:** 후보 RPC는 미리 저장한 종류 마스크와 작은 검색 필드만 사용한다. (2026-11-21: 종류 마스크 필터는 제거했다. 최신 동작은 4.5의 "검색어 처리와 키워드 후보"를 따른다.)
반복 문자열 정규화·전체 상세 조립·전체 기관 물품 수 집계를 제거하고 gzip을 사용한다.
키워드 2초·전체 5초 목표는 최대 약 3만 건 대표 범위에서 실측하며 전체 대기 상한은 4.6초다.
질의 임베딩 예산은 4.0초이며 물품 응답 무캐시/질의 벡터 128개·1시간 재사용을 유지한다.
현재 경로와 다른 아래 문단은 이전 실험 이력이다. 최신 동작은 위 순위와 README를 따른다.

**이전 2026-11-11 추가 사용자 요청:** 의미 검색 시간 초과를 해결하고 정상 응답 5초 이내를 목표로
실측한다. 물품별 고비용 퍼지 보조는 실험 후 기본 off로 전환하고 질의 측 작은 단어 사전의
유일한 1-edit 보정과 BM25 bigram을 유지한다. 종류 충돌 필터는 의미 결과에도 적용하되
이름·분류가 불완전하면 설명의 종류 근거를 인정한다. 종류 근거 없는 의미 단독 결과는
cosine 0.60 이상을 받는다. 검색 결과도 50건 커서 페이징으로 전체 수와 나머지 결과를 보존한다.
API 전체 검색 대기는 4.6초 상한이며 상한 초과는 명확한 504 응답이다. 외부 장애에서 정상
검색 성공을 보장하는 값이 아니며, 5초 정상 성공은 대표 범위의 실제 요청으로 별도 확인한다.
질의 벡터의 128개/1시간 서버 메모리 재사용은 허용하고, 물품 응답 무캐시는 유지한다.
아래 이전 2026-11-11 첫 적용분의 전량 후보/퍼지/5초 의미 전용 예산은 기준선으로 보존한다.

2026-11-11 김성현이 승인한 검색 개선 제안의 첫 적용분: 종류가 명시된 질의는
검토된 종류 표현이 이름·분류에 있는 키워드 후보를 받으며, 의미 검색 후보는 독립적으로 유지한다.
고비용 퍼지는 BM25 상위 100건과 이름 유사도 상위 100건의 합집합에 제한하고
이름 128자·분류 64자만 비교한다. 색상·브랜드의 검토된 작은 동의어는 검색 시 통일한다.
종류가 없는 여러 단어 질의는 이름·분류 단어 커버리지 0.6 이상 또는 퍼지 0.8 이상을 요구한다.
검색 필드 조회와 결과 상세 조회를 분리하되 반환 결과 전체·건수·페이지 계약은 유지한다.
의미 검색 전체 예산은 임시로 5초이며 초과·장애·작업 혼잡 시 키워드 결과와 대체 안내를 제공한다.
이는 품질 평가를 마친 최종 설정이 아니다. 합산 가중치·코사인 임계값은 기존 초안을 유지한다.

### DB 변경 배포와 적용 이력 (2026-11-16, PR #53)

- `supabase/migrations/`의 SQL과 운영 적용 이력의 버전·이름·본문을 일치시킨다. 이미 적용된 SQL은 보존하고 이후 변경·복구는 새 마이그레이션으로 추가한다. 운영에 먼저 수동 적용한 경우에도 동일 SQL과 실제 적용 버전을 저장소에 반영해 중복·누락 적용을 막는다.
- GitHub 연동은 저장소 `rlashyun/sangsang`, Working directory `.`, Production branch `main`, Automatic branching **끔**을 기준으로 한다. PR #53을 main에 병합하고 최신 운영 이력과 다시 대조한 뒤 사용자가 Deploy to production을 활성화한다. 이 문서 갱신은 연동 설정 변경이나 운영 DB 적용을 수행했다는 뜻이 아니다.
- 이후 DB 변경은 PR 검증·main 병합 후 미적용 마이그레이션을 배포하고 Supabase 적용 결과를 확인한다. Vercel 앱 배포와 DB 적용은 별도이므로 앱이 새 SQL을 요구하면 기존 앱과의 호환성·적용 순서를 PR에 명시한다. 적용 실패는 성공으로 처리하지 않는다.
- PR #53에서 복원한 과거 SQL은 운영에서 이미 적용한 이력이며 재실행하지 않는다. 이력 정렬은 현재 전체 스키마 일치나 빈 DB에서의 전체 재생성, 자동 배포 성공을 보장하지 않는다. 새 DB 전체 재생성 검증 전에는 Automatic branching을 켜지 않는다. Preview의 운영 DB 연결 제한과 기존 명시 승인 예외는 위 보안 요구사항을 유지한다.
- `maintenance/`·`repairs/`·`rollbacks/`는 수동 작업 자료다. 자동 배포 대상으로 옮기거나 통째로 실행하지 않는다. 설정 절차는 [Supabase 변경 파일 안내](../supabase/README.md), 대조 결과와 검증 한계는 [실측 기록](measurements.md)을 따른다. 연동의 미적용 SQL 실행 방식과 설정 항목은 [Supabase 공식 문서](https://supabase.com/docs/guides/deployment/branching/github-integration)를 근거로 한다.

## 10. 부록

**데모 시나리오**

1. "강남역"을 검색하고 후보 카드를 선택한다 → 기본 1km 범위와 기관을 표시한다. 기관이 0곳일 때만 1→1.5→2km 순서로 최대 2km까지 자동 확장한다.
2. 현재 범위 안의 연계기관·경찰관서 핀이 뜨고, 각 핀 배지에 **지금 보관 중인 물품 수**가 보인다.
3. 좌측에 현재 반경 기관들이 보관 중인 습득물 목록이 자동으로 표시된다.
4. "검정 지갑"을 입력한다 → 등록명이 "지갑(남성용)"이어도 색상·설명 필드 매칭으로 결과가 나온다.
5. 특정 경찰관서 핀을 클릭한다 → 그 기관 물품만으로 목록이 바뀐다. "선택 반경 전체" 버튼으로 복귀한다.
6. 카드에서 상세를 열고 보관기관·원문 설명을 확인한다. 수령 안내에 따라 방문 전 기관에 연락한다.
7. 찾는 물건이 없으면 검색어를 유지해 1.5km 또는 2km로 넓히거나 비슷한 물건 알림을 신청한다. 결과 하단의 돌아가기 버튼으로 한 단계씩 줄일 수 있다. 확장 결과에서 직전 반경 안의 보관기관 물품에는 ‘1km 이내’ 또는 ‘1.5km 이내’ 표식을 붙인다.
8. 알림은 다음날부터 7일간 유사 물품이 있는 날에만 보내고 마지막 날은 종료·연장을 안내한다.

**용어**

- **연계기관** — 경찰청 유실물 시스템에 연계된 지하철·공항·터미널 등의 기관
- **경찰관서** — 경찰서 및 지구대·파출소
- **matched / unmatched / ambiguous** — 습득물의 원문 보관장소명을 좌표가 있는 기관 레코드에 연결한 결과 상태

**기술 스택 (변경 가능)**

- 프런트엔드: React + TypeScript + Vite + React Router
- 지도: 카카오맵 JavaScript SDK
- 백엔드: FastAPI 기반 Vercel Functions
- 프런트엔드 제공 방식: Vite 빌드 결과물을 FastAPI가 정적 파일로 제공
- 데이터: Supabase Postgres + PostGIS (`vector` 확장 활성, 현재 미사용)
- 스케줄: Vercel Cron 7개, 각 하루 1회. 수집 4개는 UTC 00:00/12:00 = KST 09시대/21시대, 임베딩 복구 2개는 UTC 02:00/14:00 = KST 11시대/23시대, 알림 메일 발송 1개는 UTC 02:00 = KST 11시대(③ 스케줄러)
- 프런트엔드 구조: `frontend/src/{api, components, lib}`
- 백엔드 구조: `src/retriever_lost_found/{web, integrations, ingestion, search}`
- 배포용 정적 파일: `src/retriever_lost_found/web/static`
