# 리트리버(Retriever) PRD

> 한 줄 요약: 경찰청 습득물 데이터를 매일 모아, 잃어버린 지점 반경 1km에서 시작해 1.5·2km까지 넓히며 보관기관과 습득물을 지도에서 탐색하는 웹 서비스.

---

## 1. 배경 및 문제 정의

### 1.1 배경

경찰청은 습득물 정보를 공공데이터포털 API로 공개한다. 우리는 그중 두 개를 사용한다 —
**유실물 연계기관 습득물 API**(지하철·공항·터미널 등)와 **경찰관서 습득물 API**(경찰서·지구대·파출소).

데이터는 이미 공개되어 있다. 문제는 **찾는 방법**이다. 공식 창구인 경찰민원24는 물품분류·지역·기간 드롭다운 검색이고, 습득물 제목은 기관 담당자가 자유 기재한다("검정색 지갑", "지갑 1개", "지갑(남성용)"). 그리고 습득물은 결국 **실물로 어딘가에 보관되어 있어서**, 탐색의 끝은 언제나 "그래서 어디로 가야 하나"인데 기존 검색은 기관 이름 텍스트만 돌려준다.

### 1.2 문제 정의

**고객은 누구인가**

최근 며칠 안에 대중교통·역사·상업시설 주변에서 물건(지갑·휴대폰·가방·카드·무선이어폰·모자)을
잃어버렸고, 정확한 물품명은 몰라도 **잃어버린 대략적인 장소는 기억하는** 사람.

**고객이 겪는 문제**

> 나는 **어제 강남역 근처에서 지갑을 잃어버린 사람**이다. 나는 **내 지갑이 어느 보관소에 들어와 있는지 확인하고 찾으러 가는 것**을 하려 한다. 그러나 **검색이 정확한 분류·용어를 요구하고 결과를 찾아도 그 기관이 내가 잃어버린 곳에서 가까운지 알 수 없기** 때문에 **검색을 몇 번 헛돌다 포기하는 일**이 발생한다.

| 탐색이 어려운 이유 | 리트리버의 해결 |
| --- | --- |
| 정보가 여러 기관/출처에 흩어져 있음 | **습득물 데이터 통합** |
| 어디에서 잃어버렸는지 불확실함 | **방문 장소 기반 다중 탐색** |
| 습득물이 너무 많음 | **위치 기반 탐색 범위 축소** |
| 같은 물건도 표현이 다름 | **물품정보 표준화** |
| 공공데이터 설명이 부족함 | **Vision AI로 사진 정보 보강** |
| 비슷한 물건이 많음 | **유사도 기반 Ranking** |
| 분실자가 물건 사진을 가지고 있음 | **이미지 임베딩 기반 유사 검색** |

**검증 예정 (Q1)** — 위 서술은 팀 관찰과 기존 서비스 UI 분석에 근거한 가설이다. 2026-10-02 실사용자 인터뷰로 다음 두 가설을 검증한다 — ① 사용자는 지도 기반 UI를 더 편리하게 느낀다 ② 검색어 관련 기능 개선이 필요하다.

## 2. 목표와 성공 지표

### 2.1 목표 (Goals)

1. 분실자가 기억나는 표현이나 오타가 포함된 검색어로도 데이터베이스에 존재하는 자기 분실물을 정확하게 탐색한다. 현재 MVP는 동의어·BM25·BGE-M3 혼합 검색을 사용하며, TOP-3 포함률 95%는 평가셋 구축 후 검증한다. (추후에 다른 검색 알고리즘을 사용할 예정이다.)
2. 분실 지점 **반경 1km의 보관기관(연계기관 + 경찰관서)을 한 지도에서** 보여주고, 필요하면 1.5·2km로 넓힌다. 1km 안에 기관이 0곳이면 1→1.5→2km 순서로 최대 2km까지 자동 확장한다(4.5).
3. 지도 기반 UI로 보관 기관 위치를 시각화하여 **실제 수령 행동까지** 연결한다.
4. 검색 조건과 이메일을 저장해 새 물건 알림을 제공한다. 이번 범위는 회원가입 없이 이메일 확인 링크로 활성화하며, 등록 다음날부터 7일간 데이터 갱신 후 새 유사 물품이 있을 때만 알리고 마지막 날에는 종료·연장 안내를 보낸다(4.2).

### 2.2 비목표 (Non-Goals)

1. **분실물 신고 등록 및 습득자–분실자 직접 매칭.** 우리는 공공 습득물 DB의 *탐색*만 한다.
2. **수령 예약·본인 인증·택배 발송 등 실제 반환 절차.** 기관 방문으로 연결하고 끝낸다.
3. **6개 서비스 카테고리 밖의 습득물.** 현재 수집 단계에서 제외된다.
4. **자체 모바일 앱.** 모바일 웹으로 대응.
5. 카테고리 확장(6개 → 추가. 수집·매핑 테이블 확장)

### 2.3 성공 지표

| 지표 | 목표치 | 비고 |
| --- | --- | --- |
| 탐색 성공률 — 정답이 DB에 있을 때 TOP-3 포함 | 95% | 평가셋은 2.4 검증 방법 참조 |
| 선택 반경 내 기관이 없는 경우 | 반경 확장 전환율 측정 | 1km 안에 기관이 0곳이면 1→1.5→2km 순서로 최대 2km까지 자동 확장하고 안내한다. 물품 검색 결과가 없다는 이유로 자동 확장하지는 않는다. 각 단계에서 기관이 있으면 자동 확장을 멈춘다(2026-11-09 결정, 4.5) |
| 보관기관 매칭률 (`location_match_status = 'matched'`) | 99% | `ingestion_runs`로 측정 |

기준선(측정 날짜)은 두지 않는다 (2026-09-27 결정).

### 2.4 가설 및 임팩트

**핵심 가설** — 분실자가 실패하는 이유는 *데이터가 없어서*가 아니라 (a) 검색어가 등록명과 맞지 않고 (b) 분실위치를 기준으로 직관적인 탐색이 안된다. 동일한 공공 DB 위에 AI 매칭과 반경 1km 지도를 얹으면 탐색 성공률이 유의하게 오른다.

**검증 방법 (Q2)** — 서울역 반경 5km 습득물 약 41,000건에서 타깃 20건을 선정하고, 타깃마다 "그 물건을 잃어버린 사람이 썼을 법한 검색어" 5개를 작성해(총 100개 질의) 질의–정답 쌍 평가셋을 만든 뒤 TOP-3 포함률을 측정한다.

### 2.5 가드레일 지표

1. **응답 속도** — `/api/found-items` p95 **1.5초** (2026-09-27 결정). 위치 검색, 물품 검색 모두 1.5초. 함수 `maxDuration` 300초는 동기화용이며 조회는 즉시 응답해야 한다. (데이터 최신화 동기화 시간임)
2. **오탐 유입** — 후보 규칙과 혼합 점수를 변경할 때 무관한 물품이 상위에 오르지 않을 것.

## 3. 범위

### 3.1 포함 범위 (In Scope) — 현재 구현과 개편 목표

2026-11-08: 사진·상세 창은 main에 반영됐다. 새 시각 디자인·번호 페이지·유사도순 정렬·알림·수령 안내 흐름은 아래 목표 사양이며 아직 구현 완료로 간주하지 않는다. 현재 코드와의 차이는 `AGENTS.md` 9장에 기록한다.

1. 두 습득물 API에서 6개 카테고리만 선별해 하루 두 번 Supabase에 **멱등 upsert**하는 수집 파이프라인 (Vercel Cron, KST 09시대·21시대)
2. 출처별 보존기간(연계기관 6개월 / 경찰관서 6개월) 자동 정리 — **동기화가 완전히 성공한 출처만** 삭제 수행
3. 카카오맵 장소명·주소 검색 → 좌표 변환 → 반경을 지도에 표시 (기본 1km, 기관 0곳일 때 최대 2km 자동 확장, 검색 후 1.5·2km 수동 확장 — 4.2·4.5 참조)
4. 전국 보관기관 지도: 연계기관 핀 + 경찰관서(노란) 핀, 줌 레벨별 클러스터/개별 전환, **핀 배지에 실제 보관 물품 수** 표시
5. 선택한 반경 내 기관들의 습득물 전체 목록 조회, 개별 기관 핀 클릭 시 해당 기관만 재조회, "선택 반경 전체"로 복귀
6. 물품명·원분류명·색상·설명 대상 **동의어·BM25·BGE-M3 혼합 검색** (검색 후 유사도 높은 순으로 정렬하되 점수·%·임시값은 화면에 표시하지 않음 — 4.5)
7. 서버 전용 키 격리(카카오 REST 키·Supabase secret 키 브라우저 미전달), 전 테이블 RLS + `service_role` 전용 권한, CSP·보안 헤더
8. 동기화 감사 로그(`ingestion_runs`)와 출처별 중복 실행 차단
9. 습득물 사진과 상세 창 — 2026-11-08 main 반영. `image_url` 원본, 지연 로딩, 고정 영역, 사진 없음·실패 대체와 기관 ID 기반 연락처 연결을 사용한다(4.3-C).

### 3.2 후속 구현 및 제외 범위

1. **이미지 기반 검색** — `vector` 확장은 준비됐으나 임베딩 컬럼·파이프라인은 미구현이다. 효과 검증 후 포함 여부를 정한다(Q4). 목록 사진 표시와는 별개다. DB에 사진이 없는 물품을 사용자 첨부 사진으로 찾는 성능도 함께 검증한다. 기존 사진 비율 표본이나 평가셋 수치는 이번 UI 변경으로 재측정한 값이 아니다.
2. **디자인 개편과 수령 안내** — 기존 사진·상세 기능을 재사용해 새 카드·페이지·상세/수령 안내 흐름을 적용한다. 아직 코드 반영 전이다.
3. **새 물건 알림** — 예약 저장·이메일 확인·갱신 후 비교/발송·종료/연장 및 입력 화면은 후속 구현 대상이다. 이번 범위에 회원가입은 포함하지 않는다.
4. **모바일 개편** — 이번 디자인 작업은 데스크톱 우선이다. 현재 모바일 반응형과 상세 하단 시트는 유지하고, 전용 화면 재설계는 후속으로 둔다.

### 3.3 가정 및 제약사항

- **콘텐츠:** 습득물 제목·설명은 기관 담당자 자유 기재이며 품질이 고르지 않다. 정규화·동의어와 혼합 검색으로 흡수하되 **원문은 변형하지 않는다**.
- **법적:** 경찰청 공공데이터 이용약관 및 카카오 API 서비스 약관 준수. 습득물 설명 내 개인정보(카드 명의자명 등)는 경찰청이 마스킹한 뒤 제공하므로 이 서비스에서 따로 다루지 않는다 (Q5).
- **기술적:**
    - 데이터 신선도는 최대 24시간 지연(일 1회 크론, 주기 유지 — Q6). Vercel Hobby는 지정 시간대 내에서 실행이 지연될 수 있어 24시간 이내로 단정하지 않는다. 크론 실패 시 이메일 알림을 보낸다 (담당 권희준 — 2026-11-05 변경, 미구현).
    - 습득물 검색어 30자 상한 → 넘기면 경고 알림 발생.
    - **보관기관 매칭 실패(unmatched/ambiguous) 건은 `storage_location_id`가 NULL이라 지도·검색에서 전혀 보이지 않는다.**

        → API출력 결과와 데이터베이스 내 기관 이름이 다른 경우 혹은 존재하지 않는 경우 가끔 있다. 이거 해결해야함

    - `/api/institutions`는 CDN 5분 캐시, `/api/found-items`는 무캐시.
- **예산/리소스:** Vercel Hobby + Supabase 무료 티어 가정 → 필요시 유료구매 가능

## 4. 솔루션 개요

### 4.1 접근 방식

**"물품명으로 찾기"가 아니라, "잃어버린 장소로 좁히고 그 안에서는 대충 적어도 찾아지게"**

공간을 1차 필터로 쓴다. → 검색으로 2차필터

**기존 대안 대비 차별점**

| 기존 대안 | 부족한 점 | 우리의 해결 방식 |
| --- | --- | --- |
| 경찰민원24 (경찰청 유실물 통합포털) | 분류·지역 드롭다운 중심, 정확한 용어 요구, 결과가 지도와 분리 | 장소 검색 → 반경 1km 지도 → 그 안에 실제 보관 중인 물품만 좁혀 제시 |
| 각 기관 개별 유실물센터 페이지 | 기관마다 흩어져 있고 경찰 습득물과 합쳐 볼 수 없음 | 연계기관 + 경찰관서를 한 지도·한 목록으로 통합 |
| 지역 커뮤니티·분실물 카페 | 비공식·비구조적, 실제 보관소와 연결 안 됨 | 공공 원천 데이터만 사용, 기관 위치로 직접 연결 |
| 단순 키워드 LIKE 검색 | 오타·표현 차이에 즉시 0건 | 다중 필드 가중 퍼지 매칭(편집거리 + n-gram + 토큰 커버리지) |
| 파인딩올 | uiux불편(서버 응답 속도), 지연 문제, 검색 성능 문제, 습득물보관장소와 지도에서 연결이 안됨 | 장소 검색 → 반경 1km 지도 → 그 안에 실제 보관 중인 물품만 좁혀 제시,<br>데이터 동기화 6개월 제한 |

**핵심 차별점**

1. **공간 우선 탐색** — 반경 1km로 후보를 수백 건 수준까지 줄인 뒤에 검색하므로, 느슨한 검색어를 써도 오탐이 감당 가능한 범위에 머문다.
2. **틀리게 써도 찾아지는 검색** — 물품명 1.0 / 원분류 0.9 / 색상 0.82 / 설명·정규화 텍스트 0.72 가중치에 부분일치·부분문자열·편집거리·자카드·접두 보너스를 결합한다. 2026-11-08 최종 결정: 점수는 정렬·내부 평가에만 사용하고 사용자 화면에는 숫자나 %를 표시하지 않는다. 검색 후 유사도 높은 순으로만 보여주며 % 환산과 임시 점수 표시는 하지 않는다(3.1-6, 4.5).
3. **(기관별 실재 재고 표시** — 지도 핀 배지에 그 기관이 *지금* 보관 중인 6개 카테고리 물품 수를 띄워, "갈 만한 곳"을 즉시 판별시킨다.)

**E. 새 물건 알림 (2026-11-08 결정)**

- 검색 결과 아래에서 반경 확장 또는 새 물건 알림 받기를 선택한다. 알림을 선택하면 같은 검색 상태를 전달하고 상단 새 물건 알림 탭을 선택 표시한다.
- 장소·제출 물품명·7일 기간은 고정하고 이메일을 입력한다. 알림 조건 수정은 같은 창에서 1·1.5·2km 반경만 변경하며 검색 결과에는 반영하지 않는다. 장소나 물품을 바꾸려면 검색 화면에서 다시 검색한다. 직접 탭 진입 시 조건이 없으면 먼저 장소·물품 검색을 안내한다.
- 이메일 확인 전에는 알림을 보내지 않는다. **기준 일정은 등록일을 D일로 할 때 다음날 D+1부터 D+7까지의 한국시간 달력상 7일**이다. 이메일 확인이 시작일보다 늦거나 링크가 만료된 경우의 일정 처리·연장 기간은 구현 전에 담당자와 정한다.
- 일일 발송 시각을 오전 9시 정각으로 약속하지 않는다. 데이터 갱신 후 새 유사 물품이 있는 날에만 물품 안내를 보내며, 없는 날은 건너뛴다. 결과 안내 횟수는 7회로 고정하지 않는다.
- 마지막 날에는 결과 유무와 관계없이 “이번 알림은 종료되며 이후에는 메일이 발송되지 않아요. 계속 받고 싶다면 연장해 주세요.”라는 종료·연장 안내를 보낸다. 연장하지 않으면 종료한다. 마지막 결과와 종료 안내를 한 통에 합칠지 등 발송 단위는 담당자와 확정한다.
- 예약 이후 새로 등록된 물품만 비교하고 같은 물품을 다시 보내지 않는다. 취소한 예약에 대한 후속 발송은 중지한다. 해지·연장 접근은 이메일 링크로 제공한다.
- 현재 예약/메일 기능은 미구현이다. 수집·알림 실패 분리, 실패 재시도, 연장·확인 링크 세부 계약은 담당 구현에서 정한다.

### 4.4 목업 및 프로토타입

목표 디자인은 전체 화면 지도 위에 왼쪽 검색·결과 패널을 띄우는 데스크톱 UI다. 상단은 `RETRIEVER` 로고 오른쪽에 “물건 찾기”, “새 물건 알림”, 오른쪽 끝에 “이용 안내”를 배치한다. 새 물건 알림 앞에는 이모지를 붙이지 않는다. 파란색·부드러운 회색 텍스트·둥근 개별 카드를 사용한다.

- 장소 카드: 이름·주소·카테고리 두 번째 단계 태그. 전화번호는 초기 장소 카드에서 생략하고 보관기관 연락처는 물품 상세에서 제공한다. `#`은 붙이지 않는다.
- 물품 카드: 사진·카테고리·색상(값이 있을 때만)·원문 명칭·보관장소·등록일. 검색 후에는 카드 구성을 유지하고 유사도 높은 순으로만 정렬한다. 점수 배지는 표시하지 않는다. 설명은 상세로 옮긴다.
- 장소 결과는 같은 높이의 카드 4곳씩 고정하고(마지막 페이지만 남은 개수), 카드 영역 스크롤 대신 하단 번호 페이지를 사용한다. 지도에는 현재 페이지 후보만 같은 번호로 표시한다. 물품 목록은 페이지당 4개로 고정하고 목록 스크롤 없이 번호로 이동한다. 기본 목록의 50건 커서는 필요한 페이지에 도달했을 때만 이어 받고, 경계의 일부 물품도 빠짐없이 다음 묶음과 함께 표시한다. 페이지/반경/알림 행동 영역을 목록과 분리해 겹침을 막는다. 서버가 다음 결과를 전달하는 계약은 검색 담당자와 확정한다.
- 새 물건 알림은 배경을 흐리게 하고 검색 패널보다 넓은 흰색 둥근 창을 연다. 조건 요약은 왼쪽, 이메일 입력은 오른쪽이다.
- 이용안내는 서비스 소개와 두 탭의 사용법을 담은 한 페이지다. 지원 카테고리와 기관 사전 연락을 짧게 안내한다.
- Make는 시각/동작 참고용이다. 실제 카카오맵·검색 API·이메일 연결은 서비스 구현에서 수행한다.
- 상세 배치·반응형·가독성 수치는 `docs/design-system.md`, 동작은 `docs/ui-patterns.md`를 따른다.

### 4.5 핵심 로직 및 예외 케이스

**핵심 로직**

**2026-11-08 상세 조회 예산 조정 및 실패 관측** — 사용자 결정으로 상세 요청 상한은 재시도를 포함한 400회, 상세 단계 예산은 60초다. 동시 4개·요청별 3초·실행 시작 후 180초 마감과 전체 함수 300초는 유지한다. HTTP 429도 네트워크·5xx와 같이 예산 안에서 한 번 재시도한다. API 본문 오류·식별 오류는 재시도하지 않는다. HTTP/API의 숫자 코드, timeout·DNS·TLS·식별·파싱 오류 등 안전한 분류만 `metadata.detail_lookup.failure_attempts_by_reason`에 시도별로 기록한다. 비밀값·전체 URL·응답 본문은 저장하지 않는다. 이 집계는 재시도로 복구된 시도의 오류도 포함하므로 최종 실패 물품 건수와 다르다.

**2026-11-07 일일 동기화 검증 및 시간 예산** — 상세 조회 행과 일반 행 모두 동일한 `detail_status` 키를 포함해 일괄 저장한다. 유일하게 확정되는 검증 별칭/기관 이름에는 상세 API를 호출하지 않는다. 동명 기관의 일시적 네트워크·5xx 실패만 한 번 재시도하며, 재시도도 동시 4개·각 요청 3초·합계 400회·단계 60초 및 실행 시작 후 180초 제한 안에서 처리한다. 영구적인 응답/식별 오류는 재시도하지 않고, 최종 실패·시간 부족·규칙 없음은 미매칭으로 남긴다. 증분 동기화의 목록 수집은 실행 시작 후 150초, 일반 DB 작업은 270초, 감사 로그는 295초까지로 요청과 재시도에 같은 예산을 적용한다. 경찰 목록 API의 재시도는 수집기 한 계층에서만 맡는다. 만료 정리는 기존 출처·등록일 인덱스로 오래된 등록일부터 배치 조회하고, 정리할 시간이 부족하면 다음 실행으로 넘겨 `metadata.cleanup_deferred`에 기록한다. 실패한 출처의 삭제 금지와 6개월 KST 경계는 유지한다. 실제 Vercel 함수 상한은 `vercel.json`의 300초다. 이 설정은 외부 서비스 응답·플랫폼 장애가 없다는 보장이 아니다.

DB 트리거가 기존 수집기의 재저장에서도 제외를 유지한다. 추가 외부 API 호출은 없으며, 감사 로그의 기존 `metadata.excluded_overseas_count`에 제외 건수를 기록한다. `unmatched_count`는 `unmatched`/`ambiguous`만 세고, 매칭률 분모는 `selected_count - excluded_overseas_count`로 계산한다(분모가 0이면 비율 없음). 이전 감사 로그에 제외 건수가 없으면 0으로 간주한다.

**2026-11-07 단일 상세 매핑 규칙** — `출처 + 최신 상세 API의 현재 보관장소 + 기관 코드 → storage_location_id`를 `storage_location_detail_mappings` 한 테이블에서만 관리한다. 기관 목록의 별도 `detail_code`는 제거한다. 종결·삭제·반입중을 포함한 처리 상태는 저장만 하고 연결 조건으로 쓰지 않는다. 원래 물품명·설명·장소명·`raw_payload`는 보존하며 현재 장소는 `detail_department`에 기록한다. 같은 코드여도 현재 장소가 다르면 별개 키이며, 과거 장소명과 현재 코드를 섞거나 이름으로 추측해 새 규칙을 만들지 않는다. 새 상세정보를 저장할 때 DB 트리거도 같은 키와 활성 기관·출처를 검증한다. 상세 조회는 동시 4개, 요청별 3초, 최대 400회, 단계 60초 및 실행 시작 후 180초 중 먼저 도달하는 제한을 적용한다. 실패·시간 부족·규칙 없음은 미연결로 남기고 감사 로그에 건수를 기록한다. 과거 미연결 전량은 크론에서 조회하지 않으며, 시간 제한으로 남은 과거 물품의 재검토는 별도 수동 작업이다. 이 결정은 2026-10-07의 상세 자동 조회 금지와 2026-11-06의 코드 컬럼·상태 필터 방식을 대체한다.

검토된 종류 표현이 이름·분류에 있는 키워드 후보를 받으며, 의미 검색 후보는 독립적으로 유지한다.
고비용 퍼지는 BM25 상위 100건과 이름 유사도 상위 100건의 합집합에 제한하고
이름 128자·분류 64자만 비교한다. 색상·브랜드의 검토된 작은 동의어는 검색 시 통일한다.
종류가 없는 여러 단어 질의는 이름·분류 단어 커버리지 0.6 이상 또는 퍼지 0.8 이상을 요구한다.
검색 필드 조회와 결과 상세 조회를 분리하되 반환 결과 전체·건수·페이지 계약은 유지한다.

## 10. 부록

**데모 시나리오**

1. "강남역"을 검색하고 후보 카드를 선택한다 → 기본 1km 범위와 기관을 표시한다. 기관이 0곳일 때만 1→1.5→2km 순서로 최대 2km까지 자동 확장한다.
2. 현재 범위 안의 연계기관·경찰관서 핀이 뜨고, 각 핀 배지에 **지금 보관 중인 물품 수**가 보인다.
3. 좌측에 현재 반경 기관들이 보관 중인 습득물 목록이 자동으로 표시된다.
4. 물품 검색창에 오타 "아이퐁"을 입력한다 → 아이폰 습득물이 상위 결과에 표시된다.
5. "검정 지갑"을 입력한다 → 등록명이 "지갑(남성용)"이어도 색상·설명 필드 매칭으로 결과가 나온다.
6. 특정 경찰관서 핀을 클릭한다 → 그 기관 물품만으로 목록이 바뀐다. "선택 반경 전체" 버튼으로 복귀한다.
7. 카드에서 상세를 열고 보관기관·원문 설명을 확인한다. 수령 안내에 따라 방문 전 기관에 연락한다.
8. 찾는 물건이 없으면 검색어를 유지해 1.5km 또는 2km로 넓히거나 새 물건 알림을 신청한다. 결과 하단의 돌아가기 버튼으로 한 단계씩 줄일 수 있다. 확장 결과에서 직전 반경 안의 보관기관 물품에는 ‘1km 이내’ 또는 ‘1.5km 이내’ 표식을 붙인다.
9. 알림은 다음날부터 7일간 유사 물품이 있는 날에만 보내고 마지막 날은 종료·연장을 안내한다.

**용어**

- **연계기관** — 경찰청 유실물 시스템에 연계된 지하철·공항·터미널 등의 기관
- **경찰관서** — 경찰서 및 지구대·파출소
- **matched / unmatched / ambiguous** — 습득물의 원문 보관장소명을 좌표가 있는 기관 레코드에 연결한 결과 상태

**기술 스택 (변경 가능)**

- 프런트엔드: React + TypeScript + Vite + React Router
- 지도: 카카오맵 JavaScript SDK
- 백엔드: FastAPI 기반 Vercel Functions
- 프런트엔드 제공 방식: Vite 빌드 결과물을 FastAPI가 정적 파일로 제공
- 데이터: Supabase Postgres + PostGIS (`vector` 확장 활성, 현재 미사용)
- 스케줄: Vercel Cron 6개, 각 하루 1회. 수집 4개는 UTC 00:00/12:00 = KST 09시대/21시대, 임베딩 복구 2개는 UTC 02:00/14:00 = KST 11시대/23시대
- 프런트엔드 구조: `frontend/src/{api, components, lib}`
- 백엔드 구조: `src/retriever_lost_found/{web, integrations, ingestion, search}`
- 배포용 정적 파일: `src/retriever_lost_found/web/static`
