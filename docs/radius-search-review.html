1. 한눈에 보는 결론

반경을 계산하고 지도 범위를 바꾸는 프런트엔드 기능은 정상 동작합니다. 문제는 반경이 넓어질수록 백엔드가 가져오는 습득물 후보가 급증한다는 점입니다.

핵심 결론 3km 오류는 반경 계산 버그나 기관 300곳 제한이 아닙니다. 125개 기관의 물품 약 3만 7천 건을 서버로 모두 가져오려다가 Supabase 쿼리 제한시간을 넘겼습니다.

2. 1·3·5km 반경은 어떻게 구현했나

서버에 반경을 보내는 대신, 브라우저가 이미 받은 전국 기관 좌표에서 선택 지점과의 거리를 계산합니다.

① 장소 선택카카오 검색 결과에서 기준 위치의 위도·경도를 선택
② 반경 선택기본 1km 또는 사용자가 3km·5km 버튼 선택
③ 거리 계산Haversine 공식으로 각 기관과의 실제 지표면 거리 계산
④ 기관 필터선택 반경 안에 있는 기관 ID만 추림
⑤ 물품 조회선택된 기관 ID 묶음을 기존 API로 전송

화면에서 함께 바뀌는 항목

  • 지도에 그려지는 반경 원의 크기
  • 지도에 표시되는 기관 마커와 기관 수
  • 선택 위치 설명과 지도 하단 범위 안내
  • /api/found-items로 보내는 기관 ID 목록
  • 특정 기관을 보던 중 반경을 바꾸면 해당 반경 전체 목록으로 복귀
  • 기관이 0곳이면 사용자가 직접 3km·5km로 넓히는 버튼 제공
변경하지 않은 부분 Supabase 스키마, 백엔드 API 계약, 운영 DB는 변경하지 않았습니다. 이번 구현은 프런트엔드가 보내는 기관 ID 범위만 1·3·5km에 따라 달라지게 한 것입니다.

3. 구현 후 어떤 오류가 발생했나

서울역 3km 범위에서 물품을 불러오는 도중 화면에 습득물 로딩 실패: Failed to fetch가 표시됐습니다.

로컬 미리보기는 Vite와 임시 API 중계 서버를 한 번 더 거쳤기 때문에 상세 JSON 오류 대신 일반 네트워크 오류가 표시됐습니다. 하지만 근본 원인은 로컬 서버가 아니라 Supabase 쿼리 시간 초과입니다.

4. 이 오류로 알게 된 구조적 문제

문제 1 — 검색어가 있어도 물품 전체를 먼저 가져온다

사용자가 “검정 지갑”을 검색해도 DB에서 검정 지갑 후보만 가져오는 것이 아닙니다. 반경 안의 물품 약 3만 7천 건을 먼저 Python 서버로 가져온 뒤 퍼지 검색을 실행합니다.

기관 125곳브라우저가 기관 ID 전달
물품 37,057건Supabase에서 전체 후보 조회
1,000건씩 전송페이지마다 조회와 정렬 반복
Python 검색모든 후보를 받은 뒤 퍼지 랭킹
화면 반환최종 결과를 브라우저에 전달

문제 2 — 1,000건 페이징이 DB 작업량을 줄이지 못한다

1,000건만 반환하더라도 DB는 최신 1,000건을 고르기 위해 훨씬 많은 후보를 읽고 정렬할 수 있습니다. 현재 offset 방식은 뒤 페이지로 갈수록 앞 데이터를 반복해서 건너뛰어야 합니다.

문제 3 — 현재 인덱스가 실제 조회 형태와 정확히 맞지 않는다

현재 인덱스 순서

기관 → 카테고리 → 등록일

카테고리를 지정할 때 유리합니다.

실제 API 요청

여러 기관 → 전체 카테고리 → 등록일·ID 순

여러 묶음을 읽고 다시 정렬할 가능성이 있습니다.

문제 4 — 기관 300곳 제한과 별개의 문제다

서울역 3km는 기관 125곳뿐이므로 300곳 제한에 걸리지 않았습니다. 병목은 “기관 수”보다 그 기관들이 가진 “물품 후보 수”에서 발생했습니다.

문제 5 — 좌표 기반 공간 쿼리만으로는 해결되지 않는다

DB가 반경 내 기관을 직접 찾도록 바꾸면 긴 기관 ID URL 문제는 개선됩니다. 하지만 찾아낸 기관의 물품 3만 7천 건을 모두 가져오는 구조는 그대로이므로 이번 시간 초과의 핵심 해결책은 아닙니다.

5. 어떻게 수정하는 것이 좋은가

한 번에 구조를 모두 바꾸기보다, 병목을 측정한 뒤 목록 조회와 검색 조회를 분리해 개선하는 방식을 권장합니다.

A. 먼저 스테이징에서 쿼리 실행계획 확인

  • 운영 DB가 아닌 스테이징에서 동일 규모 데이터를 준비합니다.
  • EXPLAIN ANALYZE로 테이블 스캔·정렬·인덱스 사용 시간을 확인합니다.
  • 추측으로 인덱스를 추가하지 않고 실제 병목을 기준으로 결정합니다.

B. 실제 조회에 맞는 인덱스 후보 검증

다음 형태를 후보로 실험하되, 적용 여부는 실행계획과 쓰기 비용을 함께 보고 결정합니다.

(storage_location_id, registered_on DESC, id DESC)

C. 검색어가 없는 목록은 커서 기반으로 나눠 보여주기

  • 첫 화면에서 3만 건 전체를 보내지 않고 최신 일부만 반환합니다.
  • 사용자가 더 볼 때 다음 페이지를 요청합니다.
  • offset 대신 마지막 등록일·ID를 사용하는 커서 페이지네이션을 권장합니다.

D. 검색어가 있으면 DB에서 후보를 먼저 줄이기

  • 정규화 검색 텍스트, 카테고리, 색상 등으로 1차 후보를 DB에서 축소합니다.
  • 축소된 후보에만 현재 Python 퍼지 랭킹을 적용합니다.
  • 후보 상한은 평가셋으로 검색 품질을 확인하며 정합니다.

E. 하지 말아야 할 임시 해결

  • 기관 ID를 앞에서 300개만 잘라 일부 물품을 조용히 누락하는 방식
  • 프런트에서 여러 요청으로 쪼갠 뒤 순위를 단순 합치는 방식
  • DB 원인을 확인하지 않고 제한시간만 크게 늘리는 방식
  • 오류를 빈 결과로 바꿔 사용자가 “물품이 없다”고 오인하게 하는 방식

6. 권장 진행 순서

  1. 프런트 반경 기능은 유지지도와 기관 범위 계산은 정상이며 자동 테스트도 통과했습니다.
  2. 3km·5km 출시 전 백엔드 조회 문제 해결현재 상태로는 넓은 반경에서 안정적인 물품 조회를 보장할 수 없습니다.
  3. 스테이징 데이터와 EXPLAIN ANALYZE 준비현재 쿼리, 인덱스 후보, 커서 페이지네이션을 같은 조건에서 비교합니다.
  4. 목록 조회와 검색 조회 분리검색어가 없을 때는 최신순 페이지, 검색어가 있을 때는 후보 축소 후 퍼지 랭킹을 사용합니다.
  5. 대표 지점 성능 검증서울역 1·3·5km와 최고 밀집 지역에서 p50·p95, 후보 수, 오류율을 측정합니다.
  6. 기준 충족 후 배포지도 기관 수와 검색 범위가 일치하고, 시간 초과 없이 한국어 오류 처리가 되는지 확인합니다.
팀 결정이 필요한 항목 3km·5km에서 검색어 없이 물품 전체를 반드시 보여줘야 하는지, 아니면 최신순 페이지로 나눠 보여줘도 되는지 제품 정책을 먼저 합의해야 합니다.
최종 제안 반경 선택 UI는 유지하되 현재 상태로 바로 출시하지 않습니다. 스테이징에서 DB 실행계획을 확인하고, 목록 페이지네이션과 검색 후보 축소를 적용한 뒤 서울역 5km 기준 성능을 다시 측정하는 것이 가장 안전합니다.
