## 2. 오해하기 쉬운 두 작업

### ③ "스케줄러"는 데이터 수집 크론이 아니다

사용자가 쓰는 **분실물 알림 예약** 기능이다. PRD 2.1-4와 4.2 P1 "신규 등록 알림"이 이 기능이다.

1. 사용자가 장소와 검색어로 찾아봤지만 원하는 물건이 없다.
2. 그 검색 조건과 이메일을 저장해 **예약**을 건다.
3. 매일 습득물이 갱신될 때마다, 저장한 조건과 **유사한 물품**이 새로 들어왔는지 확인한다.
4. 있으면 입력해 둔 이메일로 알린다.
5. 예약은 처음 건 날부터 **1주일** 유지된 뒤 끝난다.

다음 두 가지와 혼동하지 않는다.

- `/api/cron/{partner,police}-sync` — 매일 KST 09:00에 도는 **수집 크론**이며 이미 있다. ③은 이 수집이 끝난 뒤에 도는 **새 작업**이다.
- PRD 3.3·Q6의 **크론 실패 이메일 알림** — 운영자에게 가는 알림이다. 이메일 발송 수단만 함께 쓸 수 있다.

### ⑦ "UI/UX"는 프런트엔드 디자인 개편이다

화면의 **시각 디자인을 바꾸는 작업**이다. 사진(②)이나 상세 창(⑤) 같은 기능 추가는 김택수 담당이다.

## 3. 작업별 현재 상태와 선행 관계

2026-11-05에 코드를 확인한 결과다.

### ① 검색을 DB로 — 권희준

- **현재:** 검색어가 있으면 `SupabaseFoundItemClient.fetch_items()`가 반경 안 후보를 **전부** 받는다. 그다음 `search/fuzzy.py`의 `rank_found_items()`가 Python에서 순위를 매긴다(`web/app.py` `found_items()`). 3km 반경이면 후보가 약 3.7만 건이다.
- 검색어 없는 목록은 PR #28에서 RPC `found_items_page` 50건 커서 페이징으로 1단계를 진행했다. 마이그레이션은 2026-11-05 운영에 적용했다.
- **목표:** 순위 매기기와 자르기를 DB에서 끝내고 상위 결과만 받는다. 응답 시간은 p95 1.5초(PRD 2.5-1)다.
- **지켜야 할 것:**
  - 검색은 언제나 `location_ids` 범위 안에서만 한다(PRD 4.1).
  - 원문은 변형하지 않고, 정규화한 값은 `normalized_search_text`에만 둔다(PRD 3.3).
  - 검색어는 30자를 넘지 않는다.
  - `/api/found-items` 응답은 캐시하지 않는다.
- **착수 시점(2026-11-05 결정):** ⑥의 결론을 기다린다. 그동안 PR #28의 운영 적용과 측정을 먼저 한다.
- **선행:** ⑥에서 정하는 검색 방식에 따라 구현이 갈린다.
  - 퍼지 검색이면 `pg_trgm` 등이 필요하다. 지금 마이그레이션에는 `postgis`·`vector` 확장만 있다.
  - 임베딩이면 `vector` 컬럼과 임베딩 파이프라인이 필요하다.
- 응답 형식이 바뀌면 화면 담당(②⑤⑦)과 먼저 합의한다.

### ② 사진 표시 — 김택수

- **현재:** `image_url`은 `/api/found-items` 응답에 이미 들어 있다. 하지만 화면 타입 `FoundItem`에 이 필드가 없어서 카드에는 카테고리 이모지만 나온다. 사진 호스트는 CSP `img-src`에 이미 추가했다.
- 주소가 `…/img02_no_img.gif`인 기본 그림은 "사진 없음"으로 처리한다(PRD 3.2-2).
- **실측(2026-11-05, 잠실역 1km 702건):**
  - 실제 사진은 44건(6%)이고, 기본 그림이 658건이다.
  - 사진 1장을 받아 봤다. 원본 JPEG로 약 2.4MB이고 `Cache-Control: no-store`로 내려온다.
  - 우리 도메인을 `Referer`로 붙여도 정상으로 받아진다.
- 목록에 원본을 그대로 쓰면 무겁다. `loading="lazy"`, 고정 비율 영역, 로드 실패 처리가 필요하다.

### ③ 스케줄러(분실물 알림 예약) — 권희준, 예약 입력 화면은 강지현

- **현재:** 관련 코드·테이블·이메일 연동이 하나도 없다.
- **필요한 구성:**
  - 예약 저장 API
  - 예약 테이블 — RLS를 켜고 `service_role`만 접근한다(절대 규칙 6)
  - 수집 뒤에 도는 비교 작업
  - 확인 메일·알림 메일 발송
  - 1주일 만료와 연장 처리
  - 화면의 예약 입력(강지현)
- 안내 문구는 "유사한 물품이 새로 등록됐다"로 쓰고, 본인 물건이라고 단정하지 않는다. 이 기능은 공공 DB를 다시 **탐색**해 주는 것이고 직접 매칭이 아니다(PRD 2.2 비목표 1).
- 같은 발송 수단으로 운영자용 크론 실패 알림(PRD Q6)도 권희준이 만든다.

**결정된 것 (2026-11-05)**

| 항목 | 결정 |
| --- | --- |
| 회원가입 | 이번 스프린트는 회원가입 없이 이메일만 받는다. 회원가입 방식과의 비교(PRD 2.1-4)는 그 뒤에 한다 |
| 저장할 조건 | 검색어 + 장소 좌표 + 반경. 비교할 때마다 그 시점의 기관 목록으로 반경 안 기관을 다시 계산한다(공간 1차 필터 — PRD 4.1) |
| "유사"의 기준 | ⑥의 결론이 나기 전까지는 지금 검색의 퍼지 순위·임계값(`rank_found_items`)을 그대로 쓴다. ⑥이 정해지면 바꾼다 |
| 비교 대상 | 예약 이후 새로 등록된 물품만 본다. 한 번 알린 물품은 다시 보내지 않는다 |
| 이메일 확인 | 확인 메일의 링크를 눌러야 예약이 켜진다. 다른 사람의 주소로 예약해 메일을 보내는 것을 막는다 |
| 만료 | 등록한 날부터 1주일. 만료 전에 늘릴 수 있도록 연장 버튼을 둔다 |
| 실행 시점 | 각 수집 크론(`partner`·`police`)이 끝날 때 그 출처에서 새로 들어온 물품만 비교한다. 크론은 늘리지 않는다 |
| 예약 입력 화면 | 강지현이 만든다(⑦과 같은 파일) |

**지켜야 할 것** — 알림 단계가 실패해도 그 출처의 수집 결과(`ingestion_runs.status`)와 보존기간 정리에 영향을 주지 않게 분리한다(출처 독립·보존 우선, `AGENTS.md` 4장). 수집 함수는 300초 안에 끝나야 한다. 2026-09-24 실측 수집 시간은 partner 114초, police 52초였다.

**결정 필요** — 아래 항목은 정하기 전에 구현하지 않는다.

| 항목 | 정할 내용 |
| --- | --- |
| 발신 수단 | 팀 도메인이 없다(2026-11-05 확인). 도메인을 사서 메일 서비스에 인증할지, Gmail 앱 비밀번호로 보낼지 권희준이 나중에 정한다. 정하기 전에는 발송 설정을 환경 변수로 바꿀 수 있게 만들어 두면 방식이 정해진 뒤 코드를 고치지 않아도 된다. 확인 메일과 알림 메일 모두 이것이 있어야 보낼 수 있으므로 ③의 선행 조건이다. 키는 서버 전용이고(절대 규칙 4), 환경 변수를 추가하면 `.env.example`·README·CI `env`를 함께 갱신한다 |
| 연장 방식 | 연장 한 번에 늘어나는 기간과 최대 횟수. 회원가입이 없으므로 연장 버튼은 메일 속 링크로 두는 것이 자연스럽다 |
| 취소·수신 거부 | 메일마다 예약 취소 링크를 넣을지 |
| 개인정보 | 이메일 수집 동의 문구, 연장하지 않고 만료된 예약의 삭제 시점. PRD 3.3 '법적' 항목은 습득물 안의 개인정보만 다룬다 |
| 발송 상한 | 남용과 비용을 막을 하루 발송 상한 |

### ④ 기관 매핑 — 김성현

- **무엇을 하나:** 경찰청 API의 원문 보관장소명(`raw_storage_name`)을 Supabase 기관 레코드에 연결한다. 연결에 실패하면 `storage_location_id`가 NULL이 되고, 그 물품은 지도와 검색에서 사라진다(PRD 6 리스크 1행).
- **현재 구현:** `ingestion/service.py`의 `_LocationResolver`가 아래 순서로 찾는다.
  1. 검증된 별칭
  2. 정규화명 정확 일치
  3. 괄호를 뺀 기본명
  4. 접미사 포함
- 이름이 같은 기관은 DB 트리거의 검증된 규칙으로 풀린다(369개, 2026-10-02).
- 그래도 풀리지 않은 물품은 `unmatched`로 저장하고 사람이 고친다. 수집 중에 상세 API를 자동으로 호출하지 않는다(2026-10-07 결정, PRD 4.5).
- **금지:** 매칭에 실패한 물품에 추정 좌표를 채워 넣지 않는다(절대 규칙 5).
- **할 일:**
  1. 현재 매칭률을 출처별·등록일별로 측정한다(`ingestion_runs.unmatched_count / selected_count`, D5).
  2. 실패가 많은 원문명부터 검증된 별칭으로 등록한다.
  3. 별칭 등록 절차를 정한다(PRD 4.3-D P0).
- **참고(2026-09-27 측정):** 전체 매칭률은 99.22%였다. 하지만 최근 2주치 경찰관서만 보면 81~94%였다.
  - 가설: 물품이 지구대에 보관됐다가 경찰서로 넘어가면서 보관장소명이 바뀐다. 그런데 증분 수집은 마지막 등록일만 다시 받기 때문에 옛 이름이 그대로 남는다.
  - 이 가설은 아직 확인하지 않았다.
- **위험:** `ingestion/store.py`의 `_fetch_all()`은 `order` 없이 offset으로 페이지를 넘긴다. 기관이나 별칭 목록을 읽다가 행이 빠지면 매칭이 조용히 실패할 수 있다. 재현된 적은 없다.

### ⑤ 물품 클릭 시 상세 창 — 김택수

- **현재(2026-11-08):** 작업 브랜치에서 카드 선택 시 데스크톱 중앙 모달·모바일 하단 시트를 여는 기능을 구현하고 검증했다. 운영에는 아직 반영하지 않았다. 제품 결정은 PRD 4.3-C, 세부 동작은 `docs/ui-patterns.md` 4장에 기록했다.
- **담을 내용:** 사진(②), 설명 전문, 보관기관 이름·주소·전화번호(PRD 4.3-C P0, M3), 등록일.
- **API 변경 없이 만들 수 있다:**
  - `/api/found-items` 응답에 `storage_location_id`가 이미 있다.
  - `FoundItemBrowser`가 받는 `scope`(기관 목록)에 `address`·`phone`이 있다.
  - 화면 타입 `FoundItem`에 `storage_location_id`·`image_url`만 추가하면 된다.
- **접근성:** `button`으로 열고 Esc로 닫는다. 열 때 초점을 옮기고 닫으면 원래 자리로 돌려 놓는다(`docs/frontend-guidelines.md` 8장).
- PRD 4.3-C P1 "언제까지 보관되는지"는 현재 API에 없어 이번 상세 창에서는 제외하기로 했다(2026-11-08 사용자 결정).

### ⑥ 검색 방식 확정 — 김성현

- **정할 것:**
  - 퍼지 유지·임베딩·LLM·조합 가운데 무엇을 쓸지(Q3)
  - 이미지 검색을 넣을지(Q4)
- **평가셋:** 서울역 반경 5km에서 타깃 20건을 고르고 타깃마다 검색어 5개를 만들어 질의 100개를 구성한다(PRD 2.4, Q2). 2026-11-05 기준 이 범위의 물품은 40,013건이다.
- **판정 기준(M2):**
  - p95 1.5초
  - TOP-5 포함률 95%
  - 거절 성능 95%
  - nDCG@5
  - 검색 1,000회당 비용, 월 10만 회 기준 비용
- PRD 2.1-1·2.3은 TOP-3 95%를 목표로 적었다. 어느 기준으로 보고할지 정해야 한다.
- **근거(2026-10-03, 서울역 1km 7,919건):**
  - 오타에는 강하다 — "아이퐁"은 100%.
  - 동의어·구어에는 약하다 — 핸드폰 16%, 백팩 13%, 비니 0%. 같은 물품을 휴대폰·가방·모자로 찾으면 100%다.
  - 검색어가 있으면 응답 시간의 약 90%를 순위 매기기가 차지한다.
- **이 작업이 먼저 끝나야 한다.** 결과가 ①의 DB 구현 방식과 ③의 "유사" 기준을 정한다.

### ⑦ UI/UX 디자인 개편 — 강지현

- **착수 전 읽기:** PRD → `docs/ui-patterns.md` → `docs/design-system.md` → `docs/frontend-guidelines.md` (`AGENTS.md` 6장).
- **정할 것:**
  - DS-01 — 시각 분위기
  - DS-02 — 웹폰트
  - UX-03 — 모바일에서 지도와 목록의 우선순위
  - 결정하면 `docs/design-system.md`의 토큰부터 바꾼다.
- **주의 — 개발 화면과 배포 화면의 색이 다르다:**
  - 개발 모드는 테마 미리보기(`warm-ivory`·`deep-cocoa`·`retriever-modern`)를 쓰고, 기본값이 아이보리·갈색 계열의 `retriever-modern`이다.
  - 배포본은 테마를 적용하지 않는다(`App.tsx`가 개발 모드에서만 `data-theme`을 설정). 그래서 `styles.css` `:root`의 녹색 계열 기본 토큰으로 보인다.
  - 어느 쪽을 기준으로 할지 먼저 정한다.
- **지켜야 할 것:**
  - loading·empty·error·disabled 상태
  - 키보드·스크린 리더 사용
  - 모바일 폭
  - 유사도 % 비노출(D2)
- **③의 예약 입력 화면도 만든다:** 이메일과 개인정보 동의 입력, 확인 메일 안내, 오류 상태가 들어간다. 검색 결과가 0건일 때만 보여 줄지, 결과 아래에 늘 둘지는 ⑦에서 정한다. 요청·응답 형식은 권희준과 먼저 합의한다.
- ②⑤와 같은 파일(`FoundItemBrowser.tsx`, `styles.css`)을 고친다. 순서를 먼저 합의한다.

## 4. 협업 규칙

- 작업마다 최종 책임자(DRI)는 그 작업의 담당 한 명이다.
- 같은 파일을 여러 명이 고칠 때는 착수 전에 순서와 범위를 합의하고, PR에 고친 파일과 이유를 적는다. 이번 스프린트에서 겹치는 곳은 다음과 같다.
  - ②⑤⑦과 ③의 예약 입력 화면 — `frontend/src/components/FoundItemBrowser.tsx`, `frontend/src/styles.css`
  - ①③ — `web/app.py`, `integrations/supabase.py`, `supabase/migrations/` (담당이 같다)
- 프런트와 백엔드를 함께 바꾸기 전에는 다음을 먼저 합의한다(`AGENTS.md` 4장).
  - 요청 파라미터
  - 응답 필드와 타입
  - 오류 코드와 메시지
  - 빈 결과 형식
  - 페이징 방식
- 브랜치는 기능·이슈 단위로 만들고, 병합한 뒤 지운다(`AGENTS.md` 10장).
