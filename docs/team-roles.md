## 2. 작업별 메모

2026-11-09에 최신 `main`을 확인한 내용이다.

### 1. 검색 기능 구현 + 동의어 사전 — 김성현, 11-13(금) 밤

- **지금:** 검색어가 있으면 기관 범위의 동의어·키워드 후보를 BM25로 정렬하고 상위 200건만 BGE-M3로 재정렬한다. 검색 결과와 검색어 없는 목록 모두 50건씩 받는다. 기존 물품별 퍼지 구현은 제거한다.
- **2026-11-12 검색 범위 결정:** 검색어 오타는 사용자가 직접 수정한다. 오타 자동 보정·오타 허용은 개발·평가·데모의 요구사항에서 제외하고, 기억나는 특징·동의어·표현 차이를 검색 품질 개선 대상으로 삼는다(PRD 2.2·2.4·4.5). 기존 보정 코드·테스트는 이번 문서 변경에서 수정하지 않았다. 위 “지금”과 아래 수치는 당시 기록이며 최신 검색 경로는 PRD 4.5를 따른다.
- **동의어 사전이 겨냥하는 약점(2026-10-03, 서울역 1km 7,919건):**
  - 과거 오타 측정 — "아이퐁"은 100%. 이 수치는 이력으로 보존하며 현재 합격 기준에는 포함하지 않는다.
  - 동의어·구어에는 약하다 — 핸드폰 16%, 백팩 13%, 비니 0%. 같은 물품을 휴대폰·가방·모자로 찾으면 100%다.
- BGE-M3 임베딩 적재 사전 확인 기록이 있다(`docs/measurements.md`, 2026-11-07).
- **지켜야 할 것:**
  - 검색은 언제나 `location_ids` 범위 안에서만 한다(PRD 4.1).
  - 원문(`item_name`·`description`)은 바꾸지 않는다. 동의어는 검색어를 넓히는 쪽이나 `normalized_search_text`에서만 쓴다(절대 규칙 3).
  - 검색어는 30자를 넘지 않는다(D3).
  - `/api/found-items` 응답은 캐시하지 않는다(절대 규칙 7).
  - 점수·%는 화면에 내지 않고 높은 순 정렬에만 쓴다(D2).
- **판정 기준(M2):** p95 1.5초 · TOP-5 포함률 95% · 거절 성능 95% · nDCG@5 · 검색 1,000회당 비용. 평가셋은 서울역 반경 5km, 타깃 20건 × 검색어 5개다(PRD 2.4, Q2). 잰 숫자는 `docs/measurements.md`에 남긴다.
- **2번이 이 결과를 쓴다.** 알림 메일의 "유사" 판정은 이 검색 방법을 따른다(2026-11-06 결정). 마감이 2번보다 하루 앞인 이유다. 판정 함수의 입력·출력은 권희준과 먼저 맞춘다.
- 정렬 방식이나 다음 결과 응답 형식이 바뀌면 강지현(7번)과 먼저 합의한다.

### 2. 메일 작업 마무리 — 권희준, 11-14(토)

- **범위:** 분실물 알림 예약(팀 명칭 "스케줄러") 메일을 운영에서 실제로 보내는 데까지다. PRD 2.1-4 · 4.2 P1 · 4.3-E가 사양이다.
- **지금:** 구현은 `feat-alert-scheduler` 브랜치에 있고 아직 PR이 없다. 설계는 그 브랜치의 `docs/alert-scheduler/2026-11-06-email-scheduler-design.md`에 있다. 화면 `NewItemAlert.tsx`(PR #38)는 아직 `/api/alerts`를 부르지 않는다.
- **남은 순서:**
  1. 1번의 검색 방법으로 유사 판정을 연결한다.
  2. 최신 `main`을 반영한다.
  3. 운영 DB에 마이그레이션을 적용한다.
  4. Vercel Production 환경 변수를 넣는다.
  5. PR·병합 뒤 실제 발송을 확인하고 `docs/measurements.md`에 기록한다.
- **맞출 것:**
  - **반경** — 브랜치는 1·3·5km만 받는다(`ALLOWED_RADII_METERS`, DB 제약 `alert_reservations_radius_allowed`, 오류 문구). 3번에 맞춰 1000·1500·2000m로 바꾼다. 메일 본문은 `radius_m // 1000`이라 1.5km가 "1km"로 나온다. 운영 DB에 적용하기 전이면 마이그레이션 파일을 고쳐서 끝낼 수 있다.
  - **일정** — PRD 4.3-E(2026-11-08)는 "등록 다음날부터 7일, 새 유사 물품이 있는 날만 결과 메일, 마지막 날 종료·연장 안내"다. 브랜치 설계(2026-11-06)는 "등록일 + 7일 11:00 만료, 만료 전날 안내 메일"이다. 한쪽으로 맞춘다.
  - **화면** — `NewItemAlert.tsx`와 요청·응답 형식을 강지현과 맞춘다(7번).
  - **여러 장소** — 알림 예약은 장소 하나(좌표 1개)만 저장한다. 5번과 동작을 맞춘다.
- **지켜야 할 것:**
  - 알림 단계가 실패해도 그 출처의 수집 결과와 보존기간 정리에 영향을 주지 않는다(출처 독립, `AGENTS.md` 4장).
  - 문구는 "유사한 물품이 새로 등록됐다"로 쓴다. 본인 물건이라고 단정하지 않는다(절대 규칙 10 부연).

## 3. 선행 관계와 겹치는 파일

- **1 → 2:** 2번의 유사 판정이 1번의 검색 방법을 쓴다. 1번(금 밤)이 늦어지면 2번(토)도 밀린다.
- **3 → 2:** 2번의 허용 반경을 3번에 맞춘다.
- **5 ↔ 2:** 여러 장소에서 알림을 걸 때의 동작을 정한다.
- **3·4 → 5·7:** 모두 프런트(`App.tsx`, `FoundItemBrowser.tsx`, `styles.css` 등)를 고친다. 마감 순서대로 김택수(목)가 먼저 병합하고 강지현(금·일)이 이어 받는다. 순서가 바뀌면 착수 전에 합의한다.

## 4. 협업 규칙

- 작업마다 최종 책임자(DRI)는 그 작업의 담당 한 명이다.
- 같은 파일을 여러 명이 고칠 때는 착수 전에 순서와 범위를 합의하고, PR에 고친 파일과 이유를 적는다.
- 프런트와 백엔드를 함께 바꾸기 전에는 다음을 먼저 합의한다(`AGENTS.md` 4장).
  - 요청 파라미터
  - 응답 필드와 타입
  - 오류 코드와 메시지
  - 빈 결과 형식
  - 페이징 방식
- 브랜치는 기능·이슈 단위로 만들고, 병합한 뒤 지운다(`AGENTS.md` 10장).
