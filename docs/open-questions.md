## 1. D1~D6 결정 근거

**PRD가 기준이다.** 아래 6건은 "어느 쪽이 맞나"의 문제가 아니라 **PRD 값이 사양이고 코드가 아직 못 따라온 것**이다.
결정 요약과 바꿔야 할 파일은 `AGENTS.md` 9장에 있다.

### D1 — 달력상 6개월 보존, 일회성 백필 완료

**보존기간은 두 군데에 있다.**

| 위치 | 역할 |
| --- | --- |
| `SOURCE_RETENTION_MONTHS` (`ingestion/collector.py`) | **수집 창** — API에서 얼마나 과거까지 가져올지 |
| `item_sources.retention_months` (새 마이그레이션: 6 / 6) | **삭제** — RPC `delete_expired_found_items`가 이 값으로 지운다 |

**한쪽만 바꾸면 조용히 어긋난다.** Python과 DB 값을 모두 달력상 6개월로 유지한다.

**2026-09-26 변경 결정 및 실행:** 사용자의 승인에 따라 일회성 임시 스크립트로 과거 누락 구간을 묶음 수집했다. 이후 사용자가 180일이 아닌 완료된 어제까지 달력상 6개월이라고 바로잡아, 2026-03-26~2026-09-25를 목표 구간으로 확장했다. 이후에는 기존 일일 증분 동기화만 사용한다.

**진행 이유** — 경찰 실제 보관은 6개월인데 변경 전 DB에는 최대 20일치뿐이었다. 3주 전에 잃어버린 사람에게 잘못된 빈 결과를 보여줄 수 있었다.

### D3 — 검색어 30자

PRD 3.3대로 **30자**가 사양이다. 상한 초과는 400과 한국어 메시지로 응답하고, 클라이언트도 같은 값으로 제한한다 (PRD 4.5 예외 케이스).

**30자는 지금의 단일 검색어 입력에 대한 값이다.** PRD 4.2 P1 "텍스트·이미지 통합 검색 입력"은 물품 설명을 길게 쓰게 하는 기능이므로, **그 기능을 만들 때 상한을 다시 봐야 한다.** 그때 PRD 3.3과 4.2 P1을 함께 정리한다.

### D5 — 지금은 얼마나 나쁜지조차 모른다

매칭 실패 → 습득물이 지도에서 사라짐은 PRD 6에서 영향도 **높음**인 최상위 리스크다. **데이터는 이미 `ingestion_runs.unmatched_count`에 쌓이고 있다.** 아직 아무도 보지 않았을 뿐이고, PRD 2.3의 매칭률 기준선이 "결정 필요"로 남은 것도 같은 이유다.

`unmatched_count / selected_count`를 먼저 확인한다. PRD 목표는 `matched` 99%다. 실제가 99%면 도구가 필요 없고, 80%면 5건 중 1건이 지도에서 사라지고 있다는 뜻이다. **수치를 본 뒤에 도구를 정한다.**

참고 — 삭제된 `tools/`(커밋 `09cca07`)에 있던 것은 `geocode_institutions.py`와 `sync_police_locations.py`(좌표 도구)다. PRD 4.3-D가 말하는 **별칭 등록 스크립트는 원래 없었을 수 있다.** 복원할지 새로 만들지는 매칭률을 본 뒤에 정한다.

### D6 — React 전환을 시작할 때

**정적 파일 제공 방식**(Vite 빌드 산출물을 FastAPI가 서빙)과 **CSP 재검토**를 함께 다룬다.

## 4. 착수 전 확인이 필요한 기술 항목

- **습득물 사진 노출(P1)** — 현재 CSP `img-src`는 `self`·`data:`·카카오 도메인만 허용한다. 공공데이터 원문 사진 호스트는 **포함되어 있지 않다.** 노출하려면 CSP 수정과 오류 이미지 처리가 선행이다. (PRD 3.2-2)
- **이미지 검색(P1, M4)** — `vector` 확장은 켜져 있으나 임베딩 컬럼·파이프라인이 없다. (PRD 3.2-1)
- **Vercel Hobby 크론 지연** — 지정한 한 시간 안에서 실행 시각이 밀릴 수 있다. 데이터 신선도를 24시간 이내로 단정하지 않는다. (PRD 3.3)
