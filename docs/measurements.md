# 실측 기록

> 이 프로젝트에서 잰 **정량 결과는 모두 이 문서에 남긴다.** 시간, 크기, 건수, 비율, 비용, 검색 품질 지표가 모두 해당한다(AGENTS.md 6장).
> **실제로 잰 숫자만** 적고, 추정치는 쓰지 않는다. 숫자마다 측정 조건을 같이 적는다.
> 원자료(CSV·스크립트·로그·스크린샷)는 저장소 밖에 둔다(AGENTS.md 6장 "개발 중 생성한 문서·자료 보관").

## 0. 기록하는 법

- 새 측정은 해당 주제 절 아래에 날짜와 함께 추가한다. 맞는 주제 절이 없으면 새 절을 만든다.
- 측정마다 아래 항목을 적는다.
  - **언제:** 날짜. 시각을 적을 때는 UTC인지 KST인지 밝힌다.
  - **무엇을:** 잰 대상(엔드포인트·함수·쿼리·지표).
  - **조건:** 데이터 범위(위치·반경·건수), 실행 위치(로컬 PC·Vercel·운영 DB), 횟수, 몇 번째 실행인지.
  - **숫자:** 전후를 비교했다면 같은 조건의 두 값을 나란히 적는다.
  - **해석과 한계:** 이 숫자로 말할 수 있는 것과 없는 것.
  - **관련 PR·커밋.**
- 같은 대상을 다시 재면 이전 값을 지우지 않고 새 행을 추가한다. 추세를 볼 수 있어야 한다.
- 운영 DB는 반복 호출하면 시간 초과가 번질 수 있다. 운영에서는 횟수를 최소로 하고, 몇 번 쟀는지 적는다.

## 1. `/api/found-items` 응답 속도

목표는 PRD 3.3·5의 조회 p95 1.5초다. 담당과 다음 작업은 `docs/team-roles.md` ①·⑥을 본다.

### 1.1 측정 조건 (2026-11-05)

| 항목 | 값 |
| --- | --- |
| 위치 | 서울역(37.5547, 126.9707) 반경 1·3·5km |
| 기관 수 | 18 · 126 · 237곳. 브라우저의 반경 필터와 같은 기관 목록이다 |
| 습득물 수 | 8,714 · 35,449 · 39,945건. 당일 수집(00:23·00:35 UTC) 직후 기준이다 |
| 운영 DB | Supabase `retriever`(ap-northeast-2) |
| 호출 위치 | 따로 적지 않으면 로컬 PC(Windows)에서 운영 DB를 직접 불렀다. 실서비스의 Vercel 함수는 같은 서울 리전(`icn1`)이라 네트워크 시간이 이보다 짧다 |
| 순위 계산 | 로컬 PC의 Python 3.12. 운영에서 받은 후보를 그대로 썼다 |

**운영 DB 시간은 실행마다 크게 흔들린다.** 같은 쿼리를 연달아 두 번 돌리면 첫 번째가 두 번째보다 약 5~35배 느렸다(아래 표의 "첫 번 / 두 번째").

### 1.2 바뀌기 전 — 후보 전체를 1,000건씩 반복해서 받기

검색어가 있든 없든, `fetch_items()`가 반경 안 습득물 **전체**를 Data API에서 1,000건씩 offset으로 받았다. offset 페이지를 받을 때마다 DB가 후보 전체를 다시 정렬한다.

| 반경 | 결과 | 걸린 시간 | 왕복 | 받은 크기 |
| --- | --- | ---: | ---: | ---: |
| 1km | 8,714건 | 7.5초 | 9번 | 6.1MB |
| 3km | **실패** — 첫 페이지에서 `57014 statement timeout`(8.3초). 사용자에게는 502 | — | 1번 | — |
| 5km | 39,945건 | 32.3초 | 40번 | 28.1MB |

예전 기록(2026-10-07, 같은 방식): 1km 3~6초 · 3km 16~26초 · 5km 23~24초였고, 3km에서 시간 초과가 관측됐다.

### 1.3 검색어 없는 목록 — 50건 커서 페이징 (PR #28, 2026-11-05 병합·배포)

검색어 없이 장소만 고르면 RPC `found_items_page`로 최신순 50건만 받는다. 화면은 "물품 더 보기"로 다음 50건을 이어 붙인다.

| 반경 | 바뀌기 전 | 바뀐 후: DB 함수 실행 | 화면에 그리는 물품 |
| --- | --- | ---: | --- |
| 1km | 7.5초, 6.1MB | 약 10ms | 8,714건 → 50건 |
| 3km | 시간 초과(502) | 약 19ms | 35,449건 → 50건 |
| 5km | 32.3초, 28.1MB | 약 20ms | 39,945건 → 50건 |

- DB 함수 실행 시간은 운영 `explain analyze`에서 반경 기관 목록을 계산하는 시간을 뺀 값이다.
- 1·2페이지 결과가 직접 정렬한 정답과 일치하는 것을 운영에서 확인했다.
- 병합 전, 로컬 PC에서 앱 REST 경로로 3km를 불렀을 때: 첫 페이지 1.6초(첫 연결 포함), 다음 페이지 0.25초.

**배포 후 실측(2026-11-05 01:50 UTC, PR #28 병합 직후).** 로컬 PC에서 배포본 `https://sangsang-retriever-mvp.vercel.app/api/found-items`를 curl로 불렀다(Vercel `icn1` → Supabase). 연결을 재사용했고 반경마다 2회씩 쟀다.

| 반경 | 바뀌기 전(1.2, 로컬→DB 직접, 전체) | 배포 후 첫 페이지(1회 / 2회) | 응답 크기 |
| --- | --- | ---: | ---: |
| 1km | 7.5초, 6.1MB | 0.79초 / 0.17초 | 34KB |
| 3km | 시간 초과(502) | 0.17초 / 0.12초 | 35KB |
| 5km | 32.3초, 28.1MB | 0.16초 / 0.12초 | 35KB |

- 3km 다음 페이지(커서): 0.43초 / 0.29초. 첫 페이지의 `total_count`는 35,449로 1.2의 건수와 같았다.
- 바뀌기 전 숫자는 Vercel을 거치지 않고 로컬에서 DB를 직접 부른 시간이다. 배포본은 여기에 함수 실행과 브라우저 전송(6~28MB)이 더해졌으므로, 실제 사용자가 느낀 시간은 이보다 길었다.
- 1km 첫 요청(0.79초)은 같은 묶음의 첫 API 호출이라 함수 준비 시간이 섞였을 수 있다.

### 1.4 검색어 검색 가속 실험 — PR #32 (보류)

> ⚠️ **운영에 반영되지 않은 값이다.** PR #32는 draft로 보류했고, 운영 마이그레이션도 적용하지 않았다. 검색 방식(⑥, 김성현)이 정해진 뒤 다시 본다(2026-11-05 결정).

검색어가 있으면 후보 전체를 받아 Python에서 퍼지 순위를 매기는 구조는 그대로 두고, 그 안의 두 단계를 각각 빠르게 했다. **순위·점수·결과 순서는 바뀌지 않는다.**

**후보 받기 — RPC 한 번(`found_items_candidates`).** 함수를 운영에 만들지 않고, 같은 SQL을 `explain analyze`로 잰 값이다.

| 반경 | 바뀌기 전 | DB 실행(첫 번 / 두 번째) | 받는 크기 | 왕복 |
| --- | --- | ---: | ---: | --- |
| 1km | 7.5초, 6.1MB | 2.5초 / 0.07초 | 4.2MB | 9번 → 1번 |
| 3km | 시간 초과(502) | 5.5초 / 0.94초 | 17.4MB | — → 1번 |
| 5km | 32.3초, 28.1MB | 6.6초 / 0.67초 | 19.5MB | 40번 → 1번 |

- 운영 3km에서 DB 정렬 + `jsonb` 방식은 0.84~4.3초였고, 정렬 없는 `json` 방식은 0.63~0.82초였다. 정렬이 메모리 한도를 넘어 디스크를 썼다.
- 로컬 Postgres 17.6(39,450건)에서는 `jsonb` + 정렬이 0.79초, `json` + 정렬 없음이 0.28초였다. 정렬 후 내용은 정답과 일치했고, 범위 밖·미매칭 섞임은 0건이었다.

**순위 계산 — 같은 점수를 내는 구현.**
- 편집거리를 `rapidfuzz`(C 구현)로 계산한다. 무작위 20만 쌍에서 기존 구현과 비트 단위로 같았다.
- 결과를 바꿀 수 없는 비교는 건너뛴다.

운영 후보로 로컬 PC에서 쟀다. 바뀌기 전은 1회, 바뀐 후는 3회 중앙값이다.

### 1.5 검색을 DB로 옮기는 실험 (2026-11-05, 실험 코드는 버림)

질문은 "검색 방식(PRD 4.5 퍼지 공식)은 그대로 두고, 계산만 Python에서 DB로 옮길 수 있는가"였다.
- 환경: 로컬 Postgres 17.6(`en_US.UTF-8`, ICU — 운영과 같은 설정)에 운영 후보 39,945건을 넣고 쟀다.
- 비교 대상: Python 시간은 같은 PC의 1.4 "바뀐 후" 구현이다.
- 결론: ①(검색을 DB로)은 ⑥이 검색 방식을 정한 뒤 진행한다(2026-11-05 결정).

**같은 공식을 SQL로 옮긴 버전.** 결과는 Python과 1건 단위로 같았다(1km 10개 + 3km 2개 조합, 반올림까지 포함).

| 버전 | 1km 시간(검색어 10개) | 비고 |
| --- | --- | --- |
| 그대로 옮김(정규화를 매번 SQL로) | 7.6초(백팩) ~ 163초(검정 가방) | Python은 1.8~3.5초 |
| 정규화를 미리 저장 + 결과를 바꾸지 않는 건너뛰기 | 0.34초(백팩) ~ 127초(검정 가방) | 3km: 지갑 20.6초, 휴대폰 3.7초 |

- 오래 걸리는 쪽은 글자 조각마다 SQL로 자카드를 계산하는 부분이었다.
- 최적화 버전의 3km 측정은 다른 작업과 시간이 겹쳤고, 나머지 조합은 측정을 멈췄다.

**하한선 — 창 만들기 + 편집거리만, 자카드 없음.**

| 조건 | 1km 카드 | 1km 검정 가방 | 5km 카드 | 5km 검정 가방 | 5km 아이퐁 | 5km 백팩 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 정규화를 매번 SQL로 | 2.7초 | 5.0초 | 13.6초 | 22.9초 | 13.2초 | 9.5초 |
| 정규화를 미리 저장 | 0.39초 | 0.73초 | 2.4초 | 2.5초 | 0.59초 | 0.32초 |

**정확한 사전 거르기 조건.**
- 조건: 검색어 글자 가운데 min(2, 검색어 길이)개 이상이 물품 텍스트에 있어야 한다. 이 조건을 못 넘는 물품은 지금 공식에서 점수가 임계값에 닿을 수 없다(공식에서 증명했다).
- 실측: 반경 3개 × 검색어 10개, 30개 조합에서 조건을 못 넘었는데 실제로는 결과에 드는 물품이 **0건**이었다. 남는 후보는 전체의 1.2~38.9%였다.
- 남은 후보만 순위 계산(Python, 3·5km)한 시간:

  | 검색어 | 시간 |
  | --- | ---: |
  | 백팩 | 0.03초 |
  | 휴대폰 | 0.16~0.25초 |
  | 모자 | 0.20~0.28초 |
  | 아이퐁 | 0.24~0.27초 |
  | 갤럭시 s24 | 0.35~0.41초 |
  | 지갑 | 0.57~0.65초 |
  | 카드 | 0.60~1.07초 |
  | 에어팟 프로 | 0.94~0.99초 |
  | 검정 가방 | 2.16초 |
  | 교통카드 | 3.88~5.49초 |

- 같은 조건을 검색할 때마다 SQL로 계산하면 4만 건(검색어 "검정 가방") 기준으로 아래와 같이 걸렸다. 4만 건 중 NFKC 정규화가 필요한 행은 15건뿐이었다.

  | 계산 방식 | 시간 | 결과가 정확한가 |
  | --- | ---: | --- |
  | 소문자 변환만 | 1.6초 | 아님 |
  | NFKC 정규화 + 소문자 변환 | 6.1초 | 정확 |
  | 필요할 때만 NFKC 정규화 | 3.1초 | 정확 |

**`pg_trgm` 한국어 동작.**
- 운영 DB: 1.6 버전을 쓸 수 있지만 설치하지 않았다. DB 로캘은 `en_US.UTF-8`, ICU다.
- 아래 값은 로컬에서 잰 것이다. 한글은 인식하지만 짧은 단어에서는 점수가 거칠다.

| 비교 | 값 |

| `similarity('핸드폰', '휴대폰')` | 0 |

### 1.6 남은 한계

- 운영 중인 검색어 검색은 여전히 1.2의 방식(후보 전체를 받아 Python에서 순위)이다. 3·5km는 p95 1.5초에 못 미친다.
- 목표에 닿으려면 DB 단계에서 후보를 줄이거나, DB 안에서 순위를 매겨야 한다(`pg_trgm`·임베딩 등).
  - 검색 결과가 바뀌는 방법이라 ⑥의 평가셋으로 TOP-5 포함률을 확인한 뒤 정한다.
  - 지금 공식을 유지하면 1.5의 "사전 거르기 + Python 점수" 방식이 맞다.
- 어느 쪽이든 DB 쪽 속도를 내려면 정규화한 텍스트를 미리 저장할 가능성이 크다. 이는 AGENTS.md 절대 규칙 3("정규화는 `normalized_search_text`에만")과 맞춰 봐야 한다.
