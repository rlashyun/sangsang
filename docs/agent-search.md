# 대화형 습득물 검색 에이전트

이 문서는 대화형 검색 MVP의 사용자 결정과 팀 합의가 필요한 API 계약을 관리한다. 기존 공간 우선 검색과 반경 정책은 [PRD 4.1·4.5](PRD.md)를 따른다.

현재는 [서버 검색 흐름](../src/retriever_lost_found/web/agent_search.py)과 [대화 처리](../src/retriever_lost_found/web/agent_conversation.py)를 테스트 대역으로 검증한 상태다. 단서가 부족하면 모델의 확인 질문을 사용하고, 장소가 바뀌면 다시 확인을 받으며, 물품 단서만 바뀌면 확정 장소에서 갱신한 검색어를 사용한다. 내부 대화 처리의 입력 상한은 메시지 1,000자, 모델에 넘기는 최근 문답은 최대 4개다.

대화 모델은 **GPT-6 Luna**로 선택했다. [모델 클라이언트](../src/retriever_lost_found/integrations/agent_model.py)는 OpenRouter Chat Completions API에 `openai/gpt-6-luna`로 구조화 출력을 요청한다. 초기 설정은 요청 타임아웃 5초, 출력 한도 400토큰, 추론 강도 `none`이다. 이 값들은 실측 전의 초기값이다.

[HTTP 라우터](../src/retriever_lost_found/web/agent_api.py)는 `create_app(..., agent_router=...)`로 연결한다. 라우터 생성 시 모델 테스트 대역 또는 서버에서 받은 OpenRouter 키와 장소·기관·물품 조회 어댑터를 전달한다. 대화, 장소 선택, 반경 변경, 다음 페이지, 취소, 종료 경로가 있다. 세션은 단일 서버 프로세스 메모리에 최대 128개, 유휴 30분을 초기값으로 사용한다. 로컬에서는 서버 전용 `OPENROUTER_API_KEY`를 설정하고 `uv run kakao-map --agent-search`로 활성화한다. 장소는 카카오, 기관은 Supabase, 물품은 현재 워크트리의 `/api/found-items`와 같은 검색 경로를 사용한다. 팀원이 확정할 하이브리드 검색은 물품 어댑터로 교체할 수 있다. 실시간 취소의 배포 환경 검증, 다중 인스턴스 세션, 새 검색 어댑터와 운영 앱 연결은 남아 있다.

확정 후 검색의 첫 결과가 0건이면 에이전트가 새 검색어를 한 번 제안할 수 있다. 일치 결과가 있으면 기억나는 특징을 덧붙일 수 있다고 안내한다. 최종 결과가 0건이면 모델이 필요한 추가 질문을 고른다. 추가 질문 생성에 실패해도 빈 결과를 반환한다. 최근 검색 안내와 질문은 다음 발화의 모델 문맥에 포함한다.

2026-11-17 KST에 실제 OpenRouter Luna로 두 차례 발화를 검증했다. 장소와 물품은 합성 데이터로 대체해 장소 확인, 같은 범위 재검색, 추천과 다음 페이지를 함께 확인했다. 이후 로컬 API에서 현재 설정된 Supabase를 읽기 전용으로 연결해 실제 기관 범위, 0건 후 재검색, 추천과 다음 페이지를 확인했다. 이 실행의 장소와 모델 응답은 테스트 대역을 사용했다. [측정 기록](measurements.md)에 검증 조건을 남겼다.

### 프런트 연결

대화는 분실 장소를 묻는 질문으로 시작한다. 조회할 장소 단서가 들어오면 물품 조건이 비어 있어도 후보를 표시하고 위치를 확정할 수 있다. 확정 뒤 물품 조건이 비어 있으면 물품을 묻고, 이미 조건이 있으면 검색한다. 서버는 모델에 현재 기다리는 답의 종류를 전달한다. 사용자가 기존 물품 조건을 부정하고 새 물품 단서를 주지 않으면 물품 조건과 이전 검색 결과·커서를 비우고, 확정 장소와 반경을 유지한 채 물품을 다시 묻는다.

[팀원 와이어프레임](https://claude.ai/artifact/1kcGtmbavraHuVhuMi21Tq)을 바탕으로 채팅 패널, 장소 후보·지도, 검색 조건 요약, 대화·결과 탭, 상위 추천 및 번호 페이지를 연결했다. 상세와 수령 안내는 기존 창을 재사용한다. 반경 안 기관 핀을 누르면 실제 실행한 검색어로 해당 기관의 결과를 다시 조회하고, 전체 기관 보기는 이전 전체 목록으로 돌아간다.

팀 시안의 후보 카드 즉시 확정은 PRD 4.3-A의 위치 미리보기와 명시적 선택 단계로 적용했다. 추천은 엔진 순서로 보여준다. 카드별 추천 이유와 기관별 일치 건수 배지는 후속 API 계약이 필요하다. 사진 첨부 검색과 외부 정보는 후속 범위다.

## 역할

- **A · 에이전트 및 검색 연결** — 대화 맥락과 검색 조건 관리, 다음 행동 선택, 장소·물품 검색 도구 연결, 실행 예산, 구조화 응답.
- **B · 채팅 및 지도** — 기존 지도를 유지하고 검색 플로팅창을 채팅 패널로 전환한다. 장소 선택, 진행 상태, 결과·오류·취소를 화면에 연결한다.
- **검색 담당자** — 하이브리드 검색의 후보 생성, 키워드·임베딩 결합, 순위, 페이지 계약을 맡는다. 에이전트는 새 하이브리드 검색을 기본 설정으로 호출한다.

## 확정한 사용자 흐름

1. 사용자가 “강남 하이디라오에서 검은 지갑을 잃어버렸어”라고 하면 에이전트가 장소와 물품 단서를 파악하고 카카오 장소 검색을 실행한다. 채팅 후보와 지도 핀에는 같은 후보 ID를 쓴다. **후보가 한 곳이어도 사용자 확인을 받는다.**
2. 사용자가 “강남역 쪽이야. 검은색이 아니라 갈색이었어”라고 답하면 장소 단서와 물품 조건을 함께 갱신한다. 사용자가 장소를 확정한 뒤에만 서버가 반경 내 기관 ID를 계산하고 해당 기관 범위에서 물품을 검색한다.
3. 기본 반경은 1km다. 기관을 정상적으로 조회했는데 0곳이면 1.5km, 2km 순서로 넓히고, 기관이 있는 단계 또는 2km에서 멈춘다. 물품 검색 0건, 조회 오류, 취소는 반경 자동 확장의 조건으로 사용하지 않는다. 수동 반경 변경은 장소와 제출 검색어를 이어받고 페이지를 초기화한다.
4. **첫 물품 검색이 정상 완료됐고 일치 결과가 0건일 때**, 에이전트는 검색어를 바꿔 **같은 장소와 반경에서 최대 한 번** 더 검색할 수 있다. 검색 실패와 취소는 0건으로 처리하지 않는다.
5. **전체 일치 목록**에는 마지막 검색 시도의 결과만 표시한다. 자동 재검색을 실행했다면 재검색의 순위와 커서를 사용한다. **추천 목록은 그 결과의 상위 3건**이며, 3건 미만이면 있는 만큼 표시한다. 새 단서를 보내면 이전 추천과 전체 목록을 비우고 새 응답으로 교체한다.
6. 사용자가 “카드지갑에 가까웠어”라고 새 단서를 주면 에이전트가 확정 장소와 유지할 물품 조건을 이어받고 검색어를 갱신한다. 새 검색의 페이지는 처음부터 시작한다.

## A·B 검토용 API 계약

아래 필드명과 요청 형식은 팀 검토용이다. 에이전트는 상태와 실제 조회 결과를 바탕으로 확인 질문, 조건 갱신, 검색, 재검색, 종료를 선택한다. 서버는 확정 장소, 반경, 상태 버전, 실행 한도를 검증한다.

| 항목 | 계약 초안 |
| --- | --- |
| 요청 | `message`, `select_place`, `change_radius`, `next_page`, `cancel`, `end`. 장소 선택 예시 `{"type":"select_place","session_id":"s1","revision":2,"candidate_id":"p3"}`. 서버는 현재 후보 목록과 상태 버전으로 선택을 검증한다. |
| 문장과 지도 데이터 | `message`는 표시 문장이다. `place_candidates`에는 후보 ID·이름·주소·위도·경도를 넣는다. `conditions`에는 확정 장소, 물품 단서, 반경, 기관 ID를 넣는다. 지도는 구조화된 좌표를 사용한다. |
| 검색 결과 | `search_attempts`에는 실행한 검색어를 순서대로 담는다. `recommended_item_ids`와 `matches`는 같은 결과를 참조한다. `matches`에는 정렬된 물품·기관 ID와 표시 필드, 전체 건수, `next_cursor`가 들어간다. 커서는 해당 검색 실행과 조건에 묶는다. |
| 진행 | 실제 도구 실행에 맞춰 `tool.started`, `tool.completed`, `tool.failed`를 보낸다. 이벤트에 `run_id`, `seq`를 붙이고 물품 조회에는 `attempt`를 추가한다. |
| 빈 결과·오류·취소 | 장소 후보 없음, 기관 0곳, 물품 일치 0건, 조회 실패, 취소를 구분한다. 오류에는 코드, 한국어 메시지, 재시도 가능 여부를 담는다. 취소 이후 새 호출을 시작하지 않고 이미 실행 중인 호출에서 늦게 돌아온 결과는 폐기한다. |

### 연동 예시

아래 예시의 ID와 좌표는 가상 값이다. 응답의 `message`는 표시용이고, 화면 상태는 `status`와 구조화된 필드로 판단한다.

**단일 장소 후보 확인 응답**

```json
{
  "session_id": "s1",
  "run_id": "r1",
  "revision": 1,
  "status": "awaiting_place_selection",
  "message": "지도에 표시한 지점이 맞나요?",
  "place_candidates": [
    {
      "candidate_id": "p3",
      "name": "하이디라오 예시 지점",
      "address": "서울 강남구 예시로 1",
      "latitude": 37.5,
      "longitude": 127.03
    }
  ],
  "conditions": {"place": null, "item_query": "갈색 지갑", "radius_m": null, "institution_ids": []},
  "search_attempts": [],
  "recommended_item_ids": [],
  "matches": null,
  "error": null
}
```

확인 요청은 `{"type":"select_place","session_id":"s1","revision":1,"candidate_id":"p3"}`이다. 첫 물품 조회가 정상 완료됐고 0건이면 서버는 재검색을 시작할 수 있다. 예시 이벤트는 전송 방식과 무관하게 아래 순서로 전달한다.

```json
[
  {"run_id":"r2","seq":1,"type":"tool.started","tool":"institutions"},
  {"run_id":"r2","seq":2,"type":"tool.completed","tool":"institutions"},
  {"run_id":"r2","seq":3,"type":"tool.started","tool":"found_items","attempt":1},
  {"run_id":"r2","seq":4,"type":"tool.completed","tool":"found_items","attempt":1},
  {"run_id":"r2","seq":5,"type":"tool.started","tool":"found_items","attempt":2},
  {"run_id":"r2","seq":6,"type":"tool.completed","tool":"found_items","attempt":2}
]
```

**재검색 성공 응답**

```json
{
  "session_id": "s1",
  "run_id": "r2",
  "revision": 2,
  "status": "results",
  "message": "확정한 장소 주변에서 비슷한 지갑을 찾았어요.",
  "place_candidates": [],
  "conditions": {
    "place": {"candidate_id":"p3","name":"하이디라오 예시 지점","latitude":37.5,"longitude":127.03},
    "item_query": "갈색 지갑",
    "radius_m": 1000,
    "institution_ids": [42]
  },
  "search_attempts": [
    {"attempt":1,"query":"갈색 지갑","status":"completed","match_count":0},
    {"attempt":2,"query":"갈색 지갑 브라운","status":"completed","match_count":2}
  ],
  "recommended_item_ids": [901, 902],
  "matches": {
    "items": [
      {"item_id":901,"institution_id":42,"item_name":"갈색 반지갑"},
      {"item_id":902,"institution_id":42,"item_name":"브라운 지갑"}
    ],
    "total_count": 2,
    "next_cursor": null
  },
  "error": null
}
```

다음 페이지가 있는 응답에서 프런트는 `next_cursor` 값을 그대로 보낸다. 예시 요청은 `{"type":"next_page","session_id":"s1","revision":2,"cursor":"example-cursor"}`이다. 조건 변경으로 버전이 달라지면 기존 커서는 만료된다.

| 제안 상태 | 응답과 후속 동작 |
| --- | --- |
| `awaiting_clarification` | 장소 또는 물품 정보가 부족하다. `matches: null`을 반환하고 질문한다. |
| `no_place_candidates` | 장소 후보가 없다. `matches: null`을 반환하고 다른 장소 표현을 요청한다. |
| `no_institutions` | 적용한 반경에 기관이 없다. `matches: null`을 반환하고 해당 반경을 표시한다. |
| `no_matches` | 물품 검색이 정상 완료됐고 0건이다. `matches: {"items":[],"total_count":0,"next_cursor":null}`을 반환한다. |
| `error` | 실패한 실행은 `matches: null`과 `error`를 반환한다. 예시는 `{"code":"search_timeout","message":"검색이 지연됐어요. 다시 시도해 주세요.","retryable":true}`이다. |
| `cancelled` | 취소된 `run_id`를 반환한다. 프런트는 해당 실행의 늦은 이벤트나 결과를 폐기한다. |

### 검색 담당자 검토용 호출 경계

- 입력 제안은 서버가 계산한 `institution_ids`, 실행할 `query`, 선택적 `cursor`다. 첫 조회와 같은 반경 재검색은 빈 커서로 시작한다. 다음 페이지는 결과를 반환한 시도의 질의와 커서를 이어받는다.
- 반환 제안은 엔진 순서의 `items`, 성공 시 일치 건수 `total_count`, 다음 페이지가 있으면 `next_cursor`다. 각 행은 물품 ID와 기관 ID를 제공한다. **정상 완료된 0건**을 오류나 취소와 구분할 수 있어야 한다.
- A는 장소·반경·실행 시도를 응답에 연결하고 추천 ID를 상위 3건에서 뽑는다. 엔진의 후보 생성과 순위 계산에는 기본 설정을 적용한다.

## 팀 검토용 기본안

아래는 첫 연결에 사용할 제안이다. 사용자가 확정한 검색 동작은 앞 절을 따르며, 이 절의 화면 배치와 전송 규약은 팀 리뷰에서 조정할 수 있다.

### B · 화면 동작

| 상태 | 채팅 패널 | 지도 |
| --- | --- | --- |
| 장소 확인 | 이름과 주소를 카드에 표시한다. 카드와 핀은 같은 번호와 후보 ID를 쓴다. 핀 클릭은 해당 카드를 강조하고, 카드의 “이 장소로 검색”으로 확정한다. 한 곳이어도 같은 방식으로 확인한다. | 현재 페이지의 후보 핀을 표시한다. 후보가 여러 곳이면 함께 보이도록 한 번 맞추고, 이후에는 사용자가 조작한 화면을 유지한다. |
| 장소 확정과 검색 | 실제 조회가 시작되면 “주변 보관기관 확인 중”, “습득물 검색 중”, 두 번째 검색이면 “다른 표현으로 한 번 더 검색 중”을 표시한다. 실행 중에는 취소를 제공한다. | 확정 장소와 적용 반경을 표시한다. 자동 확장이 실제로 발생한 경우에만 반경을 갱신한다. 결과를 기다리는 동안 지도 이동은 계속 가능하다. |
| 검색 성공 | 추천 상위 3건을 먼저 표시하고 아래의 “일치 결과 전체”에서 같은 결과의 번호 페이지를 제공한다. 추천 카드는 클릭하면 기존 물품 상세를 연다. | 반경 내 기관 핀을 유지한다. 결과 카드에서 기관을 선택하면 해당 기관 핀을 강조한다. 페이지 이동만으로 지도의 위치를 바꾸지 않는다. |
| 빈 결과·실패·취소 | 기관 없음, 일치 0건, 조회 실패, 취소를 각각 표시한다. 사용자에게 입력을 이어갈 수 있게 하고, 재시도 가능한 오류에는 다시 시도 동작을 표시한다. | 확정 장소와 적용 반경을 유지한다. 장소를 바꾸는 경우 새 후보를 표시한다. |

번호 페이지는 기존 PRD의 물품 페이지당 4건을 제안한다. 프런트는 받은 묶음을 버퍼에 담고, 필요한 페이지의 데이터가 부족할 때만 서버 커서를 이어서 요청한다. 검색 담당자가 정한 서버 묶음 크기와 화면의 4건 단위는 독립적으로 유지한다. 각 새 검색은 1페이지에서 시작한다.

### A·B · 요청과 이벤트

- `POST /api/search-chat/turns`는 자연어 입력, 장소 확정, 반경 변경, 대화 종료를 받는다. 공통 식별자는 클라이언트가 생성한 `request_id`, 응답에서 발급받은 `session_id`, 마지막 `revision`이다. 첫 메시지에서 세션 ID와 버전은 생략한다. 반경 변경은 `radius_m`에 1000·1500·2000 중 하나를 보낸다.
- 자연어 입력, 장소 확정, 반경 변경은 `application/x-ndjson` 응답을 제안한다. JSON 한 줄이 이벤트 하나다. 첫 줄 `run.started`는 `session_id`, `run_id`를 전달한다. 이후 실제 도구 이벤트와 서버의 `scope.updated`를 순번대로 보낸다. `scope.updated`는 적용 반경과 기관 ID를 전달하며, 자동 확장 시 이전 반경도 담는다. 마지막 줄 `run.finished`의 `response`에 앞 절의 최종 응답을 담는다. 대화 종료는 최종 상태 `ended`를 담은 일반 JSON을 반환한다.
- `POST /api/search-chat/pages`는 `session_id`, `revision`, `cursor`를 받고 `matches` 형식의 JSON을 반환한다. 페이지 조회는 LLM을 호출하지 않으며 상태 버전과 추천 목록을 유지한다. 커서는 불투명 문자열로 취급하고 검색 조건이 바뀌면 이전 커서를 무효화한다.
- `POST /api/search-chat/cancel`은 `session_id`와 `run_id`를 받고 취소 요청 수락 여부를 반환한다. 프런트는 취소한 실행의 늦은 이벤트를 즉시 무시한다. 서버는 같은 실행의 후속 도구 호출과 결과 반영을 중단한다. 이미 시작한 외부 조회에는 남은 시간 한도를 적용한다.
- 스트림을 열기 전 오류는 HTTP 상태와 `error` JSON으로 전달한다. 입력 오류는 400, 이전 버전·만료 커서·실행 충돌은 409, 만료 세션은 410을 제안한다. 스트림이 열린 뒤 조회 실패나 시간 초과는 `run.finished`의 `response.error`에 담는다. 종료 줄 없이 연결이 끊기면 프런트는 연결 오류로 표시한다.
- 세션당 실행은 한 건씩 처리한다. 같은 세션·`request_id`를 다시 받아도 모델이나 검색을 중복 실행하지 않는다. 브라우저가 갖는 버전·후보 ID·커서를 서버 상태와 대조한다. 서버 상태의 저장소와 만료 시간은 첫 연결에서 교체 가능한 테스트 대역으로 검증한다.

### 검색 담당자 · 연결 형식

앞 절의 입력과 반환 형태를 A 쪽 검색 어댑터 기준으로 사용한다. 엔진의 실제 필드명이 다르면 어댑터에서 매핑한다. 검색 어댑터가 반환하는 성공 응답 예시는 `{"items":[{"item_id":901,"institution_id":42,"item_name":"갈색 반지갑"}],"total_count":1,"next_cursor":null}`이다. 성공 0건은 `items: []`, `total_count: 0`, `next_cursor: null`로 전달한다. 시간 초과와 의존성 오류는 실패로 전달한다. 검색 엔진에서 별도의 순위 가중치나 전략을 받을 필요는 없다.

### 첫 연결 이후 확정할 값

- GPT-6 Luna의 초기 타임아웃·토큰 상한, 요청당 총 시간과 세션 비용·동시 실행 상한은 대표 흐름을 실행한 뒤 조정한다.
- 세션 저장소와 만료 시간, 실제 배포에서 스트림 전달과 취소가 동작하는지는 A·B 연동에서 검증한다.

## 구현과 검증 순서

1. A·B와 검색 담당자가 대표 흐름, API 예시, 빈 결과·오류·취소·페이지 계약을 확인한다.
2. LLM·카카오·기관·물품 검색 테스트 대역으로 첫 흐름을 연결한다. 장소 확정 전 물품 조회 0회, 반경 안의 정답 반환과 반경 밖 노출 0건, 첫 검색 0건에서 같은 반경 재검색 최대 1회, 첫 검색 성공 1건 이상·오류·취소에서 자동 재검색 0회를 검증한다.
3. LLM을 연결해 확인 질문, 한 발화에 여러 단서 정정, 결과 확인과 종료 판단을 검증한다. 실제 도구 호출과 진행 이벤트, 추천 ID와 전체 목록 순서, 재검색 후 커서를 대조한다. 동일 기관 범위·검색어의 단일 검색 결과를 하이브리드 엔진 단독 호출과 비교한다.
4. B와 모바일·데스크톱 대표 흐름을 검증한다. 동일한 데이터와 평가 사례로 장소 확인 성공률, 상위 5건 품질, 첫 결과까지 p50·p95, 완료 검색당 비용을 비교한다. 자동 테스트는 실제 외부 API를 호출하지 않는다. 실측 결과는 [측정 기록](measurements.md)에 남긴다.

검색 결과 아래의 ‘당근에서 찾아보기’는 확정한 장소명과 최신 물품 검색어를 넣어 당근 동네생활의 공개 웹 검색을 새 탭으로 연다. 최신 물품 검색어에 색상 등 물품 단서가 반영되어 있으면 함께 전달한다. 지역 선택은 열린 당근 화면에서 한다. 게시글 자동 조회·분류와 이미지 임베딩, 외부 웹 검색 자동화는 후속 검토 범위다. 검색 전략 선택은 하이브리드 기본 설정이 반복해서 놓치는 사례가 확인된 뒤 비교 실험으로 검토한다.
