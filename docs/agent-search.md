# 대화형 습득물 검색 에이전트

이 문서는 대화형 검색 MVP의 사용자 결정과 팀 합의가 필요한 API 계약을 관리한다. 기존 공간 우선 검색과 반경 정책은 [PRD 4.1·4.5](PRD.md)를 따른다.

현재는 [서버 검색 흐름](../src/retriever_lost_found/web/agent_search.py)과 [대화 처리](../src/retriever_lost_found/web/agent_conversation.py)를 테스트 대역으로 검증한 상태다. 단서가 부족하면 모델의 확인 질문을 사용하고, 장소가 바뀌면 다시 확인을 받으며, 물품 단서만 바뀌면 확정 장소에서 갱신한 검색어를 사용한다. 내부 대화 처리의 입력 상한은 메시지 1,000자, 모델에 넘기는 최근 문답은 최대 4개다.

대화 모델은 **GPT-6 Luna**로 선택했다. [모델 클라이언트](../src/retriever_lost_found/integrations/agent_model.py)는 OpenRouter Chat Completions API에 `openai/gpt-6-luna`로 구조화 출력을 요청한다. 초기 설정은 요청 타임아웃 5초, 출력 한도 400토큰, 추론 강도 `none`이다. 이 값들은 실측 전의 초기값이다.

[HTTP 라우터](../src/retriever_lost_found/web/agent_api.py)는 `create_app(..., agent_router=...)`로 연결한다. 라우터 생성 시 모델 테스트 대역 또는 서버에서 받은 OpenRouter 키와 장소·기관·물품 조회 어댑터를 전달한다. 대화, 장소 선택, 반경 변경, 다음 페이지, 취소, 종료 경로가 있다. 세션은 Supabase 공용 저장소에 최대 128개, 유휴 30분으로 보관한다(2026-11-20 사용자 결정). 아래 복구 계약과 배포 순서를 따른다. 테스트 대역에만 메모리 저장소를 주입한다. 로컬에서는 서버 전용 `OPENROUTER_API_KEY`를 설정하고 `uv run kakao-map --agent-search`로 활성화한다. 장소는 카카오, 기관은 Supabase, 물품은 현재 워크트리의 `/api/found-items`와 같은 검색 경로를 사용한다. 팀원이 확정할 하이브리드 검색은 물품 어댑터로 교체할 수 있다. 2026-11-20 PR #66을 운영에 배포했고 대화 이어가기·완료/취소 응답 재사용·실행 중 취소·실제 만료 삭제를 확인했다. 실제 인스턴스를 강제 분리한 검증과 단일 요청 성능 목표 달성 여부는 별개다. 상세 조건은 측정 기록을 따른다.

확정 후 검색의 첫 결과가 0건이면 에이전트가 새 검색어를 한 번 제안할 수 있다. 일치 결과가 있으면 기억나는 특징을 덧붙일 수 있다고 안내한다. 2026-11-21 사용자 결정: 물품 종류가 확인되면 색상·브랜드·특징을 먼저 요구하지 않고 현재 조건으로 검색한다. 최종 결과가 0건이면 추가 질문을 생성하지 않고 빈 결과를 안내한다. 장소나 물품 자체를 모르면 확인 질문을 유지한다. 최근 검색 안내는 다음 발화의 모델 문맥에 포함한다.

2026-11-17 KST에 실제 OpenRouter Luna로 두 차례 발화를 검증했다. 장소와 물품은 합성 데이터로 대체해 장소 확인, 같은 범위 재검색, 추천과 다음 페이지를 함께 확인했다. 이후 로컬 API에서 현재 설정된 Supabase를 읽기 전용으로 연결해 실제 기관 범위, 0건 후 재검색, 추천과 다음 페이지를 확인했다. 이 실행의 장소와 모델 응답은 테스트 대역을 사용했다. [측정 기록](measurements.md)에 검증 조건을 남겼다.

### 대화 조건 갱신과 조회

물품 종류·색상·브랜드·기타 특징을 세션에 각각 저장한다. 모델은 필드별 변경을 반환한다. `null`은 유지, 빈 문자열은 삭제다. 검색에는 물품 종류부터 최대 30자로 조합한 검색어를 사용하고, 길이 제한에 걸린 단서도 세션에는 보존한다.

장소 변경 버튼을 누른 후 보내는 메시지는 `changing_place`로 표시한다. 장소 후보를 채팅으로 지목하면 지도에서 해당 후보를 미리 보고, 위치 선택 버튼을 눌러 확정한다.

같은 검색어로 장소를 다시 선택해도 기존 반경과 기관 범위를 초기화한다. 장소를 좁히는 동안 물품 검색어가 바뀌면 `awaiting_place_clarification`을 반환해 물품 정정을 저장하고 이전 결과를 지운 뒤 장소 입력을 이어간다. 마지막 조회에서 재검색 표현을 사용했다면 조건 답변에서 입력 조건으로 만든 검색어와 실제 조회 검색어를 함께 표시한다.

조건 확인, 일반 답변, 물품 보관처 안내는 `answered`를 반환한다. 이 응답은 세션 버전만 갱신하며 기존 결과와 페이지 커서를 유지한다. 장소 미리보기는 같은 응답에 `highlight_candidate_id`를 포함한다. 물품 상세를 물으면 브라우저가 `visible_item_ids`로 현재 페이지의 순서를 전달하고, 서버는 해당 세션의 반경으로 한정해 실제 물품과 보관기관을 확인한다. 자연어 반경 변경은 1·1.5·2km 중 적용할 값을 서버가 확인한 뒤 기존 검색을 다시 실행한다.

### 프런트 연결

2026-11-22 장소 제거 후속 승인: 상단 장소별 변경 버튼을 없애고 오른쪽에 이름을 읽을 수 있는 × 제거 버튼만 둔다. 제거 성공 응답에서 해당 좌표가 빠진 것을 확인한 뒤 “‘장소명’ 장소를 제거했어요.”를 채팅에 표시하며 오류·취소에서는 성공 안내를 하지 않는다. 모델에는 최신 확정 개수·남은 추가 가능 개수와 제거 이력을 전달해 과거 3곳 목록을 현재 개수로 오인하지 않게 한다. 제거 후 다시 3곳까지 자연어로 추가할 수 있고, 3곳에 다시 도달하면 최대 개수 안내를 한 번 표시한다.

2026-11-22 장소 개수 안내: 세 번째 장소를 확정해 선택 완료 목록이 3곳이 되면 “장소는 최대 3곳까지 선택할 수 있어요.”를 확정 장소 카드 다음, 물품 질문/결과 안내 전에 한 번 표시한다. 이후 같은 3곳에서 물품을 정정하거나 다시 검색할 때는 반복하지 않는다. 서버의 기존 개수 제한은 유지하고 추가 LLM 호출은 만들지 않는다.

2026-11-22 사용자 결정: 상단 선택 장소 요약에서 “장소 추가” 버튼을 제거한다. 추가 장소는 대화에서 말하는 흐름을 사용하며, 기존 자연어 장소 추가·후보 확인·최대 3곳 제한은 유지한다. 장소별 변경·제거와 선택 중 건너뛰기·취소 버튼은 유지한다.

2026-11-21 이용안내 문구 정리: 사진 첨부·붙여넣기 설명은 물건 특징을 알려주는 3번 단계에 합치고, 이용안내의 별도 사진 안내와 “사진 검색은 아직 준비 중” 문구는 제거한다. 당근 안내는 버튼 선택→장소·물건 검색어 자동 입력의 1·2번 순서로 표시한다. 실제 사진 처리 범위는 기존 첨부 UI 승인 범위를 유지한다.

2026-11-21 이용안내 당근 설명 추가: 비슷한 물건 알림 아래에 “당근에서 검색하기”를 배치한다. 대화창의 “당근에서 찾아보기”를 누르면 선택 장소와 물건이 검색어에 자동 입력된 당근 검색 화면이 새 탭으로 열린다고 안내한다. 안내 카드 사이의 행 높이를 강제 공유하지 않아 알림 단계의 세로 간격이 과도하게 벌어지지 않도록 한다.

2026-11-21 이용안내 갱신: 장소 명시적 선택, 물품 특징 예시, 정상 0건의 1→1.5→2km 자동 탐색, 장소 선택 후 사진 첨부·붙여넣기와 사진 검색 준비 상태, 검색 후 대화창 선택지의 알림 버튼 위치를 반영한다. 물품 범위는 “경찰청에 등록된 다양한 습득물을 검색할 수 있어요”로 안내한다.

2026-11-21 검색 후속 안내 타이밍 수정: 새 검색·재시도·장소 변경을 시작하면 이전 후속 안내와 표시 타이머를 즉시 해제한다. 정상 검색 완료(results/no_matches)에서만 후속 안내를 예약한다. 성공 시 “검색을 마쳤어요. 결과 목록에서 찾으시는 물건이 있는지 확인해 보세요.”를 먼저 표시하고 답변 표시 종료 700ms 뒤에 안내·선택지를 보여준다. 일반 답변·사진 단독 첨부·오류·취소에서는 이전 결과가 남아 있어도 안내를 다시 표시하지 않는다.

2026-11-21 사진 첨부 단계 제한: 장소 후보를 사용자 선택으로 확정한 뒤의 물품 검색 단계에서만 파일 선택·이미지 붙여넣기를 허용한다. 확정 전 카메라 버튼과 이미지 붙여넣기는 “사진을 첨부하려면 먼저 잃어버린 장소를 입력하고 선택해 주세요.”라는 채팅 안내를 표시하며 파일 창·미리보기·전송을 시작하지 않는다. 일반 텍스트 붙여넣기는 유지한다. 장소 변경 중에도 동일하게 제한하며 기존 첨부 초안은 새 장소 확정까지 숨기고 장소 입력 텍스트에 섞어 보내지 않는다.

2026-11-21 사진 첨부 UI 승인: 파일 선택과 입력창의 이미지 붙여넣기, 전송 전 미리보기·삭제, 사진 단독 또는 텍스트와 함께 채팅에 표시하는 기능을 제공한다. 임시 Object URL을 사용하며 전송 전 삭제·화면 종료 시 해제한다. 서버·LLM·DB·스토리지로 사진이나 파일명을 보내지 않고, 텍스트를 함께 쓰면 텍스트만 기존 API에 전달한다. 새로고침으로 사진이 사라진다. JPG·PNG·WebP·GIF, 한 번에 최대 3장·장당 10MB를 지원하고 손상/미지원 파일은 안내한다. 전송 전후 사진 검색이 준비 중임을 표시한다. 실제 이미지 검색·업로드·영구 저장은 포함하지 않는다.

2026-11-21 단일 페이지 표기 수정: “1페이지” 문구 대신 여러 페이지일 때와 같은 숫자 버튼 “1”만 표시한다. 고정된 하단 영역과 현재 번호 강조는 유지하며 접근성 이름은 “1페이지”로 제공한다.

2026-11-21 결과 범위 제목 간소화: 왼쪽 조건 요약과 중복되는 장소·반경 줄을 결과 패널에서 제거한다. 고정 범위 줄에는 “전체 보관기관” 또는 선택한 기관명만 한 줄로 표시한다. 선택 기관의 전체 기관 복귀 버튼은 유지한다.

2026-11-21 고정 범위·페이지 후속 사용자 승인: 결과 제목 아래 고정 줄에 전체 보관기관 또는 선택 기관명과 선택 장소·반경을 표시한다. 선택 기관에서는 실제 해당 기관의 건수를 표시하고 같은 줄 오른쪽에 전체 기관 복귀를 둔다. 하단 구분선·48px 페이지 영역은 항상 유지하며 한 페이지는 “1페이지”만 표시한다. 마지막 페이지나 소수 결과는 84px 행으로 위에서부터 나열해 과도하게 늘리지 않는다.

2026-11-21 정상 물품 0건 자동 확장 승인: 1→1.5→2km 순서로 검색하고 결과가 나오는 즉시 멈춘다. 각 확장 원인과 이전/다음 반경을 스트림으로 보내 브라우저에 안내 말풍선을 표시한다. 같은 검색 실행 전체에서 검색어 재작성은 최대 한 번이며, 오류·취소에는 추가 확장을 시작하지 않는다. 최종 범위·커서·검색어를 세션에 유지한다. 본문의 과거 ‘물품 0건으로 확장하지 않음’ 설명은 이 결정으로 대체한다.

2026-11-21 채팅 스크롤 사용자 승인: 스크롤바를 패널 오른쪽 끝 가까이 배치하고 얇고 옅은 회색으로 표시한다. 실제 스크롤 시에만 나타나며 마지막 이동 후 700ms에 숨긴다. 스크롤바 자리는 유지해 나타날 때 내용이 좌우로 흔들리지 않게 하고 상하 화살표·트랙 배경은 제거한다. 모바일도 같은 원칙을 적용하고 화면을 떠날 때 타이머를 정리한다.

2026-11-21 결과 세로 비율 후속 조정: 결과 목록의 아래 정렬용 빈 공간을 제거하고 제목 바로 아래부터 채운다. 페이지 영역을 제외한 높이는 현재 물품 행에 고르게 배분하며 사진·글씨 크기와 화면별 표시 개수는 유지한다. 채팅의 아래 정렬은 유지한다.

## 확정한 사용자 흐름

1. 사용자가 “강남 하이디라오에서 검은 지갑을 잃어버렸어”라고 하면 에이전트가 장소와 물품 단서를 파악하고 카카오 장소 검색을 실행한다. 채팅 후보와 지도 핀에는 같은 후보 ID를 쓴다. **후보가 한 곳이어도 사용자 확인을 받는다.**
2. 사용자가 “강남역 쪽이야. 검은색이 아니라 갈색이었어”라고 답하면 장소 단서와 물품 조건을 함께 갱신한다. 사용자가 장소를 확정한 뒤에만 서버가 반경 내 기관 ID를 계산하고 해당 기관 범위에서 물품을 검색한다.
3. 기본 반경은 1km다. 기관이 없거나 물품 검색이 정상적으로 0건이면 1.5km, 2km 순서로 넓힌다(2026-11-21 사용자 변경). 일치 물품이 있는 단계 또는 2km에서 멈춘다. 조회 오류·취소는 자동 확장의 조건이 아니다. 물품 0건에 의한 확장은 “1km 안에 일치하는 물건이 없어 1.5km로 넓혀 찾고 있어요.”처럼 안내하고, 최종 범위·커서·기관 목록·알림 조건을 유지한다. 수동 반경 변경에서도 0건이면 최대 2km까지 같은 방식으로 탐색한다.
4. **첫 물품 검색이 정상 완료됐고 일치 결과가 0건일 때**, 에이전트는 검색어를 바꿔 **같은 장소와 반경에서 최대 한 번** 더 검색할 수 있다. 이 재작성 한도는 자동 확장을 포함한 전체 실행에서 한 번이며, 그 뒤에도 0건이면 다음 반경에서 탐색한다. 검색 실패와 취소는 0건으로 처리하지 않는다.
5. **전체 일치 목록**에는 마지막 검색 시도의 결과만 표시한다. 자동 재검색을 실행했다면 재검색의 순위와 커서를 사용한다. **추천 목록은 그 결과의 상위 3건**이며, 3건 미만이면 있는 만큼 표시한다. 새 단서를 보내면 이전 추천과 전체 목록을 비우고 새 응답으로 교체한다.
6. 사용자가 “카드지갑에 가까웠어”라고 새 단서를 주면 에이전트가 확정 장소와 유지할 물품 조건을 이어받고 검색어를 갱신한다. 새 검색의 페이지는 처음부터 시작한다.

## A·B 검토용 API 계약

아래 필드명과 요청 형식은 팀 검토용이다. 에이전트는 상태와 실제 조회 결과를 바탕으로 확인 질문, 조건 갱신, 검색, 재검색, 종료를 선택한다. 서버는 확정 장소, 반경, 상태 버전, 실행 한도를 검증한다.

| 항목 | 계약 초안 |
| --- | --- |
| 요청 | `message`, `select_place`, `change_radius`, `next_page`, `cancel`, `end`. 장소 선택 예시 `{"type":"select_place","session_id":"s1","revision":2,"candidate_id":"p3"}`. 서버는 현재 후보 목록과 상태 버전으로 선택을 검증한다. |
| 문장과 지도 데이터 | `message`는 표시 문장이다. `place_candidates`에는 후보 ID·이름·주소·위도·경도를 넣는다. `conditions`에는 확정 장소, 물품 단서, 반경, 기관 ID를 넣는다. 지도는 구조화된 좌표를 사용한다. |
| 검색 결과 | `search_attempts`에는 실행한 검색어를 순서대로 담는다. `recommended_item_ids`와 `matches`는 같은 결과를 참조한다. `matches`에는 정렬된 물품·기관 ID와 표시 필드, 전체 건수, `next_cursor`가 들어간다. 커서는 해당 검색 실행과 조건에 묶는다. |

| 빈 결과·오류·취소 | 장소 후보 없음, 기관 0곳, 물품 일치 0건, 조회 실패, 취소를 구분한다. 오류에는 코드, 한국어 메시지, 재시도 가능 여부를 담는다. 취소 이후 새 호출을 시작하지 않고 이미 실행 중인 호출에서 늦게 돌아온 결과는 폐기한다. |

### 연동 예시

아래 예시의 ID와 좌표는 가상 값이다. 응답의 `message`는 표시용이고, 화면 상태는 `status`와 구조화된 필드로 판단한다.

**단일 장소 후보 확인 응답**

```json
{
  "session_id": "s1",
  "run_id": "r1",
  "revision": 1,
  "status": "awaiting_place_selection",
  "message": "지도에 표시한 지점이 맞나요?",
  "place_candidates": [
    {
      "candidate_id": "p3",
      "name": "하이디라오 예시 지점",
      "address": "서울 강남구 예시로 1",
      "latitude": 37.5,
      "longitude": 127.03
    }
  ],
  "conditions": {"place": null, "item_query": "갈색 지갑", "radius_m": null, "institution_ids": []},
  "search_attempts": [],
  "recommended_item_ids": [],
  "matches": null,
  "error": null
}
```

확인 요청은 `{"type":"select_place","session_id":"s1","revision":1,"candidate_id":"p3"}`이다. 첫 물품 조회가 정상 완료됐고 0건이면 서버는 재검색을 시작할 수 있다. 예시 이벤트는 전송 방식과 무관하게 아래 순서로 전달한다.

```json
[
  {"run_id":"r2","seq":1,"type":"tool.started","tool":"institutions"},
  {"run_id":"r2","seq":2,"type":"tool.completed","tool":"institutions"},
  {"run_id":"r2","seq":3,"type":"tool.started","tool":"found_items","attempt":1},
  {"run_id":"r2","seq":4,"type":"tool.completed","tool":"found_items","attempt":1},
  {"run_id":"r2","seq":5,"type":"tool.started","tool":"found_items","attempt":2},
  {"run_id":"r2","seq":6,"type":"tool.completed","tool":"found_items","attempt":2}
]
```

**재검색 성공 응답**

```json
{
  "session_id": "s1",
  "run_id": "r2",
  "revision": 2,
  "status": "results",
  "message": "확정한 장소 주변에서 비슷한 지갑을 찾았어요.",
  "place_candidates": [],
  "conditions": {
    "place": {"candidate_id":"p3","name":"하이디라오 예시 지점","latitude":37.5,"longitude":127.03},
    "item_query": "갈색 지갑",
    "radius_m": 1000,
    "institution_ids": [42]
  },
  "search_attempts": [
    {"attempt":1,"query":"갈색 지갑","status":"completed","match_count":0},
    {"attempt":2,"query":"갈색 지갑 브라운","status":"completed","match_count":2}
  ],
  "recommended_item_ids": [901, 902],
  "matches": {
    "items": [
      {"item_id":901,"institution_id":42,"item_name":"갈색 반지갑"},
      {"item_id":902,"institution_id":42,"item_name":"브라운 지갑"}
    ],
    "total_count": 2,
    "next_cursor": null
  },
  "error": null
}
```

다음 페이지가 있는 응답에서 프런트는 `next_cursor` 값을 그대로 보낸다. 예시 요청은 `{"type":"next_page","session_id":"s1","revision":2,"cursor":"example-cursor"}`이다. 조건 변경으로 버전이 달라지면 기존 커서는 만료된다.

| 제안 상태 | 응답과 후속 동작 |
| --- | --- |
| `awaiting_clarification` | 장소 또는 물품 정보가 부족하다. `matches: null`을 반환하고 질문한다. |
| `no_place_candidates` | 장소 후보가 없다. `matches: null`을 반환하고 다른 장소 표현을 요청한다. |
| `no_institutions` | 적용한 반경에 기관이 없다. `matches: null`을 반환하고 해당 반경을 표시한다. |
| `no_matches` | 물품 검색이 정상 완료됐고 0건이다. `matches: {"items":[],"total_count":0,"next_cursor":null}`을 반환한다. |
| `error` | 실패한 실행은 `matches: null`과 `error`를 반환한다. 예시는 `{"code":"search_timeout","message":"검색이 지연됐어요. 다시 시도해 주세요.","retryable":true}`이다. |
| `cancelled` | 취소된 `run_id`를 반환한다. 프런트는 해당 실행의 늦은 이벤트나 결과를 폐기한다. |

### 검색 담당자 검토용 호출 경계

- 입력 제안은 서버가 계산한 `institution_ids`, 실행할 `query`, 선택적 `cursor`다. 첫 조회와 같은 반경 재검색은 빈 커서로 시작한다. 다음 페이지는 결과를 반환한 시도의 질의와 커서를 이어받는다.
- 반환 제안은 엔진 순서의 `items`, 성공 시 일치 건수 `total_count`, 다음 페이지가 있으면 `next_cursor`다. 각 행은 물품 ID와 기관 ID를 제공한다. **정상 완료된 0건**을 오류나 취소와 구분할 수 있어야 한다.
- A는 장소·반경·실행 시도를 응답에 연결하고 추천 ID를 상위 3건에서 뽑는다. 엔진의 후보 생성과 순위 계산에는 기본 설정을 적용한다.

## 팀 검토용 기본안

아래는 첫 연결에 사용할 제안이다. 사용자가 확정한 검색 동작은 앞 절을 따르며, 이 절의 화면 배치와 전송 규약은 팀 리뷰에서 조정할 수 있다.

### B · 화면 동작

| 상태 | 채팅 패널 | 지도 |
| --- | --- | --- |
| 장소 확인 | 이름과 주소를 카드에 표시한다. 카드와 핀은 같은 번호와 후보 ID를 쓴다. 핀 클릭은 해당 카드를 강조하고, 카드의 “이 장소로 검색”으로 확정한다. 한 곳이어도 같은 방식으로 확인한다. | 현재 페이지의 후보 핀을 표시한다. 후보가 여러 곳이면 함께 보이도록 한 번 맞추고, 이후에는 사용자가 조작한 화면을 유지한다. |
| 장소 확정과 검색 | 실제 조회가 시작되면 “주변 보관기관 확인 중”, “습득물 검색 중”, 두 번째 검색이면 “다른 표현으로 한 번 더 검색 중”을 표시한다. 실행 중에는 취소를 제공한다. | 확정 장소와 적용 반경을 표시한다. 자동 확장이 실제로 발생한 경우에만 반경을 갱신한다. 결과를 기다리는 동안 지도 이동은 계속 가능하다. |
| 검색 성공 | 추천 상위 3건을 먼저 표시하고 아래의 “일치 결과 전체”에서 같은 결과의 번호 페이지를 제공한다. 추천 카드는 클릭하면 기존 물품 상세를 연다. | 반경 내 기관 핀을 유지한다. 결과 카드에서 기관을 선택하면 해당 기관 핀을 강조한다. 페이지 이동만으로 지도의 위치를 바꾸지 않는다. |
| 빈 결과·실패·취소 | 기관 없음, 일치 0건, 조회 실패, 취소를 각각 표시한다. 사용자에게 입력을 이어갈 수 있게 하고, 재시도 가능한 오류에는 다시 시도 동작을 표시한다. | 확정 장소와 적용 반경을 유지한다. 장소를 바꾸는 경우 새 후보를 표시한다. |

번호 페이지는 기존 PRD의 물품 페이지당 4건을 제안한다. 프런트는 받은 묶음을 버퍼에 담고, 필요한 페이지의 데이터가 부족할 때만 서버 커서를 이어서 요청한다. 검색 담당자가 정한 서버 묶음 크기와 화면의 4건 단위는 독립적으로 유지한다. 각 새 검색은 1페이지에서 시작한다.

### A·B · 요청과 이벤트

- `POST /api/search-chat/turns`는 자연어 입력, 장소 확정, 반경 변경, 대화 종료를 받는다. 공통 식별자는 클라이언트가 생성한 `request_id`, 응답에서 발급받은 `session_id`, 마지막 `revision`이다. 첫 메시지에서 세션 ID와 버전은 생략한다. 반경 변경은 `radius_m`에 1000·1500·2000 중 하나를 보낸다.
- 자연어 입력, 장소 확정, 반경 변경은 `application/x-ndjson` 응답을 제안한다. JSON 한 줄이 이벤트 하나다. 첫 줄 `run.started`는 `session_id`, `run_id`를 전달한다. 이후 실제 도구 이벤트와 서버의 `scope.updated`를 순번대로 보낸다. `scope.updated`는 적용 반경과 기관 ID를 전달하며, 자동 확장 시 이전 반경도 담는다. 마지막 줄 `run.finished`의 `response`에 앞 절의 최종 응답을 담는다. 대화 종료는 최종 상태 `ended`를 담은 일반 JSON을 반환한다.
- `POST /api/search-chat/pages`는 `session_id`, `revision`, `cursor`를 받고 `matches` 형식의 JSON을 반환한다. 페이지 조회는 LLM을 호출하지 않으며 상태 버전과 추천 목록을 유지한다. 커서는 불투명 문자열로 취급하고 검색 조건이 바뀌면 이전 커서를 무효화한다.
- `POST /api/search-chat/cancel`은 `session_id`와 `run_id`를 받고 취소 요청 수락 여부를 반환한다. 프런트는 취소한 실행의 늦은 이벤트를 즉시 무시한다. 서버는 같은 실행의 후속 도구 호출과 결과 반영을 중단한다. 이미 시작한 외부 조회에는 남은 시간 한도를 적용한다.
- 스트림을 열기 전 오류는 HTTP 상태와 `error` JSON으로 전달한다. 입력 오류는 400, 이전 버전·만료 커서·실행 충돌은 409, 만료 세션은 410을 제안한다. 스트림이 열린 뒤 조회 실패나 시간 초과는 `run.finished`의 `response.error`에 담는다. 종료 줄 없이 연결이 끊기면 프런트는 연결 오류로 표시한다.
- 세션당 실행은 한 건씩 처리한다. 같은 세션·`request_id`를 다시 받아도 모델이나 검색을 중복 실행하지 않는다. 브라우저가 갖는 버전·후보 ID·커서를 서버 상태와 대조한다. 서버 상태의 저장소와 만료 시간은 첫 연결에서 교체 가능한 테스트 대역으로 검증한다.

### 검색 담당자 · 연결 형식

앞 절의 입력과 반환 형태를 A 쪽 검색 어댑터 기준으로 사용한다. 엔진의 실제 필드명이 다르면 어댑터에서 매핑한다. 검색 어댑터가 반환하는 성공 응답 예시는 `{"items":[{"item_id":901,"institution_id":42,"item_name":"갈색 반지갑"}],"total_count":1,"next_cursor":null}`이다. 성공 0건은 `items: []`, `total_count: 0`, `next_cursor: null`로 전달한다. 시간 초과와 의존성 오류는 실패로 전달한다. 검색 엔진에서 별도의 순위 가중치나 전략을 받을 필요는 없다.

- 세션 저장소와 만료 시간은 2026-11-20 Supabase·유휴 30분으로 확정했다. 2026-11-20 운영 스트림·취소·만료 삭제 확인은 측정 기록에 남겼다.

## 구현과 검증 순서

1. A·B와 검색 담당자가 대표 흐름, API 예시, 빈 결과·오류·취소·페이지 계약을 확인한다.
2. LLM·카카오·기관·물품 검색 테스트 대역으로 첫 흐름을 연결한다. 장소 확정 전 물품 조회 0회, 반경 안의 정답 반환과 반경 밖 노출 0건, 첫 검색 0건에서 같은 반경 재검색 최대 1회, 첫 검색 성공 1건 이상·오류·취소에서 자동 재검색 0회를 검증한다.
3. LLM을 연결해 확인 질문, 한 발화에 여러 단서 정정, 결과 확인과 종료 판단을 검증한다. 실제 도구 호출과 진행 이벤트, 추천 ID와 전체 목록 순서, 재검색 후 커서를 대조한다. 동일 기관 범위·검색어의 단일 검색 결과를 하이브리드 엔진 단독 호출과 비교한다.
4. B와 모바일·데스크톱 대표 흐름을 검증한다. 동일한 데이터와 평가 사례로 장소 확인 성공률, 상위 5건 품질, 첫 결과까지 p50·p95, 완료 검색당 비용을 비교한다. 자동 테스트는 실제 외부 API를 호출하지 않는다. 실측 결과는 [측정 기록](measurements.md)에 남긴다.

검색 결과 아래의 ‘당근에서 찾아보기’는 확정한 장소명과 최신 물품 검색어를 넣어 당근 동네생활의 공개 웹 검색을 새 탭으로 연다. 최신 물품 검색어에 색상 등 물품 단서가 반영되어 있으면 함께 전달한다. 지역 선택은 열린 당근 화면에서 한다. 게시글 자동 조회·분류와 이미지 임베딩, 외부 웹 검색 자동화는 후속 검토 범위다. 검색 전략 선택은 하이브리드 기본 설정이 반복해서 놓치는 사례가 확인된 뒤 비교 실험으로 검토한다.

## 기존 지도 UI 연결

대화 화면에도 PRD 4.2~4.4의 기존 지도 스타일을 적용한다. 현재 페이지의 장소 후보는 번호 핀으로, 미리보기·확정 위치는 흰색 핀과 주소 정보창으로 표시한다. 확정한 위치에는 파란 반경을 그리고, 연계기관과 경찰관서를 파란 핀과 황금색 핀으로 구분한다. 기관 핀은 먼저 표시하고 보관 물품 수가 도착하면 핀 정보에 표시한다. 서버가 적용한 반경과 기관 범위에 맞춰 지도를 갱신하며 반경 변경 버튼은 검색 결과 패널 하단에 둔다. 결과 패널을 접었거나 빈 결과로 패널이 닫혀 있으면 대화 패널 하단에서 반경을 변경할 수 있다.

## 실패 복구와 공용 세션 (2026-11-20)

사용자 승인 범위는 재시도·상태 일관성과 구조화 로그를 먼저 고치고 공용 세션으로 전환하는 것이다. 기관 집계 최적화와 검색 순위 변경은 이 수정의 선행 조건이 아니므로 제외한다. 당시 장소·물품 조회 오류의 특정 공급자 원인은 확인하지 못했다.

- 브라우저의 ‘다시 시도’는 원래 `request_id`, 입력, `session_id`, `revision`을 그대로 보낸다. 새 사용자 행동에만 새 ID를 만든다. 응답 유실·저장 확인 실패·처리 중 오류로 결과가 불명확하면 원래 요청을 먼저 복구하며 새 입력은 작성한 채 유지한다. 최초 응답 전체가 유실돼도 서버 전용 Supabase 키로 파생한 세션 ID로 같은 첫 요청을 찾는다. 키 자체와 원문은 ID에 포함되지 않는다. 키를 교체하면 세션 ID를 아직 받지 못한 첫 요청의 복구는 보장하지 못한다.
- `agent_session_command`가 행 잠금으로 실행 예약·취소·완료 반영·커서 갱신을 처리한다. 실행 중 중복은 409 `busy`, 완료된 최신 요청의 동일 재전송은 저장한 `run.finished` 응답을 재사용한다. 같은 ID에 다른 입력, 이전 버전, 이미 지나간 요청은 409 `state_conflict`다. 요청 ID 이력은 기존과 같이 세션당 최대 100개이며 완료 응답은 최신 한 건만 보관한다.
- 실패·취소·종료 줄 전 스트림 중단은 중간 조건과 버전을 저장하지 않는다. 실패는 같은 ID로 다시 실행할 수 있다. 수락된 취소는 최종 결과로 재사용하며 다시 검색하려면 새 요청 ID를 사용한다. 성공 완료와 취소의 순서는 DB에서 결정하며 취소가 먼저 수락되면 늦은 결과를 반영하지 않는다. 완료가 먼저 반영됐다면 취소는 `accepted:false`다. 브라우저는 취소 요청 중 후속 진행 이벤트를 무시한다.
- 실행 lease는 120초다. 작업자가 사라지면 만료 후 같은 요청을 다시 실행할 수 있다. 이전 작업자의 늦은 완료는 `run_id`로 차단한다. 이미 시작된 외부 조회를 강제 종료하지는 못하며 다음 도구 호출 전·결과 반영 시 취소를 확인한다. 상태 저장소 요청은 3초로 제한하고 장애 시 메모리로 대체하지 않는다. 완료 저장의 응답이 유실돼도 원래 요청을 재전송해 확인한다.
- 저장 항목은 최근 문답 최대 4개, 장소 후보·확정 위치, 물품 단서·검색어, 반경·기관 ID, 결과 개수·커서, 물품 안내용 최소 필드 캐시 최대 100개, 최신 완료 응답과 요청 식별·실행 메타데이터다. 사진 검색에서는 두 번째 페이지를 재현하는 데 필요한 물품 ID의 순서도 저장한다. 전체 대화 기록·업로드 이미지·키·인증 헤더는 저장하지 않는다. 물품 캐시에 없는 표시 항목은 현재 반경으로 다시 조회한다.
- 세션은 마지막 실행 예약·완료·완료 결과 재사용·페이지 반영 후 30분에 접근을 차단한다. 다음 요청에서 만료 행을 삭제하고 `pg_cron`이 매분 유휴 행을 삭제한다. 스케줄러가 정상 실행되면 논리 만료 후 다음 분에 물리 삭제하며 장애 시 복구 후 정리한다. 이 삭제는 DB 백업의 보존 정책을 변경하지 않는다. 예약 작업 자신의 실행 이력은 하루 뒤 정리한다. 테이블과 RPC는 RLS 및 `service_role` 전용이며 기존 서버 환경 변수만 사용한다.
- JSON 로그는 서버 `trace_id`, 실패 단계, 예외 종류, 안전한 외부 HTTP 코드, 소요 시간, 최종 상태만 기록한다. `timeout`, `busy`, `cancelled`, `state_conflict`, `session_expired`, `embedding.fallback`을 구분한다. 응답 HTTP 200이어도 `turn.finished.final_status=error`이면 실패다. 예외 문자열·스택·대화 원문·검색어·좌표·키·외부 본문·사용자 식별값을 로그에 쓰지 않는다. `trace_id`는 최종 응답과 스트림 전 오류 응답에도 포함한다. 임베딩 실패는 키워드 결과를 유지하며 별도 fallback 이벤트를 기록한다.

`20261120150000_agent_search_sessions.sql`은 기존 테이블과 검색 RPC를 변경하지 않는 추가 마이그레이션이다. 2026-11-20 사용자가 운영 DB 적용·병합·배포·운영 검증을 승인했고 운영 SQL을 적용했다. 앱 배포와 후속 검증 상태는 `docs/measurements.md`의 운영 기록을 따른다. SQL을 먼저 적용·확인한 뒤 앱을 배포한다. 이전 앱과 새 앱이 함께 떠 있는 동안 이전 메모리 세션은 새 공용 저장소로 이관되지 않으므로 새 대화가 필요하다. 되돌릴 때는 이전 앱으로 복귀하고 새 세션 객체는 유지한 채 만료 정리를 계속한다. 객체 삭제가 필요하면 별도의 새 마이그레이션으로 예약 작업 해제와 테이블·함수 삭제를 수행한다. 이미 적용한 SQL을 수정하거나 이력을 지우지 않는다.

검증은 `tests/web/test_agent_recovery.py`, `tests/web/agent_recovery.browser.cjs`, `tests/database/verify_agent_sessions.sql`로 실행한다. SQL 검증은 격리 DB에서만 수행하며 운영 적용 후에는 스케줄러 실행과 `service_role` 권한, 만료 행 정리를 추가 확인한다. 측정 결과와 검증 한계는 [측정 기록](measurements.md)에 남긴다.

## 대화형 다중 장소 — 2026-11-21

PRD 4.3-A·4.5의 사용자 승인으로 장소는 최대 3곳이다. 첫 장소 확정 뒤에는 “어떤 물품을 잃어버렸어요? 들렀던 장소가 더 있다면 함께 알려주세요.”라고 안내한다. 3곳을 채우면 물품만 질문한다. 기존 일반 검색의 좌표 중복 검사와 기관 합집합, 여러 중심점의 지도 반경·알림 조건을 재사용한다.

- LLM의 구조화된 행동에 `add_place`, `replace_place`, `remove_place`를 추가한다. 추가·변경할 검색어는 `place_query`, 변경·제거 대상은 서버가 전달한 확정 장소 목록의 1부터 시작하는 `target`이다. 대상이 여러 곳이면 모델이 확인 질문을 하며 서버는 범위를 검증한다. 물품 정정과 장소 추가를 함께 말하면 물품 단서도 보존한다.
- UI는 같은 검증 경로를 호출한다. `POST /api/search-chat/turns`에 `add_place`, `replace_place`, `remove_place`, `cancel_place_selection`을 허용하고 변경·제거에는 `place_target`을 전달한다. 추가·변경 요청은 후보 조회와 사용자 확정을 거친다. 같은 좌표의 중복과 3곳 초과는 `invalid_place`로 거절하고 기존 상태·버전을 유지한다.
- 응답 `conditions.places`는 확정 장소 목록, `place_operation`은 진행 중인 `add`·`replace` 또는 null이다. 기존 `conditions.place`도 유지한다. 후보를 확인하는 동안 확정 장소 목록은 보존하며 취소하면 기존 장소로 돌아간다. 장소 변경이 확정되거나 제거되면 기존 결과와 커서는 무효화하고 물품 조건이 있으면 통합 범위에서 재검색한다.
- 검색은 각 기관과 가장 가까운 확정 장소의 Haversine 거리를 사용한다. 반경과 기관 ID 합집합을 한 번 계산하고 기존 랭킹·커서 검색에 전달한다. 기관과 결과를 중복 노출하지 않는다. 반경 확대도 모든 장소에 같은 값으로 적용한다. 기존 기관 수 제한을 넘으면 기존 입력 오류로 처리하며 기관을 임의로 누락하지 않는다.
- 서버 세션 JSON에 장소 목록과 선택 작업을 보관한다. 이전 JSON에 이 필드가 없으면 기존 `confirmed`를 장소 한 곳으로 복원한다. DB 테이블·RPC 변경은 없다. 이 버전이 쓴 세션을 이전 코드로 되돌려 읽는 것은 지원하지 않으므로 앱 롤백 시 새 세션 시작 또는 기존 유휴 만료 처리가 필요하다.
- 지도에는 확정한 모든 장소와 반경을 표시하고, 추가 후보는 기존 반경을 유지하며 미리보기한다. 상단 장소별 변경·제거 버튼은 유지하고 추가 장소는 대화로 입력한다(2026-11-22 후속 결정으로 상단 추가 버튼 제거). 알림에는 전체 확정 장소 목록을 전달한다. 당근 링크는 기존 대표 장소 기준을 유지한다.

검증은 `tests/web/test_agent_places.py`에서 다중 장소·기존 세션·동일 요청 복구·기관 합집합을 확인한다. 실제 API 대신 모델·장소·기관 대역으로 확인하며 운영 DB 적용과 배포는 별도다.

### 한 발화의 여러 장소 순차 확인 — 2026-11-21

- 모델은 `place_queries`에 장소 검색어들을 발화 순서대로 반환한다. 전체 목록 지정은 `set_places`, 기존 목록에 추가는 `add_place`로 구분한다. 특정 지명에 대한 예외 처리나 문자열 구분자만으로 분리하지 않는다. 단일 장소 정정은 `place_query`로 현재 검색어만 바꾼다.
- 서버는 현재 검색어와 `pending_place_queries`를 보관하고 장소를 확정할 때 다음 후보를 조회한다. 중간 확인에서 물품 검색을 실행하지 않으며 마지막 확인 뒤 확정 목록의 통합 범위에서 검색한다. 물품 단서는 별도로 보존한다.

### 공통 대화 맥락 — 2026-11-23 사용자 승인

PRD 4.3-A·4.3-E. 기존 POST /api/search-chat/turns의 message 요청에 선택적인 dialogue를 추가한다. task는 search/alert, alert는 query·places(name/latitude/longitude)·radius, awaiting은 email/item/places/radius/conditions 또는 null, last_message는 직전 안내(최대 200자)다. 기존 요청은 검색 맥락으로 호환한다. 맥락의 개인정보는 차단하거나 번호를 마스킹하며 허용 좌표·반경·장소 수·물품 길이를 검증한다.

모델은 기존 행동과 task·alert_changes·awaiting을 JSON으로 반환한다. update_alert는 query/radius/remove_places(현재 초안의 1부터 시작하는 순번)를 함께 적용한다. 알림 응답은 answered와 dialogue(task/alert/awaiting/changed)를 반환한다. 초안 질문·안내·변경·종료는 검색 결과와 커서를 보존하고 기존 요청 ID 재생·revision 검증을 사용한다. 변경 불가·모델 장애 시 기존 초안을 유지한다. 모델 실패는 기존 error 형식, 잘못된 요청 맥락은 기존 400 invalid_request, 허용되지 않은 초안 변경은 answered와 한국어 안내다. 검색 복귀의 실제 결과에도 dialogue를 이어 전달해 화면을 전환한다.

자유 입력 한 턴은 공통 대화 모델을 한 번 호출한다. 기존 검색의 0건 재작성은 기존 별도 예산이다. 조건 변경과 사용법 질문이 함께 있으면 변경값과 message를 함께 반영한다. 메일 발송은 기존 동의와 /api/alerts의 검증을 통과한 이메일 입력 경로에서만 수행한다.

검색 실행과 함께 받은 사용법 답변은 응답의 선택적 explanation 필드로 전달하고 실제 검색 완료 안내 앞에 표시한다. 기존 결과 안내·카드 표시를 보존하면서 복합 요청의 설명을 누락하지 않는다.
